## 0. 先说结论

1. **金蝶云星空能按外部单号查付款单。** 付款单单据头自带「第三方单据编号」`FTHIRDBILLNO`。单据查询接口 `ExecuteBillQuery` 可以按任意字段过滤，一次最多返回 10000 行（[付款单 API 文档](https://github.com/chonggit/wlog/blob/main/08.%E9%87%91%E8%9D%B6/WebAPI%E6%96%87%E6%A1%A3/%E8%B4%A2%E5%8A%A1%E4%BC%9A%E8%AE%A1__%E5%87%BA%E7%BA%B3%E7%AE%A1%E7%90%86__%E4%BB%98%E6%AC%BE%E5%8D%95.md)）。所以「目标里恰好一张」和「状态已审核」都能读回核对。
2. **金蝶不提供对方幂等键，防重交给调用方。**
   - 官方 API 文档在保存接口的备注里写：「对于重要API接口，应设置幂等性校验、设置对应候选键（唯一性字段）的唯一索引等防重调用机制，以防并发导致数据重复」。
   - `ValidateRepeatJson` 只拦「Json数据包重复传入」，判定方式和时间窗都没写。
   - 苍穹的「防止重复请求」据转述只管 30 秒（二手）。
   - 所以「恰好一张」要靠平台按业务键串行、写之前先读回，不能指望目标替你去重。
3. **保存 → 提交 → 审核是三步，停在任何一步都是合法状态。**
   - 单据状态有 Z 暂存、A 创建、B 审核中、C 已审核、D 重新审核。「读当前状态，做剩下的步骤」这种收敛走得通。
   - 但付款单在金蝶里配了审批流时，审核接口默认校验流程实例；单据还在流程中，就不能直接调审核（金蝶云社区，2024-06-28）。这时「已审核」要等金蝶里的人点。
   - 应有结果因此第一次出现了「等对方的人做完」这种正常等待，它不是失败。
4. **回写 OA，三家差别很大。**
   - 飞书审批改不了已结束实例的表单，但可以写评论。评论带 `extra` 附加字段，能分页读回，所以回写可以核对。
   - 致远的标准 REST 能读流程状态和表单数据。改流程表单要写流程事件插件（客开），或者改写到「无流程」底表。
   - 泛微 E9 的 REST 有新建、提交、查询流程，但没查到修改已归档流程表单的接口。一线常见做法是在节点上挂 Action，同步调 ERP。
   - 所以「单号回写到源」要单列成一项应有结果，并注明判断依据。
5. **源头会反悔。** 飞书里，发起人可以撤销已通过的审批（事件状态 `REVERTED`）；致远有撤销、终止。应有结果因此不是只增不减：审批撤销以后，应有的是「零张有效付款单」。已经付款、已经登账的付款单撤不回来，只能交给财务。
6. **多张单据汇总成一张凭证时，凭证的业务键不来自源系统，而是由汇总规则算出来的批次键。**
   - 台账分两级：源单「已入账」，以它所在批次的凭证到位为准；批次「凭证到位」，要求恰好一张、借贷平衡、合计等于各成员之和。
   - 已过账的凭证改不了，只能红冲或补差，所以批次的「补到位」要先预演，再由人确认。
   - 源单本身就在金蝶里时，汇总应该交给金蝶的智能会计平台。官方支持一对一、全部汇总、匹配汇总三种方式，平台只管每条一份。
7. **企业微信要一把钥匙写、一把钥匙读。**
   - 自建应用只能读、不能写，而且只能读可见范围内的人；2022-06-20 以后新建的自建应用读不到手机、邮箱、企业邮箱、头像、性别、地址。
   - 写通讯录只能用「通讯录同步」secret；这把 secret 从 2022-08-15 起在新 IP 上只能读到 userid 和部门 ID。
   - 所以用通讯录同步写，用自建应用读回核对。两边拿到的 userid 都是明文，一致（[账号 ID](https://developer.work.weixin.qq.com/document/path/98728)）。
8. **`design-inputs.md` 里「企业微信不支持增量、只能全量」要改准。**
   - 读这一侧确实没有按时间查变更的接口。
   - 文档列出的变更回调接收方是通讯录同步助手、代开发应用和上游企业共享的应用，没有普通自建应用（需实测）。通讯录同步助手在 2022-08-15 以后新配置的回调只带 ID，更新事件只在部门或 UserID 变化时才触发。
   - 写这一侧可以逐条写，也可以用 CSV 增量导入或全量覆盖。
   - 按 userid 读一个人，可以；递归列出全员，也可以。
9. **企业微信上，声明式同步和结果台账都做得了，差别在字段能不能核对。**
   - 姓名、部门、职务、启用状态能读回核对；手机和邮箱只能说「写过了」，不能说「核对过」。已激活成员的手机号更新还会被静默忽略。
   - 企业微信自己就有「全量覆盖成员」这种声明式原语，还自带删除阈值，但它的语义是删除，而且会连带删掉企业邮箱，不能直接拿来用。
10. **推荐：原型用「飞书审批 → 金蝶云星空付款单，回写为审批评论」检验模型；实施路线先做「北森 → 企业微信」。**
    - 金蝶这条覆盖了六处首发主线没有的东西：每条一份、多步状态、对方人工环节、第二个目标（回写）、源头撤销、批次。
    - 企业微信这条复用首发主线的源端、处理工作流、台账和问题，只换目标。它考的主要是连接器的能力声明和跨人交接；模型只多出一处「字段级依据」。

### 这一轮核对的前提

| --- | --- | --- |

## 1. 审批通过 → 金蝶付款单并回写 OA

### 1.1 按外部单号查询

**星空。** 出处是付款单 `AP_PAYBILL` 的在线 API 文档（[镜像](https://github.com/chonggit/wlog/blob/main/08.%E9%87%91%E8%9D%B6/WebAPI%E6%96%87%E6%A1%A3/%E8%B4%A2%E5%8A%A1%E4%BC%9A%E8%AE%A1__%E5%87%BA%E7%BA%B3%E7%AE%A1%E7%90%86__%E4%BB%98%E6%AC%BE%E5%8D%95.md)）。

- 付款单开放的操作有：删除、暂存、保存、查看、提交、审核、反审核、撤销、下推、作废、批量保存、单据查询、单据查询(json)、元数据查询、工作流审批、切换组织，以及同步银行状态、同步当前银行状态、同步交易时间。
- 「单据查询」`ExecuteBillQuery` 和「单据查询(json)」`BillQuery` 的参数：
  - `FormId`、`FieldKeys`、`OrderString`、`TopRowCount`、`StartRow`、`Limit`；`Limit`「不能超过10000」。
  - `FilterString` 是一个条件数组，每个条件有 `Left`、`FieldName`、`Compare`、`Value`、`Right`、`Logic`。
- 「查看」`View` 按单据编码 `Number` 或内码 `Id` 取整张单据。
- 付款单单据头上有三个字段，都在保存接口允许引入的字段里：
  - `FTHIRDBILLNO` 第三方单据编号
  - `FSOURCESYSTEM` 来源系统
  - `FSourceBillNumber` 来源票据号

外部单号放在哪，有两种做法：

| 做法 | 好处 | 代价 |
| --- | --- | --- |
| 放进 `FTHIRDBILLNO` | 标准字段，不用二开；查询直接按它过滤 | 它不是唯一键，金蝶不会拦重复 |
| 把单据编号 `FBillNo` 直接设成 OA 审批号 | 用 `View` 就能按编号取 | 要求编码规则允许手工录入，会打乱财务的编号；编号重复时会不会被拒，取决于编码规则的唯一性校验（需实测） |

读回核对的查询长这样：`FormId=AP_PAYBILL`，`FieldKeys` 取 `FID,FBillNo,FDOCUMENTSTATUS,FCancelStatus,FTHIRDBILLNO,FPAYAMOUNTFOR`，过滤条件 `FTHIRDBILLNO = 审批号`。按 `FID` 去重以后：

- 0 张：还没生成；
- 1 张：已生成，再看状态和金额；
- 多张：重复，属于高危。

只查单据头字段时，结果会不会按分录展开成多行，需实测。

有一个容易忽略的点：查询受集成用户的组织和数据权限约束。查不到不等于不存在。如果集成用户看不到某个付款组织，平台会把「已经有了」当成「还没生成」，再建一张（推断，需实测）。

**苍穹（二手）。**

- 苍穹没有星空那样全局通用的 `ExecuteBillQuery`。
- 每个业务对象的每种操作（查询、保存、提交、审核……）都要由管理员在「开放服务云 → OpenAPI → API 开发」里零代码发布一次。路由是 `/kapi/v2/{isv}/{appId}/{formId}/{serviceName}`。
- 查询条件和返回字段在发布时就固定了，查询必须带分页。
- 来源：[操作API介绍](https://vip.kingdee.com/knowledge/555316763412680192)、[查询操作API](https://vip.kingdee.com/knowledge/555400185669328896)（需登录，经 Lingya 笔记转述）。

所以在苍穹上，「按外部单号查」不是连接器自己能做到的事：先得由金蝶管理员发布一个以外部单号为查询条件的 API。这又是一项对方后台待办。

### 1.2 幂等创建

- **`ValidateRepeatJson`。** 星空的保存、批量保存都有这个参数，原文是「校验Json数据包是否重复传入，一旦重复传入，接口调用失败，传true则启用校验，传false则不校验」。
  - 判定的范围和时间窗，文档都没写。
  - 平台重试时，只要数据包里有一个字段不同（例如备注带了时间戳），它就拦不住。
  - 需实测。
- **官方把防重交给调用方。** 同一份文档在保存、批量保存的备注里写：「对于重要API接口，应设置幂等性校验、设置对应候选键（唯一性字段）的唯一索引等防重调用机制，以防并发导致数据重复。」
- **客户金蝶里可以加唯一性校验。** 金蝶云社区提到，可以在保存操作的校验规则里加「合法性检查，检查组合字段唯一性」（二手）。这项配置在客户的金蝶里做，要由金蝶管理员或实施方完成。
- **苍穹（二手，[保存操作API](https://vip.kingdee.com/knowledge/555401045317338880)、[OpenAPI 整体介绍](https://vip.kingdee.com/knowledge/523450118653958400)）。**
  - 保存操作 API 用「候选键」决定更新还是新增：命中候选键就更新，不传就新增。还可以开 `judgeKeyRepeatCheck`。
  - 操作 API 可以打开「防止重复请求」：相同参数 30 秒内只执行一次。
  - 把外部单号配成候选键，保存就变成了按外部单号的 upsert。单据审核之后还能不能被这样覆盖，需实测。
- **一线集成平台也在平台侧防重。** 轻易云的泛微 → 金蝶差旅报销方案，把 OA 的 `requestId` 配成 `idCheck` 去重键，写入用 `batchSave`（[厂商文章，2024-11-09](https://www.cnblogs.com/qliang-cloud/p/18537362/KINGDEE-FW)）。

小结：「恰好一张」要靠三件事一起保证。

1. 平台按业务键串行：同一个审批号，同一时刻只有一个处理在跑。
2. 写之前，先按外部单号读回。
3. 超时之类「结果未知」的情况，先读回再决定，不盲目重发。

客户愿意的话，再在金蝶里加唯一性校验，作为第二道闸。

### 1.3 保存 → 提交 → 审核

接口和参数（在线 API 文档 + [WebAPI 接口说明书 V6.0](https://vip.kingdee.com/article/490771221039228672)）：

- **单据操作。** 保存 `Save`、批量保存 `BatchSave`、提交 `Submit`、审核 `Audit`、反审核 `UnAudit`、撤销 `CancelAssign`、删除 `Delete`、作废 `Cancel`、工作流审批 `WorkflowAudit`。除保存外，都按单据编码 `Numbers` 或内码 `Ids` 批量操作。提交、审核、删除还有 `NetworkCtrl`（是否启用网控）参数。
- **`IsAutoSubmitAndAudit`：别用。**
  - V6.0 说明书里有这个参数：「是否自动提交与审核，布尔类型，默认false」。
  - 现行在线文档的保存参数里已经不再列出。
  - 金蝶云社区文章写：「避免使用参数【IsAutoSubmitAndAudit：True】平台最新说明里面已经屏蔽此参数了，在大并发时此参数可能会导致某些服务未正常执行」（[程晓峰，2023-11-27](https://vip.kingdee.com/article/11179)）。
- **审核前会校验审批流。**
  - 审核接口有参数 `IsVerifyProcInst`：「是否检验单据关联运行中的工作流实例，布尔类型，默认true」。
  - 金蝶云社区文章说（[eris，2024-06-28](https://vip.kingdee.com/article/512660052604278528)）：单据提交进流程后再调传统审核，会出现「单据已审核，工作流程终审节点还未处理」。从 2023 年 11 月的补丁起改为默认校验，「如果单据在流程中，将不能直接调传统审核接口」。
  - 出路有两条：改流程的启动条件，让 API 建的单不进流程；或者调 `WorkflowAudit`，以审批人身份审批。`WorkflowAudit` 的参数有 `ApprovalType`（1 通过、2 驳回、3 终止）、`UserId` 或 `UserName`、`PostId`、`Disposition` 等。
- **会话。** 登录后会话默认保持 20 分钟，期间每次调用都会续期；V6.0 说明书写明「不要每次调用WebAPI都去先调用登录接口」。返回的 `MsgCode=1` 表示会话丢失，要重新登录。
- **单据状态的取值。** 在线文档只写了字段 `FDOCUMENTSTATUS`，没列取值。下面的取值来自多个开源对接库的一致说法（二手，例如 [kingdee-k3cloud-skill](https://github.com/adamzhang1987/kingdee-k3cloud-skill/blob/main/kingdee-k3cloud/references/verified-fields.md)）。

按「读当前状态 → 做剩下的步骤」收敛，平台在每种状态下的动作：

| 读到的状态 | 应有结果是「已审核」时，平台下一步 | 说明 |
| --- | --- | --- |
| 查不到 | 保存，带上 `FTHIRDBILLNO` | 先确认查询权限覆盖所有付款组织 |
| Z 暂存 | 保存 | 下推接口的注释说「暂存的单据是没有编码的」 |
| A 创建 | 提交 | |
| B 审核中 | 不动作；单据在金蝶流程中时，等金蝶审批人，超过时限提醒 | 合法等待，不是失败 |
| C 已审核 | 核对金额、收款单位，然后去回写 | |
| D 重新审核 | 不自动重提，读出差异交给财务确认 | 有人反审核过，可能正在修改，平台不该和人抢 |
| 多张 | 停下，按高危交给财务 | 重复 |

### 1.4 常见错误与谁能修

| 错误 | 证据 | 谁能修 |
| --- | --- | --- |
| 基础资料不存在、未分配到组织、反审核、作废：往来单位、收款单位、结算方式、付款用途、银行账号、费用项目 | 付款单字段说明里标「必填项」的有 19 个，往来单位、收款单位、结算方式、付款用途、付款组织都是基础资料引用；社区文章列出的不合法情形是「未分配、反审核、作废」（程晓峰，2023） | 数据所有者：财务系统管理员、主数据管理员 |

### 1.5 苍穹与星空的差别（二手）

这一节都转述自 Lingya 笔记，它引用的知识库页面需要登录。

- **每个对象、每种操作都要先发布 API。** 星空是全局通用的 WebAPI；苍穹的读写都要先在开放服务云里发布，保存、提交、审核、反审核、删除、撤销、下推各是一个 API。下推只支持整单。
- **保存的系统参数。**
  - `multiOps`：组合执行，例如 `save,submit,audit`。
  - `forcedAudit` 加 `WF=false`：跳过工作流，直接审核。
  - `mutex_ignoremodify`：忽略网络互斥。
- **统一返回结构。** `{status, errorCode, message, data{result, failcount, successcount}}`；提交、审核这类操作另带 `filter`、`totalCount`。
- **鉴权。** 增强型 Token：`getToken` 1 分钟限 30 次，有效期 2 小时，只能放在请求头里。R202410.001 起，业务 API 还要带 `x-acgw-identity` 头（[认证方式](https://vip.kingdee.com/knowledge/537672007656380928)）。
- **对产品的影响。**
  - `WF=false` 能绕过财务的审批流，这是客户的内控问题，平台不该默认用它。
  - 接苍穹的前置工作比星空多：发布若干操作 API、给第三方应用授权、取身份凭证。这些都是对方后台待办。

### 1.6 回写 OA

| OA | 能写回吗 | 能读回核对吗 | 前提与代价 |
| --- | --- | --- | --- |
| 飞书审批 | 没查到修改已结束实例表单的接口。可以「创建评论」，内容是 JSON，另有 `extra` 附加字段；传 `comment_id` 可以修改已有评论（[创建评论](https://open.feishu.cn/document/server-docs/approval-v4/instance-comment/create)） | 能。「获取评论」返回每条评论的 `id`、`content`、`commentator`、`extra`、`is_delete`，可以分页（[获取评论](https://open.feishu.cn/document/server-docs/approval-v4/instance-comment/list)） | 评论必须以某个用户的身份写（`user_id` 必填）；频率 1000 次/分钟、50 次/秒 |
| 致远 A8 | 标准 REST 没有修改流程表单的接口。改流程表单要写流程事件插件，在「事前事件」里 `addFieldValue`（客开）。「无流程的批量更新」`cap4/form/soap/batch-update` 只针对无流程底表（Since V8.0），支持按 `uniqueFiled` 更新，登录名必须有底表操作权限（[CAP4表单应用接口](https://open.seeyoncloud.com/seeyonapi/728/750.html)、[表单流程集成](https://open.seeyoncloud.com/seeyonapi/728/734.html)） | 能读。`flow/data/{flowId}` 取表单数据；`flow/state/{flowId}` 取流程状态（0 结束、3 待处理、4 处理中、5 撤销、6 回退、7 取回、15 终止）；`flow/FromFinish/{templateCode}/{startTime}/{endTime}` 按模板和日期取已结束的流程 | 写到底表是变通，审批人在单子上看不到；客开要 OA 实施方来做 |
| 泛微 E9 | Token 认证之后，`/api/workflow/paService/` 下有新建 `doCreateRequest`、提交 `submitRequest`、查询 `getWorkflowRequest` 等（[丸子·张](https://oneszhang.com/archives/197.html)，二手）。没查到修改已归档流程表单的接口。一线做法是在节点后附加操作（Action）里同步调 ERP，失败就返回 `FAILURE_AND_CONTINUE` 阻止提交（[CSDN，2023-03-16](https://blog.csdn.net/weixin_46041943/article/details/129378443)） | 能读，`getWorkflowRequest` | 想异步回写，需要 OA 管理员在流程里加一个「等待 ERP」节点，由接口账号提交（`submitRequest` 能否同时改主表字段，需实测）；否则只能客开 |

泛微 Token 认证的几处坑，来自官方文档（[云商店 Token 认证使用步骤](https://e-cloudstore.com/doc.html?appId=af09c25938714c26b9736f535ca20fc9)）：

- **OA 侧要先配三样。** 配接口白名单（「配置后的白名单需要重启生效」）、发许可证 `appid`、可选地限制注册端 IP（`allowIp`）。
- **注册只能做一次。** 原文：「第一步接口再次请求时会更新原有密钥，导致密钥不匹配解密失败」；「对于分布式异构系统需要自行解决并发状态下密钥被更新的问题」。
- **token 和 userid。** token 默认 1800 秒过期；调用业务接口时，`userid` 要用注册时返回的公钥 `spk` 加密。

源头「不漏」这一侧，三家都能靠拉取兜底：

- 飞书：订阅 `approval_instance` 事件，加上「批量获取审批实例 ID」。后者按审批定义和创建时间查，「单次查询时间范围不要超过10小时」，限 100 次/分钟（[批量获取审批实例 ID](https://open.feishu.cn/document/server-docs/approval-v4/instance/list)）。
- 致远：用 `FromFinish` 按模板和日期取已结束的流程。
- 泛微：用 `getWorkflowRequest` 读流程数据。

### 1.7 「每条一份」能否读回核对

| 子结果 | 星空 | 苍穹 | 判断依据 |
| --- | --- | --- | --- |
| 目标里恰好一张 | 能：按 `FTHIRDBILLNO` 查张数；前提是查询权限覆盖所有付款组织 | 能，但要先发布以外部单号为条件的查询 API | 读回核对 |
| 状态到位（已审核） | 能：`FDOCUMENTSTATUS = C`；付款单有审批流时，要等金蝶审批人 | 能 | 读回核对 |
| 内容一致（金额、收款单位、行数） | 能，而且必须核对：保存成功不代表行没丢 | 能 | 读回核对 |
| 单号回写到源 | 飞书：能（评论加 `extra`）。致远：能读不能改，改要客开或写底表。泛微：能读，异步写要加流程节点或客开 | 同左 | 视 OA 而定：读回核对、只有写入记录，或者不做 |

结论：「每条一份」这个形态成立，但要拆成能分别判定的子结果，每个子结果写明依据。回写要能单独关掉：有的客户的 OA 根本不允许回写。

还有一种情况：一张审批可能要生成几张付款单，例如付给几个收款单位。这时「份」按子键数，子键是审批号加收款单位或明细行号，`FTHIRDBILLNO` 里放子键，台账行显示「3 张中 3 张已审核」（推断）。

### 1.8 源头反悔：撤回与撤销

- **飞书。** 「发起人撤销已通过的审批时，触发该事件并推送 REVERTED（已撤销）状态」。此外还有 `CANCELED`（发起人撤回）、`DELETED`（审批定义被删）、`OVERTIME_CLOSE`（超时被关闭）（[审批实例状态变更](https://open.feishu.cn/document/server-docs/approval-v4/event/common-event/approval-instance-event)）。
- **致远。** 流程状态有撤销 5、终止 15。
- **应有结果随源头当前状态变。** `APPROVED` 时，应有一张已审核的付款单；`REVERTED` 时，应有零张有效付款单。
- **收敛到「零张」的动作，取决于付款单走到了哪一步。**
  - 状态 A、B：撤销提交或删除，需实测。
  - 状态 C：反审核后作废，前提是还没付款、没登账。付款单上有「是否登账」`FISPOST`、「银行处理状态」`FBankStatus` 等字段可以判断。
  - 已经付款：平台不自动处理，交给财务。

### 1.9 批次：多张单据汇总成一张凭证

**金蝶自己怎么做。**

- 「智能会计平台是系统提供的自动生成凭证的工具，基本实现方式是根据定义好的凭证模板，对业务系统的单据生成业务凭证和总账凭证」（[智能会计平台概述](https://open.kingdee.com/K3Cloud/help/TM_NewTopic3.html)）。
- 凭证生成的使用前提是「凭证模板已设置；业务单据已审核」。总账凭证的生成方式分一对一、全部汇总和匹配汇总；匹配汇总指来源单据上匹配字段值相同的多张业务凭证汇成一张（[凭证生成](https://help.open.kingdee.com/dokuwiki/doku.php?id=%E5%87%AD%E8%AF%81%E7%94%9F%E6%88%90)）。
- 「凭证生成情况查询」是一张报表，「全面展示业务单据是否生成凭证、对应的凭证号、未生成原因等信息」（[凭证生成情况查询](https://help.open.kingdee.com/dokuwiki/doku.php?id=%E5%87%AD%E8%AF%81%E7%94%9F%E6%88%90%E6%83%85%E5%86%B5%E6%9F%A5%E8%AF%A2)）。它能不能通过 WebAPI 读到，未查到。苍穹的官方路线是写自定义 API，在里面调报表 SDK（二手）。

**凭证本身**（[凭证 API 文档](https://github.com/chonggit/wlog/blob/main/08.%E9%87%91%E8%9D%B6/WebAPI%E6%96%87%E6%A1%A3/%E8%B4%A2%E5%8A%A1%E4%BC%9A%E8%AE%A1__%E6%80%BB%E8%B4%A6__%E5%87%AD%E8%AF%81.md)）：

- 单据头上没有第三方单据编号字段。分录上有「业务编号」`FBUSNO` 和摘要 `FEXPLANATION`。
- 凭证号 `FVOUCHERGROUPNO` 是必填项，但会被「凭证整理」重新编号。原文：「该操作是不可撤消的」；「已过账凭证不允许再对凭证号进行整理」（[凭证整理](https://help.open.kingdee.com/dokuwiki/doku.php?id=%E5%87%AD%E8%AF%81%E6%95%B4%E7%90%86)）。
- 所以对应关系里存凭证内码 `FVOUCHERID`；凭证号只用来显示，每次读回时重新取。

**两种情况，业务键的粒度不同。**

1. **源单本身在金蝶里**（付款单、应付单、报销单）。汇总交给金蝶，平台只管「每条一份」。凭证生成是金蝶内部的事，平台最多加一个只读的「已生成凭证」子结果；这要先确认报表读得出来。
2. **源单不在金蝶里**（费控系统、业务系统直接出凭证）。平台要自己汇总：
   - **批次键**：账簿 + 会计期间（或业务日期）+ 凭证字 + 汇总维度的取值（例如部门、费用类型）+ 封口序号。它由汇总规则算出来，不来自任何源系统。
   - **封口**：到点（例如 T+1 零点）冻结这一批的成员名单。迟到的单进下一批，已封口的批次不再打开。
   - **源单这一级**：应有结果是「被某个已到位的批次包含，且金额一致」。凭证内码和分录号回写到源单。
   - **批次这一级**：应有结果是「恰好一张凭证、借贷平衡、合计等于成员之和、状态到位」。写凭证时，在分录的 `FBUSNO` 里填源单号或批次键，读回时按它对。
   - **补到位**：
     - 还没生成：生成。
     - 已生成未审核，但和成员对不上：预演差异，由人确认后修改，或者删掉重建。
     - 已审核或已过账：不动原凭证，生成红冲或补差凭证，由人确认。
   - **边界**：T+1 批量汇总离「搬数」很近。`users-and-scenarios.md` §3.9 把它标为「在边界内，但按批次处理」。建议首发不做；第二阶段只做「源单在金蝶里」那一种。

### 对设计的含义

1. **连接器契约改成「幂等键或查重键」。** 写操作至少声明其一：幂等键（飞书 `client_token`），或者查重键（能按业务键读回的字段，例如金蝶 `FTHIRDBILLNO`）。金蝶这类目标只有查重键。平台统一把「结果未知」处理成「先按查重键读回，再决定」，不再把它当成要人确认的独立流程。
2. **平台按业务键串行。** 同一个业务键，同一时刻只允许一个处理在跑（用 `distributedLock`），不指望目标替你去重。金蝶里的唯一性校验算客户可选的第二道闸，写进方案的安装清单。
3. **「每条一份」拆成子结果，每个子结果带依据。** 例如：金蝶单据（读回核对）、单据状态（读回核对）、OA 回写（视 OA 而定：读回核对、只有写入记录，或者关闭）。子结果之间有依赖：回写要等单号出来。时限从审批通过起算，每个子结果可以有自己的时限。
4. **台账行要有「合法等待」，和失败分开。** 等金蝶审批人、等 OA 回写节点、等员工激活，都是「已处理，等对方的人」。超过时限才变成「逾期」，再进问题。`design-inputs.md` 里的「等待对方」现在只是问题的一种状态；台账行也需要它。
5. **应有结果跟着源头的当前状态算，「零张」也是一种应有结果。** 撤销时，默认只自动处理到「已审核、未付款」为止，再往后进问题，交给财务。
6. **读回时核对内容，不只看存在。** 金额、收款单位、行数都要比；保存时默认打开基础资料校验。
7. **区分「查不到」和「无权查」。** 平台认定「未生成」之前，连接要先证明自己的查询范围覆盖了全部组织。这一项放进连接健康检查；不通过时，不允许执行创建类的补到位。
8. **「谁能修」多出五种人**：财务系统管理员（基础资料、科目）、金蝶里的审批人、金蝶管理员（权限、许可、发布 API、唯一校验）、OA 管理员（白名单、appid、回写节点）、集成工程师（字段顺序、映射）。
9. **批次是由规则算出键的派生业务记录。** 它不是新增的第五种结果形态。源单仍然按「每条一份」进台账，批次作为它的「经过」出现。首发不做。

### 2.1 2022 年之后的读写边界

| --- | --- | --- | --- | --- |
| 通讯录同步 secret | 能：创建、更新、删除成员和部门、标签；还有异步导入（增量更新成员、全量覆盖成员、全量覆盖部门） | 2022-08-15 起，「新的IP（过去90天通讯录同步助手未使用过的IP）」只能调「获取成员ID列表」「获取部门ID列表」，拿到 userid 和部门 ID。读取成员、获取部门成员、获取部门成员详情、获取部门列表、获取单个部门详情、导出成员、导出成员详情、导出部门，一律停用。历史 IP（8 月 15 日前已配进可信 IP 的，以及系统按过去 90 天的调用记录自动补进去的）暂不受影响，「针对历史IP的接口调整将另行提前通知」 | 8 月 15 日后新配置或改过 URL 的回调，成员属性只回 `UserID`、`Department`；更新事件「只会在成员部门相关变更……或UserId变更的情况下触发」；同步助手自己通过 API 新增的成员，不回调给自己 | 「只有管理员才可以看到“管理工具” - “通讯录同步”这个工具，其他分级管理员无操作权限」；要开启 API 接口同步、设读或编辑权限；必须配企业可信 IP，「请配置本企业服务器的IP地址，不允许配置第三方服务商的IP」；回调 URL「需要配置本企业主体的域名链接」 |
| 自建应用 secret | 不能。创建、更新、删除成员的权限说明都写着「仅通讯录同步助手或第三方通讯录应用可调用」 | 能读可见范围内的成员。2022-06-20 以后新建的应用，「不再返回以下字段：头像、性别、手机、邮箱、企业邮箱、员工个人二维码、地址」，要成员本人用 OAuth 授权才拿得到；这之前建的应用，仍可读敏感字段 | 文档列出的成员变更通知接收方是通讯录同步助手、代开发自建应用、上游企业共享的应用，没有普通自建应用（需实测） | 2022-06-20 以后新建的自建应用必须配可信 IP。配可信 IP 之前，要先设可信域名或接收消息服务器 URL：社区文章引的是 2022-09-16 的通知，2023 年之后的界面提示是「配置企业可信IP前，请先设置可信域名或设置接收消息服务器URL」。可信域名的主体要和企业的认证主体一致 |
| 代开发应用、第三方应用 | 第三方通讯录应用经「通讯录编辑授权」后可以写 | 升级后拿到的是密文 userid（`open_userid`） | 代开发应用默认收回调 | 属于服务商主体，不适合自托管 |

### 2.2 通讯录同步 secret 写入的细节

| 细节 | 原文 | 对平台意味着什么 |
| --- | --- | --- |
| userid 由调用方指定 | 「企业内必须唯一。长度为1~64个字节……系统进行唯一性检查时会忽略大小写」；「如果userid由系统自动生成，则仅允许修改一次」；重复创建报 60102「UserID已存在」 | 可以拿工号或按规则生成的值直接当 userid，对应关系天然确定，重复创建也安全 |
| 部门不存在时自动新建 | 「当填写的部门不存在时，会在其他（待设置部门）下新建对应部门」 | 映射错了不会报错，而是静默建出垃圾部门，必须在写之前校验 |
| 默认发邀请 | `to_invite`「默认值为true」，通过微信服务通知、短信或邮件下发，「每天自动下发一次，最多持续3个工作日」 | 新建成员有对外副作用，预演里要写清楚 |
| 手机号静默忽略 | 「若成员已激活企业微信，则需成员自行修改（此情况下该参数被忽略，但不会报错）」 | 「更新成功」不等于手机号已改 |
| 企业邮箱不是原子更新 | 「biz_mail_alias、biz_mail与更新其他字段的操作不具备原子性」 | 会出现部分成功 |
| 停用 | `enable` 1 启用、0 禁用；读回的 `status`：1 已激活、2 已禁用、4 未激活、5 退出企业 | 「暂停账号」可以做，也能读回核对 |
| 删除 | 「若是绑定了腾讯企业邮，则会同时删除邮箱账号」 | 删除不可逆，还会连带删掉企业邮箱，首发仍然只停用 |
| 频率 | 每个企业调用单个接口不超过 1 万次/分、15 万次/小时；「每企业创建账号数不可超过账号上限数*3/月」（[访问频率限制](https://developer.work.weixin.qq.com/document/path/90312)） | 上线第一天批量开通要按账号上限算预算 |
| 异步导入 | 上传 CSV 拿 `jobid`，结果按 userid 逐条给 `errcode`（[获取异步任务结果](https://developer.work.weixin.qq.com/document/path/90983)） | 批量导入也能逐人记账 |
| 全量覆盖成员 | 「通讯录中存在、文件中不存在的成员，执行删除操作」；删除的人数「多于50人，且多于现有人数的20%以上」或「少于50人，且多于现有人数的80%以上」时中止导入（[全量覆盖成员](https://developer.work.weixin.qq.com/document/path/90981)） | 这是企业微信自带的声明式原语和闸门，但语义是删除；增量更新成员（`syncuser`）只增改、不删人（[增量更新成员](https://developer.work.weixin.qq.com/document/path/90980)） |

### 2.3 能否读回核对

用自建应用调「读取成员」（按 userid 读一个人），或「获取部门成员详情」（逐个部门读）。可见范围要覆盖全员。

| 字段 | 写（通讯录同步） | 读回（2022-06-20 以后新建的自建应用） | 依据 |
| --- | --- | --- | --- |
| 是否存在、userid | 能 | 能 | 读回核对 |
| 姓名 | 能 | 能 | 读回核对 |
| 部门、主部门 | 能 | 能（只返回应用有查看权限的部门） | 读回核对 |
| 职务 | 能 | 能 | 读回核对 |
| 启用、禁用、激活状态 | `enable` | `status` | 读回核对 |
| 直属上级 | 能 | 文档没写自建应用受限，需实测 | 待定 |
| 手机号 | 能（已激活的成员会被忽略） | 不能 | 只有写入记录 |
| 邮箱、企业邮箱 | 能 | 不能 | 只有写入记录 |

两点补充：

- 只核对「谁存在」时，可以用通讯录同步 secret 的「获取成员ID列表」拿全员的 userid 和部门 ID，不受可见范围限制。它「仅支持通过“通讯录同步secret”调用」，一页 1 到 10000 条（[获取成员ID列表](https://developer.work.weixin.qq.com/document/path/96067)）。
- 2022-06-20 之前建的自建应用还能读手机号。所以「能不能核对手机号」是一个连接的属性，不是连接器的属性。

### 2.4 全量还是增量

- **北森这一侧**不变：时间窗增量加定期全量，见 `users-and-scenarios.md` §3.2。
- **企业微信读这一侧**：
  - 没有按时间查变化的接口。
  - 全量：用通讯录同步 secret 调 `list_id`，再用自建应用逐个部门调 `user/list`。文档原文：「如需获取该部门及其子部门的所有成员，需先获取该部门下的子部门，然后再获取子部门下的部门成员，逐层递归获取」。
  - 单人：`user/get`。
- **企业微信事件**：新配置的回调只告诉你部门变了、userid 变了。有人在管理后台改了姓名、职务，或者手工停用了某人，事件里看不到，只能靠定期全量读发现。
- **企业微信写这一侧**：逐条接口、CSV 增量导入、CSV 全量覆盖，三种都有。
- **结论**：对账只能全量读，读的是企业微信这一侧。按每分钟 1 万次的频率，几千人、几百个部门的全量读不是瓶颈（推断）。

### 2.5 上线第一天和跨人交接

**对齐存量成员。** 现有成员的 userid 多半是管理员手填的，或者系统生成的，和工号对不上。可用的匹配办法：

- **按手机号或邮箱查 userid。** 逐个查，前提是「应用须拥有指定成员的查看权限」。注意原文：「请确保手机号的正确性，若出错的次数超出企业人数上限的20%，会导致1天不可调用」（[手机号获取userid](https://developer.work.weixin.qq.com/document/path/95402)、[邮箱获取userid](https://developer.work.weixin.qq.com/document/path/95895)）。北森里手机号脏的话，第一天对齐就可能把这个接口打封。
- **用自建应用读全员（不含手机号），按姓名加部门批量预匹配。** 重名的要人确认；只有拿不准的人才按手机号查，并给剩下的出错额度留余量。
- **请管理员从后台导出通讯录。** 导出文件里有哪些字段，需实测。

**对方后台待办**（集成工程师自己做不了）：

- 通讯录同步：管理员开启 API 接口同步，设编辑权限，配可信 IP。
- 自建应用：创建；可见范围设为全员（否则读不到）；配可信 IP；先配好主体一致的可信域名，或者接收消息服务器 URL。
- 网络：固定出口 IP。一个可信 IP 只能用于一个企业，「如果用于多个企业将被认定为服务商」（[阿里云 IDaaS 对接企业微信](https://help.aliyun.com/zh/idaas/eiam/user-guide/bind-idaas-to-wecom)）。自托管在这一点上反而占优，见 `china.md` §11.3。

### 2.6 声明式同步（方向 B）的可行性

- **能做。** 源和目标都能列出全量，能按 userid 精确匹配，既能逐条写，也能批量写。
- **要额外处理的事。**
  - 差异只能算在可核对的字段上。手机号、邮箱只能设成「仅创建时写入」，和 Entra 属性映射里的「Only during object creation」是一类（`declarative-sync.md` 有对照）。
  - 一个同步要用两把钥匙：自建应用负责读，通讯录同步负责写。连接模型得支持这样分工。
  - 企业微信自带的全量覆盖是删除语义，和「首发只停用不删除」冲突。只能用逐条写或增量导入，平台自己算差异。
  - 第一天的匹配，受手机号查询出错率的封禁限制。
- **结论。** 在企业微信上，B 做得到；但引擎要处理字段级的可核对性和两把凭证。B 的主要风险（第二个场景进不来，要再写一个引擎）不会因为换成企业微信而变小。

### 2.7 结果台账（方向 C）的可行性

- **能做。**
  - 按 userid 读回：补到位之后马上就能核对一个人。
  - 能全量对账。
  - 状态读得出来：未激活、已禁用都能分辨。
- **要额外处理的事。**
  - 「到位」要按字段给依据：姓名、部门是「读回核对」，手机号是「依据：写入记录」。
  - 「已开通、未激活」要等员工本人在邀请里完成激活，属于合法等待；它可以带自己的时限，例如入职三天还没激活就提醒。
  - 对账靠全量读，要按企业微信的频率排程。
- **结论。** C 在企业微信上成立，前提是应有结果支持字段级的依据。

### 对设计的含义

1. **一个连接可以有几把凭证，按能力分工（读、写）。** 连接器按字段声明「可写」「可读回」。台账上每个字段的依据由这份声明决定，不允许界面写「已核对」而实际只写入过。
2. **能力按连接探测，不按连接器写死。** 2022-06-20 之前建的自建应用能读手机号，之后建的不能；同步助手在 8 月 15 日前的历史 IP 还能读详情。连接向导读一份样本来判定能力，判定结果进入「依据」。
3. **写之前的预检：**
   - 部门 ID 必须存在，否则会静默建出新部门。
   - `to_invite` 的默认值，在预演里写清楚。
   - 第一天对齐时，按手机号查 userid 要按出错率预算来排；批量开通按「账号上限 ×3/月」预算。
4. **「暂停账号」在企业微信里是 `enable=0`。** 删除会连带删掉企业邮箱，所以保持「首发只停用不删除」。批量停用的闸门照旧；企业微信在全量覆盖里也设了删除阈值，和我们的闸门是同一类保护。
5. **对方后台待办单要有企业微信版。** 至少包括：通讯录同步只有管理员能开、可信 IP、可信域名要和企业主体一致、自建应用可见范围设为全员。
6. **对账必须全量读企业微信。** 这是发现后台手工改动的唯一办法，因为事件里看不到。
7. **方案换目标时，变的只有目标连接器的能力声明和交接清单。** 北森侧、处理工作流的骨架、台账、问题都不变。这正好对上 `critique-v3.md` 实验 1 的要求：换了方案，界面上不出现上一个系统的名字。

## 3. 结论：两个候选各检验了什么

### 3.1 对照

| 模型的部件 | 审批 → 金蝶并回写 OA | 北森 → 企业微信 |
| --- | --- | --- |
| 结果形态 | 每条一份（首发没有）；批次（派生键） | 保持一致（和首发相同） |
| 业务键 | 审批实例 ID；一张审批生成多张单据时要子键；批次键由规则算出 | 工号 ↔ userid，可以直接相等 |
| 「到位」怎么判 | 读回张数、状态、金额；回写这一项要看 OA | 读回存在、姓名、部门、职务、状态；手机号、邮箱只有写入记录 |
| 幂等 | 目标没有幂等键，靠平台串行加查重键 | userid 唯一，天然幂等 |
| 合法等待 | 金蝶审批流、OA 回写节点 | 员工激活 |
| 源头反悔 | 审批撤销后，应有零张 | 离职停用（和首发相同） |
| 补到位 | 单据：读状态续跑；批次：先预演，再由人确认 | 和首发相同 |
| 谁能修 | 财务系统管理员、主数据管理员、金蝶审批人、金蝶管理员、OA 管理员 | 企业微信管理员（只有管理员能开通讯录同步）、网络管理员 |
| 连接 | 苍穹要对方先发布 API；泛微 Token 只能注册一次，要处理并发 | 两把凭证；可信 IP，加上主体一致的域名 |
| 要新做的连接器 | 金蝶星空；飞书审批的操作（现有飞书连接器没有审批相关操作，见 `platform-inventory.md` §1.14）；泛微或致远 | 企业微信通讯录（现在只有告警渠道） |

### 3.2 推荐

**原型用来验证模型的，选「审批 → 金蝶」。** 具体组合是「飞书审批 → 金蝶云星空付款单，回写为审批评论」。

- **为什么选它。**
  - 它检验的是应有结果这个抽象本身：每条一份、子结果和依据、合法等待、源头撤销、重复（高危）、谁能修。
  - 只画首发主线，模型会再一次长成人员同步的形状。
  - 选飞书审批，是因为回写能读回核对，原型可以把「三个子结果都核对过」完整地画出来；而且仓库里已经有飞书连接器，补审批相关的操作比新接泛微、致远便宜。
- **只画运维面，在 `design-inputs.md` 第 4 节第 5 问的基础上补四处：**
  - 台账里一行展开后，看得到三个子结果和各自的依据；
  - 一张「等待金蝶审批，第 2 天」的合法等待；
  - 一个撤销（审批已撤销，付款单已作废，回写已更新）；
  - 一个「同一审批号两张付款单」的高危问题。
- **批次不画搭建。** 最多在台账里放一行派生记录的示意。

**实施路线上先做的，选「北森 → 企业微信」。** 「审批 → 金蝶」排在它后面。

- **为什么先做企业微信。**
  - 它复用首发主线的源端、处理工作流、台账和问题，只换目标；模型只多出一处「字段级依据」。
  - 风险集中在连接器上：两把凭证、字段级可核对、只能全量读、手机号查询有封禁；还有交接清单。这些都能单独交付。
  - 产品备忘本来就把企业微信排在第二批连接器里，而告警渠道已经有了企业微信。
- **审批 → 金蝶为什么排后面。** 它要新做三类连接器，还依赖客户那边的配置：唯一性校验、审批流的启动条件、集成用户的权限；泛微、致远的回写还要客开。第二阶段先做星空加飞书审批；泛微、致远等真有客户再做。

### 对设计的含义

1. **方向 C 保留，「应有结果」的定义补三样：**
   - 子结果和各自的依据（读回核对，还是只有写入记录）；
   - 合法等待（对方的人还没做完，不算失败）；
   - 随源头的当前状态变化，包括「零」。

   方向 B 的模型里只有「一致、不一致」，表达不了每条一份的子结果和对方的人工环节。方向 A 能表达，但算不出健康口径。
2. **连接器契约补三条：**
   - 写操作声明幂等键或查重键；
   - 字段级的「可写」「可读回」；
   - 能力按连接探测。

   连接器深度清单（`design-inputs.md` 第 5 节）要相应加上这几项机器检查。
3. **方案的安装清单要按目标系统列出对方待办：**
   - 金蝶：唯一性校验、审批流启动条件、集成用户的组织权限。
   - 苍穹：发布操作 API、给第三方应用授权。
   - 泛微：接口白名单、`appid`、回写节点。
   - 致远：底表或客开。
   - 企业微信：管理员开通讯录同步、可信 IP、主体一致的域名、可见范围。
4. **首页口径仍然是一套。** 两个场景都能用「到位、等待对方、未到位、逾期」说话；人员同步的「一致」只是「保持一致」形态下的到位。
5. **`design-inputs.md` 里有两句要改：**
   - 「企业微信不支持增量、只能全量」改成「读的一侧没有增量，写的一侧有」；
   - 「用对方的幂等键让结果未知极少出现」改成「用幂等键或查重键，结果未知一律先读回」。

## 未查到与需实测

- **金蝶 `ValidateRepeatJson`**：判定方式和时间窗；平台重试时数据包稍有不同还能不能拦住。需实测。
- **金蝶 `FBillNo`**：手工指定时，重复编号会不会被拒。需实测。
- **`FTHIRDBILLNO` 的唯一性校验**：在 BOS 里配「组合字段唯一性」的具体步骤，以及并发下能不能挡住。需实测。
- **只查单据头时的返回行数**：`ExecuteBillQuery` 会不会按分录展开成多行。需实测。
- **查询权限**：集成用户的组织权限不全时，查询是返回空还是报错。需实测。这一项决定「查不到」和「无权查」能不能区分。
- **作废状态的取值**：`FCancelStatus` 各取值的含义，未查到原文。
- **撤销已审核付款单的路径**：已审核付款单反审核、作废的前提条件（与付款、登账、银企状态的关系）。需实测。
- **星空的调用频率限制**：`MsgCode=14`「调用限制」的阈值，未查到。
- **集成用户的许可**：星空集成用户要不要单独的许可，未查到。
- **苍穹知识库原文**：候选键 upsert、「防止重复请求」30 秒、`WF=false`，都只有二手转述，需登录核对，再在苍穹环境实测。
- **凭证生成情况**：「凭证生成情况查询」报表能不能通过星空 WebAPI 读到，未查到。
- **泛微 E9**：有没有修改已归档流程表单的标准接口，未查到；`submitRequest` 提交时能不能同时改主表字段，需实测；E10 的开放接口未查到。
- **致远**：`updateCacheFormData` 能不能用于已结束的流程。文档说的是「更新后端表单的数据缓存，在保存表单时会将缓存中的值存入数据库中持久化」，看起来针对的是正在编辑的表单。需实测。
- **飞书审批**：能不能修改已结束原生审批实例的表单，没查到对应接口，按「不能」处理。
- **企业微信，普通自建应用的回调**：能不能收到成员变更事件，需实测。
- **企业微信，直属上级字段**：自建应用读成员时返回不返回 `direct_leader`，需实测。
- **企业微信，通讯录同步 secret 查 userid**：在新 IP 上还能不能调「手机号获取userid」（它不在停用列表里），需实测。
- **企业微信，禁用与删除的差别**：禁用成员占不占账号数、会不会触发离职继承，未查到。
- **企业微信，后台导出**：管理后台导出的通讯录里有哪些字段，需实测。
- **访谈要问的**：客户的付款单有没有在金蝶里配审批流；OA 允不允许回写，回写写到哪；财务能不能接受平台在金蝶里加唯一性校验。
