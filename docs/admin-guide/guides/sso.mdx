## Overview

Each tenant decides how people are allowed to authenticate: which email domains are accepted, and
whether email-and-password login is available at all. Both settings live on the tenant, so a tenant
admin can change them without an operator touching environment variables.

Navigate to **Tenant Settings** → **Security** → **Authentication** to configure them.

## Allowed domains

Restrict authentication to a list of email domains — `acme.com`, `acme.co.uk` — so only addresses at
your organisation can sign in or accept an invitation. It applies to sign-up and sign-in alike; an
address outside the list is rejected with `DOMAIN_NOT_ALLOWED` before any account is created.

The list and the enforcement switch are two separate fields. While enforcement is **off**, the list is
ignored and every address is accepted.

<Warning>
Enforcement **on** with an empty list rejects everyone, including you. It is not read as "no
restriction" — an address is allowed only if it matches an entry. Add your own domain before turning
enforcement on.
</Warning>

Matching is exact on the part after `@`, trimmed and lower-cased on both sides. Subdomains do not
inherit: `acme.com` does not admit `someone@mail.acme.com`, and a lookalike like
`someone@acme.com.evil.com` is rejected.

## Email and password login

Turn **Allowed Email Login** off to stop accepting email-and-password credentials for the tenant.
Existing sessions are unaffected; new sign-ins through the password form are refused with
`EMAIL_AUTH_DISABLED`.

<Warning>
Turning email login off leaves a tenant with no interactive sign-in method, because this build ships
no federated identity provider. Only do it for a tenant whose users are provisioned and driven through
the API.
</Warning>

## What this build does not include

There is no SAML, no Google or GitHub sign-in, and no identity-provider discovery by domain. The
tenant record still carries a `federatedAuthProviders` column from upstream, and the API rejects any
attempt to write a SAML configuration into it with *"SAML SSO is not available in this build"*.

The OIDC endpoints the server exposes (`/v1/worker/...` and the discovery document at the domain root)
authenticate **workers**, not people — they are part of the execution tier, not a sign-in method.
