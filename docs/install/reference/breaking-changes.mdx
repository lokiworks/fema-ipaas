## Unreleased

### What has changed?

#### First-party connectors ship inside the image

A fresh install used to have no connectors at all: every connector, including
HTTP, Webhook, Schedule and AI, had to be downloaded from a connector registry that
`FEMA_CONNECTOR_REGISTRY_URL` pointed at, and that variable has no default. Worse,
when no registry was configured the hourly sync deleted every `OFFICIAL` connector
row it found.

The 24 first-party connectors are now built into the image and loaded from it
directly, with no download or install step:

- When `FEMA_DEV_CONNECTORS` is unset, every connector built into the image is
  loaded. Setting it (even to an empty string) keeps the old development
  behaviour of loading only the listed connectors.
- A workflow pinned to a connector version the image does not carry runs on the
  bundled version when it has the same major version and is not older than the
  pin. A different major version is not substituted.
- With no registry configured, the connector sync is skipped instead of deleting
  connectors.
- The image base moves from Debian 11 (bullseye) to Debian 12 (bookworm), because
  the bullseye security archive no longer serves packages and the image could not
  be built.
- Built-in connectors run in the default `UNSANDBOXED` and `SANDBOX_CODE_ONLY`
  execution modes. The isolate modes (`SANDBOX_PROCESS`,
  `SANDBOX_CODE_AND_PROCESS`) and the slim `Dockerfile.worker` image do not carry
  them yet.

**When is action necessary?**

If you run the worker with `FEMA_EXECUTION_MODE=SANDBOX_PROCESS` or
`SANDBOX_CODE_AND_PROCESS`, keep a connector registry configured for now. If you
set `FEMA_DEV_CONNECTORS` in production, unset it to get every built-in connector.
If you build your own image on top of ours and install system packages, check them
against Debian 12.

#### Community and support links are hidden by default

The "Help translate" link in the language menu and the support entries in the
workflow editor header used to be shown on every instance. They point at an
upstream community that a self-hosted deployment does not run, so they are now
hidden unless you opt in.

- New variable `FEMA_SHOW_COMMUNITY` (default `false`) controls them.
- The static page title shown before the app loads is now the neutral
  `Integration Platform`; the title after load still comes from your tenant
  appearance settings.

**When is action necessary?**

Only if you want the links back: set `FEMA_SHOW_COMMUNITY=true`.

#### Webhook URLs are now rate limited per workflow

Anyone who held or guessed a webhook URL could call it without limit. Public webhook
URLs (`/api/v1/webhooks/:workflowId` and its `/sync`, `/draft` and `/test` variants)
now accept at most **600 requests per workflow per 60 seconds**. The counter is shared
by all variants and methods of one workflow and by all API instances (it lives in Redis).
A request over the limit is rejected with **HTTP 429** and a `Retry-After` header
(seconds until the window resets); it is not queued and starts no run. Rejections are
recorded in the request log with `webhook.rateLimited=true`.

- New variable `FEMA_WEBHOOK_RATE_LIMIT_MAX` (default `600`). Set it to `0` to turn the
  limit off.
- New variable `FEMA_WEBHOOK_RATE_LIMIT_WINDOW_SECONDS` (default `60`).
- The authentication rate limit switch `FEMA_API_RATE_LIMIT_AUTHN_ENABLED` keeps working
  as before and does not affect webhooks.

**When is action necessary?**

Only if a sender posts more than about 10 requests per second to a single workflow, for
example a bulk import that calls one webhook once per row. Make the sender honour
`Retry-After` and retry, raise `FEMA_WEBHOOK_RATE_LIMIT_MAX`, or set it to `0` to
disable the limit.

#### The last of the billing and plan vocabulary is gone

This fork has no editions, plans or credits, but several leftovers from upstream
were still in the code and, in one case, on screen:

- The `QUOTA_EXCEEDED` run status and the matching `ErrorCode` are removed. Both
  call sites that could produce it sat behind a hardcoded `const creditsExhausted
  = false`, so no run could ever reach that state, yet the builder still carried a
  message about the tenant running out of credits. `execution.status` is a
  `varchar` and no row used the value, so no migration is needed.
- `Tenant.plan` is now `Tenant.limits`, and the `TenantPlan` / `TenantPlanLimits`
  schemas are a single `TenantLimits`. `TenantPlan` described a `tenant_plan`
  table that does not exist. Instance-wide caps still live in `SYSTEM_LIMITS`,
  unchanged.
- `tenantService.getOneWithPlanOrThrow` and `getOneWithPlanAndUsageOrThrow` are a
  single `getOneWithLimitsOrThrow`; the second only delegated to the first.
- The `BILLING_USAGE_REPORT` system job name and the `TenantUsageMetric` enum are
  removed — nothing scheduled or read them.
- The project settings form no longer offers **Active Workflows Limit**. The field
  was never sent to the API and the `project` table has no column for it, so
  filling it in did nothing.

**When is action necessary?**

If an API consumer reads `plan` off the tenant response, read `limits` instead —
the shape of the object is unchanged. Anything filtering runs by the
`QUOTA_EXCEEDED` status should drop it; no run has ever carried that status.

#### Connector HTTP requests now verify TLS certificates

Every outbound request made through the connector HTTP client used to run
`process.env.NODE_TLS_REJECT_UNAUTHORIZED = '0'` before sending. That switch is
process-wide and was never restored, so a single connector call silently disabled
certificate verification for everything else running in the same worker or API
process — including OAuth token exchanges and the platform's own outbound calls.

Certificates are now verified by default. A request that genuinely needs to reach a
host with a self-signed or otherwise untrusted certificate opts out for itself by
setting `rejectUnauthorized: false` on the request, which is scoped to that one call
through its own dispatcher and never touches process-wide TLS settings. The **HTTP**
connector exposes this as the **Allow untrusted TLS certificate** checkbox.

**When is action necessary?**

If a workflow talks to an internal service over HTTPS with a self-signed or
private-CA certificate, that step now fails with a certificate error. Either install
the certificate authority on the host running the worker, or tick **Allow untrusted
TLS certificate** on the HTTP step. Workflows that only call public HTTPS endpoints
need no action.

#### Workspaces are now called Projects, across the database, routes and API

The organisational unit between a tenant and its users is renamed from **Workspace** to **Project**, end to end and with no aliases kept.

- **Database** — the `workspace` and `workspace_member` tables become `project` and `project_member`; every `workspaceId` / `workspaceIds` / `workspaceRoleId` / `workspaceUsage` / `workspaceDisplayName` / `preSelectForNewWorkspaces` column is renamed to its `project*` equivalent, along with every index and foreign key that carried the old word. Migration `RenameWorkspaceToProject1787900000006` performs the rename and is fully reversible.
- **Routes** — `/workspaces/:id/...` becomes `/projects/:id/...`. Bookmarked links to the old paths no longer resolve.
- **API** — request and response models use `projectId` in place of `workspaceId`, and the authenticated principal exposes `projectId`.
- **CLI** — the `workspace` command becomes `project`.
- **Sandbox settings** — `WORKSPACE_WORKER` becomes `PROJECT_WORKER`.

#### What you need to do

Run the migration; it renames in place and preserves all rows. Then update anything outside the app that referenced the old names: API clients sending or reading `workspaceId`, scripts calling `/api/v1/workspaces`, saved links to `/workspaces/:id/...`, and any deployment that sets `WORKSPACE_WORKER`. There is no compatibility shim — the old names stop working the moment the migration runs.


### What has changed?

#### Encrypted payloads now carry a key id, enabling encryption key rotation

Values encrypted at rest (connections, variables, OIDC keys) now store the id of the key that encrypted them. Rotation is supported end to end: set `FEMA_ENCRYPTION_KEY` to the new key, list the previous one in the new `FEMA_RETIRED_ENCRYPTION_KEYS` (comma separated, 32-char hex each), then call `POST /v1/encryption/rotate` as a tenant admin to re-encrypt existing rows.

#### What you need to do

Nothing to upgrade. Payloads written before this change carry no key id and are still decrypted by trying the current key and then each retired key, so existing data keeps working untouched. You only need `FEMA_RETIRED_ENCRYPTION_KEYS` when you actually rotate — and it must stay set until `POST /v1/encryption/rotate` reports no remaining rows, or values encrypted with the old key become unreadable.

#### Project permissions are now enforced, and project access requires membership

Every route already declared a `Permission`, but nothing checked it — reaching a project at all granted everything inside it. The permission is now enforced against the caller's project role, and the permission vocabulary moved to the `RESOURCE:ACTION` form (`WORKFLOW:READ`, `CONNECTION:MANAGE`) with four roles: Admin, Developer, Operator, Viewer.

Access itself is also narrower. A user reaches a project only as its owner, as a tenant admin, or through a row in the new `project_member` table. Accepting a project invitation now creates that row; previously the invitation was marked accepted and granted nothing.

#### What you need to do

Project owners and tenant admins keep full access and need no action. Any other user who previously reached a project without an accepted project invitation will be denied until they are added — call `POST /v1/project-members` with `projectId`, `userId` and `role`, or re-send the invitation. API consumers that stored permission strings must move to the new `RESOURCE:ACTION` values; the old `READ_WORKFLOW`-style strings are no longer recognised.

#### Connector builds fail when connector code uses `__dirname` without declaring `bundleForkedEntries`

The connector bundler now emits files a connector loads by path at runtime (for example a `child_process.fork` target) beside the main bundle, when they are declared in a `bundleForkedEntries` array in the connector's `package.json`, and it keeps dependencies that only those files import in the published manifest. Because an undeclared `__dirname`-relative file access always breaks after publishing — this is exactly how `@fema-ipaas/connector-oracle-database` 0.1.11/0.1.12 shipped with every new connection failing — the build now fails loudly when a connector's source references `__dirname` and declares no forked entries. Previously such a connector built successfully and shipped broken.

#### What you need to do

Nothing for catalog connectors — oracle-database is the only connector that forks a sibling file, and this change fixes it (0.1.13). If you build custom connectors and one references `__dirname`, either declare the runtime-loaded file in `bundleForkedEntries` (see [Bundling Connectors](/build-connectors/misc/bundling-connectors)) or remove the `__dirname` usage. Already-published connectors keep working; the check runs at build time only.

#### MCP OAuth: revoking a token requires a client identity, and registration issues a usable secret

Two changes to the MCP OAuth endpoints:

- `POST /revoke` used to revoke a refresh token for a caller that presented no client identity at all, so anyone who learned a refresh token could disconnect its owner. It now requires the request to identify the client, and a confidential client to authenticate, per RFC 7009. A revocation that sends only `token` now returns `400 invalid_client`.
- Dynamic client registration (`POST /register`) that omits `token_endpoint_auth_method` now records the client as `client_secret_basic` and issues a client secret, per RFC 7591. It previously issued a secret but recorded the client as public, so that secret was never checked. A client registered from now on must present it when calling `/token` and `/revoke`. Concretely: a client that omits `token_endpoint_auth_method` **and** discards the `client_secret` it is handed now gets `400 invalid_client` at `/token`, where it previously succeeded. Such a client must either store and send that secret, or register explicitly with `token_endpoint_auth_method: "none"` to stay public.

#### What you need to do

Nothing for already-connected clients. A client's authentication method is read from the row it registered with, so existing registrations are untouched, including the ones created before this fix that hold a secret while recorded as public. Those keep working whether or not they send it.

Claude, Cursor and anything else built on the MCP SDK are unaffected: the SDK stores and sends the `client_secret` it is given, and it never calls the revocation endpoint. A confidential client's secret is accepted from either the request body or the `Authorization: Basic` header, so a client is never rejected for choosing one over the other.

If you maintain your own MCP OAuth client, check two things before upgrading: that it sends `client_id` when it revokes a token, and that it stores and presents the `client_secret` that `/register` returns. Note that disconnecting and re-adding an MCP server creates a fresh registration, so an existing user meets the new behaviour when they reconnect rather than at upgrade.

#### Agent steps move from the workflow engine to the server

An agent step used to run its loop inside the engine, holding a worker for as long as the agent took. It now pauses the workflow, runs on the server, and resumes when the agent finishes. This upgrade rewrites every existing agent step to the new version.

The step's inputs and its output shape are unchanged, so anything reading the step's result or its structured output keeps working. Sub-workflow, MCP server, knowledge base and connector action tools all run on the new path.

Two differences are worth knowing before you upgrade:

- **Web search is no longer a step setting.** It follows what the platform has configured rather than a per-step toggle. A step that had it switched on keeps working; the stored value is ignored.
- **Max steps is honoured up to a ceiling.** The value you set still applies, but the server caps a single run at 50 turns. A step configured above that runs 50.

#### What you need to do

Nothing on upgrade. Check any agent step that relied on the per-step web search toggle, or that set max steps above 50, since those now follow the platform and the server ceiling.

#### The container no longer bundles PM2 — crashes exit the container

The Docker image used to run the app and worker under PM2, which restarted a crashed process *inside* the container. PM2 is removed; the entrypoint now launches the processes with plain `node`. When a process crashes (or is OOM-killed), the container exits instead of silently recycling the process in place, and your orchestrator restarts it.

#### What you need to do

Nothing if you deploy with Docker Compose, Kubernetes/Helm, or any orchestrator that already restarts failed containers (all official deployments do). If you run the image with a bare `docker run` and relied on PM2 to keep the container alive across process crashes, add a restart policy: `docker run --restart unless-stopped ...`.
#### Table record filters compare date columns chronologically

The `gt`, `gte`, `lt` and `lte` operators on `GET /v1/records` used to parse every cell value as a number. On a Date column that meant `2026-08-12T14:30:00Z` was read as `2026`, so two dates in the same year always compared equal and a range filter matched nothing. Those four operators now compare Date and Date & Time columns as instants.

This affects the Tables connector's Find Records action and any direct API call that filters a Date column with a range operator. `eq`, `neq` and `co` are unchanged and still compare the stored text exactly, so two spellings of the same instant (`...T14:30:00Z` and `...T14:30:00.000Z`) do not match each other.

#### What you need to do

Nothing on upgrade. Re-check any workflow or API integration that filters a Date column with `gt`, `gte`, `lt` or `lte` — it now returns the rows the filter actually describes, which may be more or fewer than before.

#### Emailed sign-in codes allow ten wrong guesses per account per hour

The six-digit login code already allowed five wrong guesses, but that budget lived on the code itself, and the fifth wrong guess threw the code away — so asking for a new code handed out five fresh guesses immediately, with no ceiling on how often that could repeat. A six-digit code is only a million possibilities, so unlimited retries reduce it to a matter of hours.

Wrong guesses are now counted per account over a rolling hour, independently of how many codes get sent. Entering the right code clears the counter, so someone who fumbles a few digits and then succeeds is unaffected.

Two consequences worth knowing. Someone who spends ten wrong guesses on an account within an hour cannot sign in **with an emailed code** until the hour is up; password and Google sign-in are unaffected. And because the counter is keyed on the account rather than the caller, anyone who knows an address can spend that budget on the owner's behalf — a temporary nuisance for the owner, and the trade the cap is worth making.

#### What you need to do

Nothing. The limit applies out of the box and needs no configuration. If your support team sees a report of "the code keeps saying it's wrong", have them check whether the account has burned its hourly budget, and point the user at password or Google sign-in in the meantime.

#### One-time codes are no longer stored in a readable form

The `otp` table used to hold the six-digit sign-in code as plain text, so anyone who could read the database — a replica, a backup, a support query — could sign in as any account for the ten minutes that code was alive, without a password. Codes are now stored as a digest keyed with a server-held secret, so reading the table no longer yields anything you can sign in with. The code itself is held only long enough to re-send it if the person asks for it again.

A code found to be expired is thrown away when it is next presented, rather than sitting in the table until the same person happens to request another one.

#### What you need to do

Nothing, and no new configuration: the key is derived from a secret your instance already has. Codes written by an older build are recorded as such and keep working until they expire, so a sign-in already underway when you deploy still completes, an email verification link still opens, and a rolling deploy where both builds are serving at once behaves the same.

Rolling back costs at most the codes issued after the deploy: the older build cannot read those, so whoever holds one asks for a fresh code. Nothing is rewritten and nothing is deleted, so no cleanup is needed either way.

#### Expired connections are a status of their own, and reconnecting must use the same account

A connection whose token can no longer be refreshed used to be marked **Connection error**. It is now marked **Expired** (已过期), so a lapsed authorization is no longer confused with credentials that failed validation.

- A failed OAuth2 refresh, or a failed custom-auth refresh, records `EXPIRED`. `ERROR` stays for connections whose credentials failed the connection test.
- Neither status is refreshed again automatically. Both count as "not usable" before a run starts, in the builder's validation and in the engine: a step that uses one fails with an expired-connection error, and all such failures group into one issue per connection in the Issue Center.
- Connections that were already in `ERROR` are **not** converted to `EXPIRED`. They stay as they are until someone reconnects or retests them.
- Reconnecting an existing connection now has to use the **same account**. The platform compares the account the stored credentials belong to with the account of the new ones (ignoring case and surrounding spaces) and refuses the save with a `409` when they differ: `This connection was authorized as A, but the new credentials belong to B. Reauthorize with the same account, or create a new connection for the other account`. Placeholder connections (status **Missing**) are never checked.
- The check only runs when both sides expose an account identifier: an email in the OAuth2 token response, or an identifier the connector provides. Connections made of an App ID and Secret, such as the Feishu and Beisen connectors, expose none and are not checked.
- A member who only has **Can Use** on a broken connection can press **Remind the owner to reconnect** (提醒所有者重新授权). The owner gets an in-app notification; the same person can remind about the same connection once every 6 hours. API: `POST /v1/connections/:id/remind-reauth`.

**When is action necessary?**

Yes, for every connection that now shows **Expired**. Open **Connections**, open the connection and choose **Reconnect** (重新连接), signing in with the account that created it. If that account is gone, create a new connection for the new account and use **Replace connection** (替换连接) to repoint the workflows that used the old one.

Connections still showing **Connection error** from before the upgrade are worth one pass: reconnect them, or run the connection test again, so their status reflects the cause.

#### "Can Edit" for project members no longer applies to the Viewer role

A connection can give every member of its projects **Can Use** (可使用) or **Can Edit** (可编辑). Setting **Can Edit** used to let Viewers rename the connection, share it and change which projects it is available in. Now a member's permission is capped by their project role: where the role cannot write workflows (Viewer), **Can Edit** counts as **Can Use**. Operator, Developer and Admin are unaffected, and so is a **Can Edit** that was granted to a person directly.

**When is action necessary?**

Only if you relied on Viewers editing connections. Give them a Developer or Admin role in the project, or share the connection with them directly.

#### Project invitations are permission-checked

`POST /v1/user-invitations` for a project only checked that the caller could reach the project, not that the caller could manage invitations. A Viewer could invite their own email address as **Admin** and so promote themselves. The calls are now checked against the caller's project role:

- Sending and deleting a project invitation needs the invitation-management permission. Only the project **Admin** role has it, plus the project owner and tenant admins. Operator, Developer and Viewer get `403`.
- Listing project invitations needs access to that project and a project id; listing tenant invitations (`type=TENANT`) needs a tenant admin.
- An invitation token that does not verify (malformed, expired, or signed with another key) now returns `404`.
- Without SMTP configured, the **Invite member** (邀请成员) dialog now shows the invitation link to copy, with the note that links expire after 7 days. Before, the link existed in the API response and the dialog did not show it.

**When is action necessary?**

Only for scripts and integrations that create project invitations as a non-admin member: send them as a project Admin, the owner or a tenant admin. Instances without SMTP need nothing, the dialog now hands over the link.

#### Several project endpoints now check the caller's project role

A security audit of every route found endpoints that checked only project membership, so a role with fewer rights than the screen suggested could still call them. These are now checked against the caller's project role (`403` otherwise):

- `POST /v1/workflows/:id`: changing the status needs the permission to run workflows, publishing (`LOCK_AND_PUBLISH`) needs the publish permission, and everything else (importing a definition, moving to a folder, changing metadata or the owner) needs the permission to edit workflows. **Operators can no longer edit, import or publish a workflow through this endpoint.**
- `POST /v1/projects/:id/info`: renaming a project or changing its description or icon needs the permission to manage the project. **Developers can no longer do it.**
- `POST /v1/sample-data/test-step`, `POST` and `DELETE /v1/test-trigger`, `POST /v1/trigger-events`, `POST /v1/connectors/options` and the editor's test-run socket message need the permission to edit workflows. **Viewers and Operators can no longer test steps and triggers.**
- `POST /v1/templates/from-workflow` needs the permission to manage templates. **Viewers can no longer publish a workflow as a tenant template.**
- MCP services: membership of a service no longer grants access on its own. The caller must be the owner, a member of the project, or the service must be published and available to them. A personal key stops working as soon as its holder leaves the project or the service is unpublished.
- Viewers can no longer take the edit lock of a workflow in the editor, and approving an agent action needs the permission to run workflows (Operator and above).

Also: a tenant owner can no longer be demoted to a regular member, a workflow cannot point at a folder or an owner from another project or tenant, a private AI model connection is only usable by its owner, and engine tokens can no longer write runs, waitpoints or files of another project.

**When is action necessary?**

Only for scripts, integrations or habits that relied on the looser checks. Give the person the role that has the permission (Developer to edit workflows and manage templates, Admin to manage the project), or call the endpoint with a token of such a user.

#### More failures reach the Issue Center, and its numbers are counted differently

- **Trigger failures create issues.** A polling trigger that cannot check for new events, for example because Beisen rate-limited the tenant or the credentials were rejected, used to leave no trace. It now opens an issue on the trigger step, and the issue resolves itself when the trigger next checks successfully.
- **Timeouts and out-of-memory runs create issues.** The engine cannot tell which step was running when a worker kills a run. The API now takes the step that was still `RUNNING` when the run ended (or the last step, or the trigger) as the failed step. Runs that timed out before this release have no issue.
- **Issues close themselves** when the cause is gone: when every failed run of an issue has been replayed successfully, and when a workflow is deleted (its open issues are resolved by the system; issues grouped by connection are unaffected). Both are recorded in the issue's activity.
- **"Merged N" on alerts and the issue's total impact count triggers**, not attempts. A rerun that fails again, an in-place retry, or the same run recorded twice no longer adds to the count or to the alert's merged total. A rerun that fails again still reopens a resolved issue.
- **Deleting an alert policy keeps its alert history.** Migration `KeepAlertRecordsAfterPolicyDeletion1790940000000` drops the foreign key from `alert_record` to `alert_policy` and cascades from the tenant instead. History rows of a deleted policy show **Deleted policy** (已删除的策略). Rolling this migration back deletes the history rows whose policy no longer exists.
- **"Last 7 days" and the other day ranges are calendar days, in the viewer's time zone.** Run logs (3/7/15/30 days), the Issue Center summary, project home statistics, alert statistics and the monitor page all count the 7 calendar days that end today, starting at local midnight, instead of a rolling 168 hours or a UTC midnight. The browser sends its zone as the `timezone` query parameter (an IANA name such as `Asia/Shanghai`); callers that omit it get UTC. Ranges from 15 minutes to 24 hours are still rolling windows.
- **Alerts for capacity** (a project's runs this month reaching the threshold of its limit) are also delivered as an in-app notification to the project owner and the tenant admins, once per policy and project per month.
- **A connector can mark a failure as blocked until a time.** When the Beisen API rate-limits a tenant, the error now ends with a machine-readable line `[blocked-until=<ISO time>]` (00:00 Beijing time the next day). Until that time the issue says not to retry, and the replay dialog holds those runs back as **Blocked** instead of offering them as transient errors; after it, they replay as before. The issue signature does not change. Custom connectors can use the same line (`blockedUntilMarker` from the connector SDK); API clients that parse run error messages will see the extra last line.
- **The run monitor's "Executed steps" (and the per-run average) now include the step a failed run stopped at.** Before, only steps that completed were counted, so many failures pulled the average down. The stored per-run step count and the `FEMA_MAX_NODES_PER_RUN` cap are unchanged. Steps whose failure was ignored or sent to a branch are still not counted.

**When is action necessary?**

No configuration. Expect issues you have not seen before after the upgrade, especially on trigger steps, and expect totals on dashboards to differ from the old numbers. API clients that compute their own windows should pass `timezone`.

#### Workflows and connections that are still in use can no longer be deleted

- A workflow cannot be deleted while another workflow of the same project calls it with a **Call workflow** (subflows) step, or while an MCP service uses it as a tool. The delete returns `409` and names the callers: `This workflow is called by workflows X and used as a tool by MCP services Y. Remove those references before deleting it`. Deleting a whole project or tenant is not blocked. The batch delete of the workflow list (`DELETE /v1/project-workspace/batch`) applies the same check to every selected workflow before it deletes any, so one blocked workflow stops the whole batch with `409`. Callers that are part of the same batch do not count: selecting a workflow together with the workflows that call it deletes them all.
- A connection cannot be deleted while workflows (including ones in projects you cannot see), an MCP service's pinned connection or an environment connection replacement still uses it. The delete returns `409` with the number of each. This applies to the project route and to the tenant-wide global connections route. **Replace connection** with "delete the old connection" still works, because it swaps references first.
- Deleting a connection used to leave its workflows to fail at run time.

**When is action necessary?**

Only for scripts that delete workflows or connections in bulk. Remove the references first, or replace the connection in its workflows before deleting it.

#### Run logs carry a business key (migration)

Migration `AddExecutionBusinessKey1790851200000` adds a nullable `businessKey` column to the `execution` table and an index on `("projectId", "businessKey")`.

- The index is created with `CREATE INDEX CONCURRENTLY`, so the migration runs outside a transaction and does not block runs from being written. On a large `execution` table it can take a while, and the instance keeps starting up until it finishes. Adding the column itself is instant.
- Runs started before the upgrade have no business key. It is not back-filled.
- A run's business key is the value of its trigger's dedupe key, read from the trigger payload (for example `{{trigger.recordInfo.jobNumber}}`), cut to 255 characters. Triggers without a dedupe key, manual runs and test runs have none. Reruns keep the key of the original run.
- Run logs gain a **Business key** (业务标识) column and filter, and each run links to **All logs of this record** (这条记录的全部日志). The filter matches a part of the value (`ILIKE '%…%'`) and the **Log content** search also matches it. API: the `businessKey` query parameter of the run log list.

Migration `AddExecutionIndexesConcurrently1790950000000` builds four more indexes on `execution` the same way (outside a transaction, `CONCURRENTLY`), so writes are not blocked either.

**When is action necessary?**

Plan the upgrade window for a very large `execution` table; nothing else is needed. If the migration is interrupted, see [Operations Reference](/install/configure-operate/operations-reference#upgrades-and-migrations) before starting it again.

#### Workflow export files carry mapping tables

The workflow export file has an optional `mappingTables` list holding every mapping table the workflow looks up, **including their rows**. Older files without it still import.

- **Import** and **copy to another project** reuse a mapping table of the target project when its name, key column name and value column name are all the same, and create it otherwise (a taken name gets `(2)`, `(3)`, …). Existing tables are never overwritten. The lookup steps in the imported workflow are repointed to the target project's table. Copying inside the same project changes nothing.
- **Save as template** removes the table id from lookup steps and keeps the transform, because a template is shared and cannot point into one project. Whoever creates a workflow from the template picks a table in the mapping editor.
- Before this change, an exported or copied workflow kept pointing at the source project's table.

**When is action necessary?**

No. Treat export files as holding mapping data if the tables contain anything sensitive, and check the tables an import created or reused before enabling the workflow.

#### Solutions: new tables, and one official solution in the library (migration)

Migrations `AddSolutions1790921911539` and `AddSolutionInstallWorkflowKeys1790930000000` add the tables `solution`, `solution_version` and `solution_install`, and a nullable `workflowKeys` column on `solution_install`. The official solution **Beisen → Feishu people sync** (北森 → 飞书 人员同步, version 1.0) is built into the application and appears in every tenant's solution library. See [Solutions](/workflows/solutions).

**When is action necessary?**

No. Nothing is installed until a person runs the install wizard, and the library entry cannot be hidden. The tables are created empty by the migration.

#### Beisen 0.3 and Feishu 0.4 connectors

The Beisen and Feishu connectors first appeared after 0.88.3, so only instances that already built workflows with them on a main-branch build are affected. The image carries one version of each connector, and a workflow pinned to an older version of the same major runs on the bundled one as soon as the image is upgraded.

**Beisen 0.3**

- Employee Changed (员工信息变动) and Search Changed Employees (查询变动员工) now call Beisen's official `/TenantBaseExternal/api/v5/Employee/GetByTimeWindow`. The old `/TenantBasePublicApiV2/v2/employee/timewindow/search` path is not used any more.
- **The output changed shape.** Records used to be flat (`UserID`, `Name`, `EmployeeNumber`); they are now nested as `employeeInfo` (name, mobile, email, `userID`) and `recordInfo` (job number, department OId, employee status, change type, last work date). Steps that read the old fields must read the new ones, for example `{{trigger['output']['employeeInfo']['name']}}`.
- The trigger has two new required settings. **Employee Status** (员工状态) chooses who to watch: active employees (default), departed employees, upcoming and active, or every status. Departed employees are only returned when you choose **Departed** or **Every status**, and a leaving counts only once it is in effect, after the last work day. **What Counts As A Change** (什么算变动) chooses business changes only (default) or any modification; the second also fires for the nightly job that recalculates tenure, so unchanged employees show up every day.
- The **Columns** setting is gone from the trigger. **Only When This Column** is now **Only When This Field** (仅当这个字段) and takes a path into the nested record, for example `recordInfo.changeTypeOID`.
- Windows longer than 90 days are fetched in 89-day segments, times use the `T` separator, and a poll that cannot read all pages fails instead of dropping rows.
- On the Search Changed Employees action, **Batch Size** and **Include Deleted** are gone and the page size is 300.

**Feishu 0.4**

- New actions: **Update Employee** (调整员工信息, department, manager, job title, name), **Suspend Employee Account** (暂停员工账号) and **Resume Employee Account** (恢复员工账号), both through the account's `is_frozen` field, and **Get Employee** (读取员工), which only reads.
- There is no delete or offboard action, and none is planned for the first release: a suspended account keeps its data and can be resumed. The solution has no delete option either.
- Feishu limits changing a department and suspending an account to one call per second, and rejects overlapping calls with error 44025. Let the step's retry run it again instead of firing such steps in parallel.

**When is action necessary?**

Yes, for existing Beisen workflows. Open each workflow with an Employee Changed trigger or a Search Changed Employees step, choose **Employee Status** and **What Counts As A Change** (a workflow that must also catch leavers needs **Departed** or **Every status**), update every reference to the old flat fields and the old filter column, test the trigger, and publish again. New Feishu actions need nothing on existing workflows.

#### Read-back verification runs every day

A scheduled job, `verify-recent-results`, reads Feishu back for production runs that succeeded in the last 72 hours and opens an issue in the Issue Center where Feishu does not hold what the run wrote. It runs every day at **03:37 UTC** (11:37 in China), and a person with the issue-management permission can run it on demand with **Check recent results** (核对最近的结果) on a project's Issues page (`POST /v1/verification/run`).

- It only reads. For each account written by a Feishu step (**Provision Employee Account**, **Update Employee**, **Suspend Employee Account**, **Resume Employee Account**) it calls **Get Employee** once, using the connection that step used, and compares the department or the suspended state. Each account is checked against its most recent write only. At most 200 runs per project are checked per pass.
- Only runs that have a business key are checked, so the trigger needs a dedupe key.
- A mismatch becomes one **Result mismatch** (结果对不上) issue per workflow step with severity High, and closes by itself when a later check agrees. A read that fails (permission, network) is counted as "could not be read" and opens no issue.
- There is no setting to switch it off. Instances without Feishu steps do nothing.

**When is action necessary?**

If you use the Feishu steps above, the job now reads your Feishu contacts on your behalf. The Feishu app already needs `contact:contact` and a contact scope that covers the target departments to provision accounts, and reading a member needs the same contact scope. Feishu does not count contact calls against the monthly call allowance of its free edition, but they still count against rate limits. When a check reports "could not be read" with a permission error, add the permission the error names to the app, create a new app version, and have a Feishu administrator approve it. See [Reliability](/workflows/reliability#read-back-verification) and the [Beisen to Feishu guide](/workflows/guides/beisen-to-feishu-people-sync).

#### Two migrations are flagged as breaking for rollback

Migration `DesignDocRolloutSchema1790501279466` (release 0.89.0) creates many tables at once, and `KeepAlertRecordsAfterPolicyDeletion1790940000000` changes how alert history is kept. Both carry `breaking = true`, so `npm run rollback -- --to 0.88.3` asks for `--force`. `DesignDocRolloutSchema` also changes existing data:

- `DELETE FROM "connector_blueprint"`: every connector created in the no-code connector builder before this release is removed, because the table changed shape.
- Every existing connection gets `projectMembersPermission = 'EDIT'` (**Can Edit**), so members keep the access they had before connection sharing existed. New connections start with no member access.
- Existing non-admin users are given the MCP services module. Connector development and platform administration are not granted to anyone but tenant admins.
- The unique constraint on `store-entry` and the unique index on folder names are replaced by partial indexes.

**When is action necessary?**

Take a database backup before upgrading, see [Rollback](/install/configure-operate/rollback) and the migration list in the [Operations Reference](/install/configure-operate/operations-reference#upgrades-and-migrations). If you built connectors in the no-code connector builder, write down their definitions first, because they are not carried over.

## 0.86.0

### What has changed?

#### Log fields are now grouped by entity
Log fields are now grouped under the entity they belong to, so each thing has one name. A workflow run id is `execution.id` (it used to appear as `runId`, `executionId`, or a bare `id`), and other ids follow the same shape (`workflow.id`, `project.id`, `job.id`, …). Errors are logged under `error`. This only changes how logs look — nothing about the API, database, or workflows changes.

#### Google SSO is configured via environment variables only
"Sign in with Google" can no longer be enabled from the SSO page in the admin panel — that setting has been removed. It is now controlled solely by the `FEMA_GOOGLE_CLIENT_ID` and `FEMA_GOOGLE_CLIENT_SECRET` environment variables. The button only appears when both are set (and the platform's Google auth toggle is enabled).

#### Connectors are now self-contained bundles
Each connector is now built into a single self-contained bundle — its own code, the FEMA Integration Platform framework, and its third-party dependencies are inlined into one artifact, so the engine provisions a connector by downloading one file instead of installing a dependency tree at runtime. As part of this, the shared libraries (`@fema-ipaas/shared`, `@fema-ipaas/connectors-framework`, `@fema-ipaas/connectors-common`, `@fema-ipaas/core-*`) are no longer published to npm, and connectors import only from `@fema-ipaas/connectors-framework` (which re-exports the foundation symbols that used to come from `@fema-ipaas/shared`). Built-in connectors are unaffected — this only matters for custom connectors.

#### `FEMA_PRE_WARM_CACHE` removed
The `FEMA_PRE_WARM_CACHE` environment variable no longer exists. It used to make a worker install connectors into its cache on startup. The worker is now its own sandbox and fills its cache lazily on first use, so the flag has no effect and setting it does nothing. Cache warmth now comes from running long-lived worker replicas rather than an up-front install step.

The up-front install is no longer needed because connector installs are now fast: each connector is a self-contained bundle fetched as a single file. If you have S3 enabled, official connector bundles are cached to your S3 bucket on first use and served from there via signed links — so when your bucket is co-located in the same region as your workers, subsequent installs are a low-latency download from a nearby object store instead of a registry round-trip.

### Do you need to take action?
- Only if you set up Google SSO from the admin panel. Move your Google OAuth2 credentials into the `FEMA_GOOGLE_CLIENT_ID` and `FEMA_GOOGLE_CLIENT_SECRET` environment variables.
- Only if you build dashboards or alerts on FEMA Integration Platform logs. Update them to the new grouped names, e.g. `runId` → `execution.id` and `err` → `error`.
- Only if you maintain **custom connectors** (in a fork or built outside the repo). Migrate each one to the bundle model — run `npm run cli -- connectors migrate <connector-name>` (or `--all`), or follow the [migration guide](/build-connectors/misc/migrate-connectors-to-bundles). Connectors that still import `@fema-ipaas/shared` or depend on the now-unpublished libraries will fail to build.
- Only if your deployment sets `FEMA_PRE_WARM_CACHE`. Remove it from your environment — it is no longer read. Nothing else is required.

- If you are dealing with large files in the actions, consider increasing the `FEMA_MAX_FILE_SIZE_MB` to a higher value, and make sure the storage system (database/S3) has enough capacity for the files.


## 0.30.0

### What has changed?

- `FEMA_SANDBOX_RUN_TIME_SECONDS` is now deprecated and replaced with `FEMA_WORKFLOW_TIMEOUT_SECONDS`
- `FEMA_CODE_SANDBOX_TYPE` is now deprecated and replaced with new mode in `FEMA_EXECUTION_MODE`

### When is action necessary?

- If you are using `FEMA_CODE_SANDBOX_TYPE` to `V8_ISOLATE`, you should switch to `FEMA_EXECUTION_MODE` to `SANDBOX_CODE_ONLY`
- If you are using `FEMA_SANDBOX_RUN_TIME_SECONDS` to set the sandbox run time limit, you should switch to `FEMA_WORKFLOW_TIMEOUT_SECONDS`

## 0.28.0

### What has changed?

- **Project Members:**
    - The `EXTERNAL_CUSTOMER` role has been deprecated and replaced with the `OPERATOR` role. Please check the permissions page for more details.
    - All pending invitations will be removed.
    - The User Invitation entity has been introduced to send invitations. You can still use the Project Member API to add roles for the user, but it requires the user to exist. If you want to send an email, use the User Invitation, and later a record in the project member will be created after the user accepts and registers an account.
- **Authentication:**
    - The `SIGN_UP_ENABLED` environment variable, which allowed multiple users to sign up for different platforms/projects, has been removed. It has been replaced with inviting users to the same platform/project. All old users should continue to work normally.

### When is action necessary?

- **Project Members:**

If you use the embedding SDK or the create project member API with the `EXTERNAL_CUSTOMER` role, you should start using the `OPERATOR` role instead.

- **Authentication:**

Multiple platforms/projects are no longer supported. Technically, everything is still there, but you have to hack using the API as the authentication system has now changed. If you have already created the users/platforms, they should continue to work, and no action is required.
