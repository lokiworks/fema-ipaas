## 一页结论

1. **预演（L）可行，引擎里有两个现成的先例。** 单步测试时 `connectorExecutor` 已经会改调动作的 `test` 方法（方法路径 `['actions', 名, 'test']`）；`actionRunMode` 是一个贯穿引擎常量、等待点、进度上报的模式开关。做法是连接器契约加一个可选的 `plan` 方法，引擎加 `planMode`，走一个不建运行记录的同步作业。难点不在引擎，在三件事：写操作的 `plan` 要逐个手写；默认 `UNSANDBOXED` 下代码步骤和表达式都能联网，预演时必须强制改走 V8 isolate；几百上千人的批量预演不能靠跑 N 次工作流，只能来自对账的差异，于是有两套逻辑可能不一致。
2. **批量闸门（M）推荐「待执行意图表 + 时间窗汇总」作为唯一机制，外加 24 小时滚动额度。** 对账、补到位、首次启用产生的批次，整批写进同一张表。申领放在引擎执行写操作之前：先调 `plan` 算出这次是不是「停用」。被拦下的运行以「已交给停用批次」正常结束；放行不是恢复原运行，而是对选中的人重新补到位。闸门不放在 `submitPayloads`，因为那里只知道「北森有变动」，不知道这次要不要停用。
3. **生效日排程（M）不复用延迟和暂停恢复。** 原因有三：`FEMA_PAUSED_WORKFLOW_TIMEOUT_DAYS` 默认 30 天，且不能超过日志保留天数；暂停的运行钉在旧版本、旧数据上；到点恢复靠 Redis 里的一次性任务。改为新建排程表，分钟级清扫，到期对这个业务键补到位，也就是读当前生效状态、用最新版本。
4. **依赖顺序（S 到 M）两样都要。** 「等待前置」保证正确，因为事件逐条到达，没法排序；排序只是批量下发时的优化。上级用两遍写：先建账号不带上级，上级到位后再补。台账显示「账号已到位，上级待补」。Entra 的 HR 开通文档也要求先处理上级记录。
5. **业务键与台账（L）：运行记录不加列，加一张旁表。** 这样避开在最大最热的 `execution` 表上建索引（仓库里没有 `CREATE INDEX CONCURRENTLY` 的迁移先例）。台账 1 万人 × 3 个应有结果、保留 6 个月，总量在百兆以内，量不是问题。问题是写入时机依赖两条异步链路：生产运行行经 Redis 暂存后才落库；运行结束的钩子看不到每一步做了什么。
6. **读回核对（M）分三层**：写后在同一个连接器进程里读回、按批核对、定期对账。按键逐个起 action run 去读不可行。现在每个步骤都会重新取访问令牌（令牌缓存在子进程里，进程一结束就没了），先改用 SDK 已有的 `CustomAuthRefresh`。按批读的话，1 万人每天全量核对约 200 次飞书调用、几十次北森调用（批量接口的单次上限需实测）。读回还顺带替代了首发的「结果未知」流程。
7. **地基顺序要改（第 7 节）。** 连接器的读能力和台账（含只读的「看现状」）提前到预演之前。闸门、排程、等待前置共用一套「表 + 清扫 + 补到位」机制，放在一起做。「启用时选起点」「检查点原子性」「幂等契约与重放分类」挪到切片之后，因为对账和补到位兜住了它们要防的事。
8. **首发切片总成本约 40 到 50 人周（XL）**，3 个人约 4 个月；其中本文六项约 18 到 22 人周。最大的三个技术风险（第 9 节）：
   - 预演的保真度，以及「预演时不写」的保证；
   - 「已到位」受读回能力和对方配额约束；
   - 台账和闸门的一致性建在异步链路和单一入口上，而现状有多条旁路。

## 1. 预演（计划模式）

### 方案

**按能力分三级，界面如实标出。** 不要求一次覆盖所有步骤：

| 级别 | 含义 | 谁提供 |
| --- | --- | --- |
| 差异级 | 读目标当前状态，算出动作（创建、更新、停用、无变化）和字段差异，给出预测输出 | 实现了 `plan` 的写操作。首发：飞书的确保账号、移动部门、暂停账号、发群消息 |
| 请求级 | 只算出将发送的请求（方法、地址、打码后的请求体），不读目标，不知道结果 | HTTP 请求步骤；蓝图（devkit）连接器的写操作（运行时解释清单，可以统一做） |
| 不可预演 | 在不写的前提下没法执行 | 没有 `plan` 的写操作和未分类的操作、需要网络的代码步骤、要等外部输入的步骤 |

**连接器契约怎么扩展**

- `createAction` 增加可选的 `plan(ctx)`。入参和 `run` 一样，是同一个 `ActionContext`。返回 `ActionPlan`：
  - `effect`：`NONE | CREATE | UPDATE | DEACTIVATE | DELETE | SEND | UNKNOWN`
  - `target`：类型、ID（已存在时）、显示名
  - `changes`：字段、改前、改后
  - `request`：将发送的请求（打码）
  - `predictedOutput`：和 `run` 返回同形状的预测输出
  - `unknownOutputPaths`：写入之后才知道的字段，例如新账号的 `open_id`
  - `blockers`：能预判的失败，例如「部门不在通讯录权限范围」，带错误码，用来和已开着的问题对上
- `plan` 只能调读接口，可以复用 `run` 里「先查」的那段逻辑。飞书 `feishuContacts.provisionUser` 本来就是「`batch_get_id` 查人 → 有就返回、没有才建」，`plan` 只是把最后一步换成「返回计划」，改动很小。
- `plan` 不像 `test` 那样缺省成 `run`，没有实现就是没有。
- 元数据加 `planSupport`（布尔），由 `createAction` 按有没有 `plan` 自动填写，随 `connector_metadata.actions` 入库。搭建器靠它静态算出哪一步是边界；运行时以 `hasPath(['actions', 名, 'plan'])` 为准。
- 写操作同时返回统一的「写入结果」形状（`effect`、`targetId`、`changed`），和 `plan` 的预测同构。补到位、台账、「状态真的变了才通知」都用它（第 5、6 节）。
- 安全网（可选）：预演期间，`httpClient` 把发出的每个请求的方法和路径记进预演报告。不能按 HTTP 方法拦截，因为飞书 `batch_get_id`、北森时间窗查询都是用 POST 来读的。

**引擎按节点类型怎么处理**（`planMode` 打开时）

| 节点 | 行为 |
| --- | --- |
| 连接器 · 读（READ、SEARCH） | 照常执行，输出是真实数据 |
| 连接器 · 写，有 `plan` | 调 `plan`；步骤输出 = `predictedOutput`；报告记下 `effect`、差异和 `blockers` |
| 连接器 · 写或未分类，没有 `plan` | 不执行，输出记为「未知」，成为边界 |
| HTTP 请求 | 实现 `plan`：GET、HEAD、OPTIONS（RFC 9110 的安全方法）照常执行，其他方法只返回将发送的请求，输出未知。允许在步骤上标「这是只读查询，预演时照常执行」，给用 POST 的查询接口用 |
| 代码 | 强制走 V8 isolate（没有 `require`，没有网络）。纯计算照常出结果；需要模块或网络的直接失败，记为边界「代码需要网络或模块，预演时不执行」 |
| 表达式 | 同样强制在 isolate 里求值 |
| 数据组件（映射、过滤、转换）、映射表查找 | 照常执行。前者是进程内的纯函数，后者经 API 只读 |
| 延迟、等到某时 | 不建等待点，记「将等待到 10-15 09:00」，然后继续 |
| 等待审批、Webhook 等待点、调用工作流（等回调） | 边界 |
| 分支、循环、并行 | 照常执行；分支条件用到「未知」值时判不出，这个分支记为边界 |
| 停止、HTTP 响应 | 只记录，不发送 |

**预测值和「未知」怎么往下传**

- **步骤级**：`createPropsResolver` 取上游输出一律经过 `getStepView`。预演时包一层，记下每一步的入参实际读了哪些上游步骤：读到了「预测」步骤，标「依据预测值」；读到了「未知」步骤，标「依赖不可预演的结果」。
- **字段级**：`unknownOutputPaths` 列出的字段，在预测输出里填一个固定的占位值，例如 `⟦写入后确定⟧`。
  - 下游写操作的入参里含占位值时，照样出计划，只是把这个字段显示成「写入后确定」，例如「将给新账号发私聊，账号 ID 写入后确定」。
  - 分支条件里含占位值时，判不出。
- 于是「依赖写入结果的分支」分两种：
  - 依赖确定的预测字段（`effect != NONE`、`created`）的，照常判断。模板里「状态真的变了才通知 HR 群」就属于这一种（000042）。
  - 依赖写入后才知道的值（新建记录的 ID）的，判不出，成为边界。

**「此步之后无法预演」的边界**

- 一个步骤 S 是边界，当且仅当满足下面任一条：写操作没有 `plan`；代码在 isolate 里失败；要等外部输入；分支条件依赖未知值。
- S 之后「无法预演」的范围是两部分：入参直接或间接依赖 S 输出的步骤；S 是分支时，它下面的所有步骤。
- 不依赖 S 的步骤照常预演。所以边界是一个依赖集合，不是画布上的一条横线。

**怎么呈现**

- **静态（搭建时）**：校验规则里加一类「预演覆盖」提示，每个节点标「可预演 / 依据预测值 / 不可预演（原因）」，画布顶部给「预演可覆盖 6 / 8 步」。只用元数据（`classification`、`planSupport`）和节点类型就能算，不调接口。
- **动态（每次预演）**：报告逐步列出「已读取 / 将执行（未发送）/ 依据预测值 / 未预演（原因）」，结尾一句「预演到『调用 ERP』为止，其后 2 步依赖它的返回」。

**执行通道**：新增一种同步的计划作业，照 action run 的做法：
- 进用户交互队列，`submitAndWaitForResponse` 等结果，端到端 120 秒期限；
- 不建运行记录，所以不进问题中心、告警、月度配额、运行监控；
- API 把报告存进一张短期表（建议保留 7 天），补到位的预演卡和审计都引用它。

输入有三种：一个业务键（收敛工作流从触发输出里只读业务键，见本节「对设计的含义」）、某次真实运行的触发输出、手写。多个键的预演（例如补到位 5 个人）并发跑几个计划作业，一次最多 50 个键。

**批量预演不跑工作流。** 启用前「将创建 31、更新 58、停用 3」这类数字，来自对账：读两边名单，按声明里的匹配规则和关键字段比较。不是把工作流跑 1,229 次。代价是两套逻辑：声明算出来的差异，和处理工作流实际会做的事。缓解办法：
- 处理工作流的确保步骤直接引用声明里的匹配规则和映射，不另抄一份；
- 每次批量预演，随机抽 20 个键跑真实的计划作业，和对账的预测逐个对比，不一致就在预演卡上报出来。

  - `packages/server/engine/src/lib/operations/`：`workflowOperation` 加计划分支；

- **作业与契约**：`packages/core/execution/src/lib/engine/`（`EngineOperationType` 加计划操作）；`packages/core/execution/src/lib/workers/`（新作业类型进 `UserInteractionJobData`，按约定升 `LATEST_JOB_DATA_SCHEMA_VERSION`）；`packages/server/worker/src/lib/execute/jobs/`（新处理器，照 `execute-action.ts`）。
- **API**：新建 `packages/server/api/src/app/plan/`（计划服务、报告表、接口），派发方式照 `actionRunService`。
- **连接器**：飞书 `packages/connectors/community/feishu/`（4 个写操作的 `plan`）；HTTP `packages/connectors/core/http/`（`send-http-request-action` 的 `plan`）。
- **前端**：`packages/web/src/app/builder/validation/`（`ValidationCode` 加预演覆盖类规则）；`packages/web/src/app/builder/test-step/`（写操作的「测试此步骤」默认改为预演，真写要二次确认）。

### 对现有引擎执行模型的影响

- 不动持久化模型（`nextAction` 树加 `graph` 汇合边）、`workflowCompiler`、`executionPlanCursor`。多出来的是一个贯穿各执行器的模式开关，和 `actionRunMode` 同一个量级。
- 预演运行不建等待点、不发进度、不上传日志，所以不会出现「暂停中的预演运行」，也不会进问题中心。
- 重试照旧：预演里只有读调用，重试是安全的。
- 照 action run 做成用户交互作业的话，它默认不在 `PROJECT_GROUP_ROUTABLE_JOB_TYPES` 里，不会按项目路由到专属工作节点（action run 现在就是这样）。北森、飞书是公网 SaaS，不受影响；以后接内网系统（泛微、致远）时，要把计划作业加进可路由的类型，否则预演可能落到够不着内网的共享节点上。
- 引擎构建不做类型检查（brain：Nothing typechecks the engine）。这一项改动面广，要单独跑 tsc 并逐文件对比。

### 风险

- **保真度**：`plan` 是手写的第二份逻辑，可能和 `run` 不一致。不少失败只有写的时候才知道：40004（权限范围）、41001（手机号已被占用）、44021（直属上级已离职）。预演只能预判一部分，权限范围可以先读接口预检。界面要写明「预演不保证执行成功」，并列出预检过的项。
- **「不写」靠连接器作者自觉**，平台没法按 HTTP 方法拦截。第三方连接器的 `plan` 要进评审；连接器 CLI 的 `validate` 只能查有没有，查不了对不对。
- **强制 isolate 之后**，依赖 npm 包或网络的代码步骤在预演里一律是边界；isolated-vm 在鲲鹏加麒麟环境里能不能正常加载，需实测。
- **批量预演和单键预演是两套逻辑**，见上文。

### 成本：L（约 5 到 6 人周）

SDK 与元数据 S；引擎计划模式与依赖传播 M；计划作业与报告 S；飞书 4 个写操作和 HTTP 的 `plan` S 到 M；搭建器的静态标注和预演面板 M。如果只做首发模板、不做搭建器的静态分析，可以压到 M+（约 3 到 4 人周）。

### 对设计的含义

- 预演在界面上分级说话。「将创建 张三（深圳研发中心 / 平台组）」是差异级；「将发送 POST /api/vouchers，结果未知」是请求级；第三级写「这一步不能预演：……」。不要把请求级包装成差异级。
- 收敛工作流只从触发输出里读业务键，其余一律重新读源。搭建器加一条校验：引用了触发输出里业务键以外的字段时，提示「补到位和预演时这些字段不存在」。有了这条约束，预演、补到位、排程到期、闸门放行都走同一个入口：给一个业务键。台账行要同时存源记录 ID（例如北森 UserID），补到位时一并放进触发输出。
- 写操作的「测试此步骤」默认就是预演；真写放进二级菜单，并写明用哪个连接、哪个环境。
- 启用前的数量预演来自对账，单人预演来自工作流；两者不一致时要报出来，不能静默取其一。
- 首发只给模板里的飞书写操作做到差异级；HTTP、代码之后的步骤如实显示为边界。

## 2. 批量闸门

### 两种方案

| | A. 待执行意图表 + 时间窗汇总 | B. 对账驱动的批次 |
| --- | --- | --- |
| 怎么做 | 写之前算出效果；是「停用」就登记一条意图，进当前时间窗。时间窗结束时汇总：没超阈值就自动放行，超了就整批停下等人 | 事件驱动的运行不直接停用，只把台账行标成「应停用」；由对账或定期的停用批次任务汇总全部「应停用」，整批判断 |
| 好处 | 事件流也能拦；批次边界清楚 | 整批名单一开始就完整；实现集中在 API |
| 坏处 | 每个停用都要等一个时间窗；固定时间窗会被「每窗 4 人」的细水长流绕过（Entra 也是按周期计数，见来源） | 停用的时效取决于批次频率，「离职当天停用」实际变成「下一批停用」；对账没做好之前什么都拦不了 |
| 和现有代码 | 要在引擎写之前加申领，API 加意图表和清扫任务 | 只动 API |

### 推荐：A 作为唯一的机制，B 的批次作为它的一个来源

**机制**：意图表 + 时间窗（默认 10 分钟，约两个轮询周期）+ 24 小时滚动额度。
- 时间窗挡突发：HR 一次导入 300 条离职，分两三个轮询周期进来，一个都不会先放过去。
- 滚动额度挡细水长流：每个时间窗都没超，但一天累计超了。

**来源**：
1. 事件驱动的单条：引擎在写之前申领。
2. 对账、补到位、首次启用、问题修好后的批量补齐：一次性登记一整批，不进时间窗，直接按批判断，不会出现「先放过去 5 个」。

**在哪里申领**：引擎里，执行写操作之前。
- 有 `plan` 的写操作，先调 `plan` 得到 `effect`，是 `DEACTIVATE` 或 `DELETE` 才申领。这样「确保状态 = 暂停」在对方已经暂停时（`effect = NONE`）不占额度。
- 没有 `plan` 但分类是 `DESTRUCTIVE` 的，按停用保守申领。

**申领的结果**：
- 放行：带有效的放行凭证，或者属于已放行的批次。
- 拦下：登记意图。步骤输出记「已交给停用批次 B-12」，运行以成功结束（复用引擎已有的「停止」语义），并打一个标签（运行行已有 `tags` 列），方便在运行列表里和真成功区分开。台账行变成「待放行」。

**时间窗结束时**（分钟级系统任务）：统计窗内的意图（按业务键去重），加上 24 小时内已自动放行的数量。
- 都在阈值内：给每条发放行凭证，对这些键补到位。
- 超了：批次转为「待放行」，开一个闸门类问题，告警一次。

**人来放行**（整批或逐条）：发凭证，对选中的键补到位。
- 放行不恢复原运行，而是新开一次收敛，重新读源。被拦期间 HR 改了数据（比如撤销离职）的人，新运行算出来已经不用停用，意图变成「已失效」。
- 拒绝的意图转成台账的「例外（人工保持）」，带到期日。

**为什么不用智能体确认那套「暂停 → 恢复」**：恢复只会重跑暂停的那一步，入参是暂停前就算好的。闸门可能一等几个小时，到时候停用一个已经撤销离职的人，正是闸门要防的事。

### 和现有触发器的衔接

- **`submitPayloads` 和去重**：都不动。闸门不放在入口，因为入口只知道「北森有变动」。去重继续按业务键降噪。补到位（包括闸门放行、排程到期、等待前置唤醒）一律经 `triggerRunPolicy.startRuns` 进来，但要跳过可配置去重；否则去重窗口内的放行会被当成重复丢掉。
- **并发拦截器**：放行 300 人就是 300 次补到位，每次带并发票据（保序键 = 业务键），由 `workflowConcurrencyInterceptor` 按工作流的并发上限排队，顺带限住对飞书的写入速率。现在重跑和手动运行直接调 `executionService.start`，不带票据；补到位入口必须走 `startRuns`，不能照抄重跑。
- **补到位的入口用伪造的触发输出建运行**（`executeTrigger: false`），触发步骤的状态记为成功。这和 brain 里「伪造触发步骤要选对状态」的提醒一致：载荷来自 `submitPayloads` 一侧的，记成功；记成失败，重试时会去重新轮询。

### 改动位置

- **引擎**：`packages/server/engine/src/lib/handler/`（`connectorExecutor`：写之前 `plan` → 申领 → 放行或停止）。
- **API**：
  - 新建 `packages/server/api/src/app/outcome/gate/`：意图表、批次表、申领接口（`/v1/worker/` 前缀，和 `agentApprovalWorkerController` 同一类）、放行和拒绝接口；
  - `packages/server/api/src/app/helper/system-jobs/`：`SystemJobName` 加时间窗清扫；
  - `packages/server/api/src/app/trigger/`：`triggerRunPolicy.startRuns` 支持「补到位来源，跳过去重」；
  - `packages/server/api/src/app/issue/`、`packages/core/shared/src/lib/automation/issue/`：`IssueKind` 加闸门类。
- **多实例**：申领按（应有结果，效果类别）加 `distributedLock`；清扫用 `FOR UPDATE SKIP LOCKED` 领取到期的时间窗。
- 新表进 `getEntities()` 并写迁移；纯加表，不用标 `breaking`。

### 风险

- **旁路**：闸门只覆盖经过引擎写操作的路径。
  - 「从失败节点重放」用旧版本和旧的上游输出接着写。因为申领在引擎里，那一步如果是停用，会再申领一次，闸门照样拦得住；这正是申领不能放在入口的原因之一（重放、手动、同步 Webhook 都不经过 `startRuns`）。
  - MCP 的 action run 直接调连接器操作，不经工作流：要么在 action run 里同样申领，要么对 `DESTRUCTIVE` 操作只走智能体确认。
  - 第三方连接器没填分类、没实现 `plan` 时，闸门看不见它的停用。
- **阈值口径**：备忘写的是「超过 5 人或在职人数的 3%」。1 万人的企业，按年流失 15% 算，每个工作日约 6 人离职（推算）：取两者里小的，几乎天天触发；取大的，要 300 人才触发。两样都不对。建议默认值由「看现状」时读到的近 90 天离职分布算出，例如日离职量 p95 的 3 倍，下限 5 人。需访谈确认。
- **停用延迟**：每个停用最多多等一个时间窗（默认 10 分钟）。备忘说分钟级可以接受，首发要和客户确认。
- 被拦下的运行以「成功」结束，运行列表、成功率统计要能把它和真成功分开（靠标签或台账状态）。

### 成本：M（约 3 人周）

### 对设计的含义

- 闸门在界面上是一个对象：「待放行批次」。它有名单、来源（事件、对账、补到位）、额度占用，可以整批放行、逐条放行、拒绝（转为例外并设到期日）。
- 首页文案写「今天已自动停用 4 人（额度 6）；另有 37 人等待放行」，不要只写「已暂停」。
- 放行等于对这些人补到位，放行卡和补到位的预演卡是同一张：读当前状态、将停用 35 人、2 人已不需要停用。
- 阈值平台管理员可调、不能关；默认值从客户自己的历史数据算，不写死。
- 放行必须登录并有权限（`design-inputs.md` 第 4 节第 3 条）。

## 3. 生效日排程

### 现有的延迟和暂停恢复为什么不够

| 问题 | 依据 |
| --- | --- |
| 最长 30 天 | `FEMA_PAUSED_WORKFLOW_TIMEOUT_DAYS` 默认 30，`Delay Until` 超出直接报 `PausedWorkflowTimeoutError`。系统校验要求它不超过日志保留天数，要放长就得一起放长日志保留，增加存储。提前一两个月确定的离职、提前录用的入职都会超 |
| 醒来用的是旧版本、旧数据 | 暂停的运行钉在暂停时的工作流版本上；恢复只从暂停那一步往下走，上游读到的数据是暂停前的 |
| 不耐 Redis 丢数据 | 到点恢复靠 BullMQ 一次性任务；Redis 丢了，要等应用下一次启动时 `refillPausedRuns` 从库里补回，运行期间没有巡检 |
| 撤销要先找到运行 | 撤销得按业务键找到那次暂停中的运行再取消，现在没有按键的索引 |
| 一人多条 | 调岗 10-10 生效、离职 10-31 生效，就是两次暂停中的运行，各自醒来 |

### 推荐：排程表 + 分钟级清扫 + 到期补到位

- **表（新建）**：一行 = 应有结果 × 业务键 × 到期时间 × 原因（生效日，或生命周期提前量，例如入职前 1 天开通）。状态为待执行、已触发、已撤销、已被取代，并记录触发的运行。（应有结果，业务键哈希，到期时间，原因）唯一，重复登记自然去重。
- **谁来登记**：收敛运行读源时，同时读「当前生效」和「最新」两条记录（北森 `option=2`、`option=1`）。最新记录的 `startDate` 或 `lastWorkDate` 在未来，就登记一条排程。登记方式有两种：
  1. 一个平台组件「排程到生效日」，在模板里放在读源之后。组件在引擎进程内运行，有 `server.apiUrl` 和引擎令牌，直接调 API。
  2. 引擎在运行结束时，随写入结果一起上报（第 5 节的 `effects`）。

  首发用第 1 种，最直接。
- **到期**：系统任务每分钟领取到期的行（`FOR UPDATE SKIP LOCKED`），对这些键补到位，用最新发布版本，重新读当前生效状态；状态改为「已触发」并记下运行 ID。时间用租户时区，往后错几分钟（例如 00:05），避开北森「当前生效」切换的时刻（切换时刻需实测）。
- **撤销**：
  - 源头撤销（HR 撤回离职）：北森会再产生一次变动，收敛运行重新读，最新记录里已经没有这条未来变动，就把原排程标为「已被取代」。
  - 操作员撤销：在界面上直接取消这一行，进审计。
  - 就算撤销没赶上，到期那次补到位读到的当前生效状态里也没有这次变动，什么都不会做。这是 000042 收敛语义的兜底。
- 台账行冗余一个「下一次排程」字段用来显示，真相在排程表。
- 现有的延迟组件保留，只用于工作流内部的短等待。

### 改动位置

- **API**：新建 `packages/server/api/src/app/outcome/schedule/`（排程表、登记接口、清扫任务）；`packages/server/api/src/app/helper/system-jobs/`（`SystemJobName` 加排程清扫）。
- **组件**：`packages/components/builtin/src/lib/runtime/`（新组件，结构照 `delayUntilComponent`）。
- **北森连接器**：`packages/connectors/community/beisen/`。新增「按 UserID 读当前生效和最新任职」，带 `option` 参数和日期字段；触发器补上带离职员工的参数（第一轮已查明默认不含离职）。
- **补到位入口**：同第 2 节（`triggerRunPolicy.startRuns`）。

### 风险

- 一个人同时有两条以上未来记录时，`option=1` 只给最新的一条，中间那条可能看不见，可能要用条件查询（`option=0`）列出全部未来记录（需实测）。
- 待入职人员在 `option=2` 下有没有记录、入职前的「当前生效」是什么，需实测。首发的「入职前 1 天开通」可能要改从待入职接口取（连接器已有「取待入职人员」）。
- 清扫任务挂在 BullMQ 可重复任务上。Redis 丢了任务定义，要靠应用启动时重新登记；排程数据在 Postgres 里不会丢，最坏是晚到下一次启动。

### 成本：M（约 2 人周）

如果只在台账行上加「下一次到期」两列、不建独立的表和撤销界面，可以压到 S，但没有审计，也处理不了一人多条。

### 对设计的含义

- 台账行多一个状态「排程中」：「10-31 生效的离职，届时停用」，点开能看到来源记录（北森的哪条任职记录）。
- 排程没有 30 天上限，界面可以列出未来 90 天内要发生的开通和停用，这本身就是一张对 HR 和 IT 有用的表。
- 「撤销」分清两种：源头撤销是自动的，界面上看到「已被取代」；人工撤销要写理由、进审计。
- 生效时刻的口径（生效日 00:05、最后工作日次日、按租户时区）是方案的设置项，不是硬编码。

## 4. 依赖顺序

### 两种方案

- **排序**：批量下发前做拓扑排序：部门先于人员，上级先于下属，按组织层级分批。只对一次就知道全集的批量有效，比如首次启用、对账补齐、闸门放行。北森事件是一人一次运行、陆续到达，没法排。
- **「等待前置」**：运行发现前置记录没到位时，不算失败；台账行进「等待前置」并记下前置是谁；前置到位时，平台自动对等它的记录补到位。对事件和批量都成立。

### 推荐：两样都要，「等待前置」管正确，排序管效率

- **部门**：首发没有部门同步，部门靠映射表。所以部门这个前置表现为两种问题：「映射缺失」，等数据所有者；「不在通讯录权限范围」，等飞书管理员。它们是问题中心的「等待对方」，不是记录之间的依赖。以后做部门同步，部门也成为台账里的业务记录，人员行等部门行，用同一套机制。
- **上级**：两遍写。
  - 第一遍建账号或改部门时，上级没到位就不带上级；台账行显示「账号已到位，上级待补」，前置 = 上级的业务键。
  - 上级那一行变成「已到位」时，台账写入的副作用查出等它的行，逐个补到位。
  - 好处：新员工不会因为上级还没开通就拿不到账号；互为上级的脏数据也不会死锁，两人的账号都能先建出来。
- **44021（直属上级已离职）**：不是等待，是数据问题，交给 HRIS；账号照建，上级留空。
- **批量下发时按组织层级排序**，减少两遍写的次数。Entra 的 HR 开通文档写明，上级记录要在作用域内、要先于下属处理，按需开通时也要先对上级执行一次（来源见文末）。我们用「等待前置」把这条要求从使用说明变成平台行为。

### 改动位置

- 台账行加两列：等待的前置类型、前置业务键哈希；加（应有结果，前置键哈希）的部分索引。唤醒逻辑放在台账写入的副作用里（新建 `packages/server/api/src/app/outcome/` 下的 `*-side-effects.ts`，按项目约定显式调用）。
- **模板**：确保账号拆成两步：「确保账号（不带上级）」和「确保上级」。第二步在上级还没有对应关系时报告「等待前置」，而不是失败。报告方式和排程组件同一类（组件经 API 写台账），或者用写入结果里的 `effect = WAITING_PREREQ`。
- **批量排序**：放在补到位的批量派发里（新建的派发服务），按前置关系分层，依次提交。

### 风险

- 前置链很长（新部门的一整串人）时，逐层唤醒会放大运行数。同一个前置的唤醒要合并，一次唤醒一批。
- 「等待前置」不进问题中心（它不是失败），但要有超时：前置一直不到位（比如上级从未入职）时，转成数据问题。

### 成本：S 到 M（约 1 到 2 人周），前提是台账和补到位入口已经有了。

### 对设计的含义

- 台账行要能表达「部分到位」：「账号已到位 · 上级待补（等 李航 开通）」，点进去就是上级那一行。
- 「等待前置」和「等待对方」是两个词：前者等另一条记录，平台会自己接着做；后者等人。
- 首发不画部门同步；画「缺部门映射 → 交给 HRIS」和「上级待补」两种，就够说明模型。

## 5. 业务键与台账

### 5.1 运行记录按业务键建索引

**推荐旁表，不给 `execution` 加列。** 新建 `execution_business_key`：运行 ID、项目 ID、应有结果 ID（可空）、键哈希、键预览、创建时间；索引（项目 ID，键哈希，创建时间）。理由：

- `execution` 是最大最热的表，仓库里没有 `CREATE INDEX CONCURRENTLY` 的迁移先例。在大的老实例上给它建索引会长时间锁住写入，而建一张新表是瞬时的。
- 一次运行对应多个键时（循环、批量型触发器），一个键一行，不用改约束。
- 按人删除只清这张旁表和台账，不碰运行表。

**键在哪里算**：
- 触发器运行设置加「业务键」（键路径），校验和推荐候选字段复用 `triggerRunSettingsUtils` 的 `validateKeyPath`、`readKey`、`keyCandidates`。
- 在 `triggerRunPolicy.startRuns` 里按载荷算出，经 `executionService.start` 传下去。
- 生产运行行是经 `runsMetadataQueue` 异步落库的，旁表的写入也挂在同一条落库路径上，运行行落库后再写。所以按键查运行会有秒级延迟。
- 同步 Webhook（`executeTrigger: true`）入口拿到的是原始请求，要等引擎回传触发输出才算得出键。首发主线用不到，先不支持。

**重跑**：「从失败节点」是同一行，键不变；「整体重跑」和补到位新建运行时把键带上。

**隐私**：学 `deduped_event`，存 SHA-256 哈希和打码预览；精确搜索时对输入算哈希再查。

### 5.2 台账的表结构（全部新建）

| 表 | 关键字段 | 索引与约束 |
| --- | --- | --- |
| 应有结果 `outcome` | 项目、名称、形态（保持一致、每条一份、每次变化一条、留存一份）、源连接和对象、业务键定义、范围规则、目标连接和对象、匹配规则（有序）、关键字段及比较方式、时限规则、处理工作流 ID、闸门策略、核对策略、状态（草稿、只读、启用、停用）、版本 | 项目内名称唯一；改动走变更通道、进审计 |
| 对应关系 `record_link` | 项目、源（连接 + 对象）、键哈希、目标（连接 + 对象）、目标 ID、状态（已链接、待确认、冲突、例外）、来源（存量对齐、确保操作的写入结果、人工确认） | （源，键哈希，目标）唯一；（目标，目标 ID） |
| 台账行 `outcome_record` | 应有结果、键哈希、键预览、源记录 ID、显示名（可空、可删）、状态、原因码、问题 ID、对应关系 ID、到期时间、最近一次源变动时间、最近处理时间和运行 ID、最近核对时间和依据（写后读回、对账、发送记录）、期望摘要哈希、实际摘要哈希、小摘要（打码后的关键字段对照）、等待的前置、例外到期、下一次排程 | （应有结果，键哈希）唯一；（项目，状态，到期时间）；（问题 ID）；（应有结果，前置键哈希）部分索引；（项目，键哈希），用来跨集成查一个键 |
| 经过 `outcome_record_event` | 应有结果、键哈希、时间、类型（源变动、运行成功、运行失败、核对通过、发现漂移、被拦、放行、排程、设为例外）、前后状态、运行 ID、问题 ID、操作人、小详情 | （应有结果，键哈希，时间）；按保留期清理 |

另有第 2、3 节的闸门表、排程表，第 1 节的预演报告表。

**台账行的状态**：已到位、已处理待核对、未到位、等待前置、待放行、排程中、结果未知、例外。「逾期」不存，查询时按「到期时间早于现在，且不是已到位」算，免得为它反复写行。

### 5.3 写入时机

| 时机 | 写什么 | 谁触发 |
| --- | --- | --- |
| 「看现状」和每次对账 | 批量建行或更新状态：已到位、未到位（原因）、无法匹配（进对应关系的待确认池）、目标有源无 | 对账任务（在 API 里比较；读两边用 action run） |
| 源变动到达 | 更新到期时间和期望摘要；期望变了就回到「未到位（待处理）」 | 运行带着业务键落库时 |
| 运行结束 | 成功：已处理待核对（写入结果显示已读回一致的，直接已到位）；失败：未到位 + 问题 ID；被拦：待放行；等待前置 | `executionHooks.onFinish` 之后的台账副作用 |
| 写后读回、按批核对 | 已到位，或未到位（漂移） | 引擎上报的写入结果；核对任务 |
| 排程、闸门、例外 | 排程中、待放行、例外 | 对应的 API 动作 |

**关键缺口**：`onFinish` 只拿得到运行行（状态、标签、失败步骤），拿不到「这次建了账号还是什么都没做」。建议给 `UploadRunLogsRequest` 加一个可选字段 `effects`：引擎从返回统一「写入结果」形状的步骤里抽出 `{ 步骤名, effect, targetId, verified }`，一起上报，经 `runsMetadataQueue` 落到台账。改动是加法（可选字段；应用和工作节点本来就要求版本完全一致）。不这样做，就只能逐个解压日志文件去读，那条路按人删除数据时已经在用，只适合后台任务。

**只写变化**：核对通过、状态也没变的行，不逐行更新，只在应有结果上记一次「全量核对完成时间」；行上的「最近核对时间」取两者里较晚的。否则 3 万行每天全量核对一次，就是每天 3 万次更新、半年 540 万次，平白制造表膨胀。

### 5.4 和问题中心的关系

- 每个「未到位」都有原因：
  - 运行失败造成的，挂到这次运行所属的问题上（`issueService.recordFailure` 之后取 `execution.issueId`）；
  - 对账发现、根本没有运行的（「没发生」），按（应有结果，差异类型）开一个新类型的问题或挂到已有问题上，不重复告警（000040）。
- 问题的影响 = 挂在它上面的台账行。「影响 12 人，其中 3 人今天入职」按行的到期时间算，不再数失败次数；问题按这些行里最早的到期时间排序。
- 自动关闭：挂着的行全部「已到位」时关闭问题，不再按运行判断。
- 「等待对方」修好之后的自动复检，就是对挂着的行批量补到位；其中的停用要过闸门。
- 改动位置：`packages/server/api/src/app/issue/`（`issueService.recordFailure`、`issueSideEffects`、`IssueEntity`）；`packages/core/shared/src/lib/automation/issue/`（`IssueKind`、`IssueStatus` 加「等待对方」）。

### 5.5 数据量估算（1 万人 × 3 个应有结果，保留 6 个月）

- 在职 1 万人；年流失 15%、调岗 10%：半年约 750 人离职、750 人入职、500 人调岗，生命周期变动约 2,000 次。

## 6. 读回核对

### 三层核对

1. **写后读回（同一次运行内）**：确保类写操作写完，在同一个连接器子进程里再读一次目标（令牌在进程内还有效），把 `verified` 和读到的关键字段放进写入结果。一致就直接「已到位（依据：写后读回）」。成本是每次写多 1 次读。
2. **按批核对（运行之后）**：对「已处理待核对」的行，以及读回不一致、超时、结果未知的行，定时按批读目标（一次 action run 读几十个键），更新状态。
3. **定期对账（全量）**：列出两边的全量名单，发现目标端被人改过（漂移）的，和根本没发生的。

第 1、2 层能替代「结果未知」的大部分：写超时之后读一次目标，到位了就是到位；没到位就补到位，确保类操作靠对方的幂等键（飞书创建用户的 `client_token`）兜住重复。这样首发可以不做引擎层面的「结果未知」状态，盘点里这一项是高成本。

### 通用做法

- 连接器为每类目标声明一个「按键读」操作，返回统一形状：是否存在、目标 ID、规范化后的关键字段（部门 ID 列表；状态：在职、暂停、离职；上级 ID）。飞书「获取单个用户信息」返回 `status`（含 `is_frozen`、`is_resigned` 等）、`department_ids`、`employee_no`、`leader_user_id`（文档）。
- 应有结果的声明里定义关键字段和比较方式（集合比较、忽略大小写、空值视为相等等），比较在 API 里做；期望值由源记录经同一份映射算出。
- 读不回的结果（群消息）不假装核对过：写「依据：发送记录」，靠飞书消息的 `uuid` 去重兜住重复（`critique-v3.md` P1-7，评审人补充、未复核）。
- 不要按键逐个起 action run：每次是一个用户交互作业、一次引擎启动、一个连接器子进程，1 万个键就是 1 万次，还会挤占搭建时的交互（同一个高优先级队列）。

### 限流成本

**先修令牌。** 现在飞书、北森每个步骤都在新子进程里重取令牌，一次收敛运行有 4 个飞书步骤，就多出 4 次取令牌的调用。改用 `CustomAuthRefresh.generate` 后，令牌由服务端缓存，读回的调用量才算得过来。北森取令牌的调用算不算进企业配额，未查到。

| 场景 | 飞书调用 | 北森调用 | 说明 |
| --- | --- | --- | --- |
| 一次收敛（读源 → 查人 → 确保 → 读回 → 通知） | 3 到 4 次（令牌修好后） | 1 到 2 次 | 读回多 1 次 |
| 补到位预演 5 个人 | 约 10 次 | 约 5 到 10 次 | 只读 |
| 1 万人每天全量核对 | 约 200 次（按已知的目标 ID 每批 50 个，批量上限需实测）；要发现「飞书有北森无」，还要按部门遍历列出全部 | 约 34 次（按 UserID 每次 300 个），外加列出全量名单 | 飞书单个接口 1,000 次/分钟、50 次/秒（创建用户见 `china.md`；批量读用户据检索摘要）；北森全企业 3,000 次/分钟 |
| 首次「看现状」1,229 人 | 约 25 到 30 次 | 约 5 到 15 次 | 不到北森每分钟配额的 1% |

结论：按批读，核对的调用量很小；危险的是逐键读和令牌重取。

平台还没有按对方租户限流（盘点里的高成本项）。首发用工作流的并发上限按配额倒推（推算）：北森给本平台留 30%，即 900 次/分钟（每秒 15 次）；每次收敛约 2 次北森调用，每个槽位每秒最多跑约 1 次运行，并发上限设到 7 以下就不会超。把「本次占对方配额多少」显示在预演卡和对账页上。

### 改动位置

- **连接器**：
  - 飞书 `packages/connectors/community/feishu/`：新增按工号或手机号读用户、批量读、列出全部；确保类操作返回写入结果并读回；`feishuAuth` 改用 `refresh.generate`；
  - 北森 `packages/connectors/community/beisen/`：按 UserID 读当前生效、列出全量；`beisenAuth` 同样改。
- **API**：新建 `packages/server/api/src/app/outcome/verify/`（核对任务，用 `actionRunService.runConnectorAction` 按批调「按键读」）；`packages/server/api/src/app/helper/system-jobs/`（核对和对账的定时任务）。
- **引擎**：上报 `effects`（第 5 节）。

### 风险

- 写完马上读，飞书能不能立刻读到（读写一致性），需实测。读不到时不能判「未到位」，要推迟到第 2 层再判。
- 北森有没有能列出全量在职（含待入职、离职）员工的接口，未查到。时间窗查询有 90 天上限，不能拿来列全量。
- 大名单走 action run 的返回通道（120 秒期限，结果经 Redis 回传），1 万条可能超时或过大。北森滚动游标两次调用的间隔不能超过 10 秒，所以也不能拆成多次 action run 去翻页（需实测）。可能要让列全量的操作把结果写成文件，只返回文件引用。
- 飞书批量读用户接口单次能读多少个、频率是多少，官方页面因证书问题没能直接取到原文，需实测。

### 成本：M（约 2 到 3 人周），不含对账本身。

### 对设计的含义

- 台账的每一行写明依据：写后读回、对账、发送记录。没有依据的，不叫「已到位」。
- 对账页和预演卡显示「本次约占北森每分钟配额 x%」，方案设置里给一个选项：「给本平台留多少配额」。
- 「结果未知」在首发里基本不出现：超时后平台自己去读，界面显示「正在核对」，而不是让值班去对方系统里翻。
- 核对频率是应有结果的设置（默认写后立即读回、每天全量一次），不是全局常量。

## 9. 最大的三个技术风险

1. **预演的保真度，和「预演时不写」的保证。**
   - 来源：`plan` 是每个写操作手写的第二份逻辑；不少失败只在写的时候才出现；默认 `UNSANDBOXED` 下代码步骤和表达式都能联网，预演必须强制走 isolate（鲲鹏、麒麟上的可用性需实测）；批量预演来自对账、单人预演来自工作流，两套逻辑会分叉。
   - 后果：只要发生一次「预演说不会写，实际写了」，或者「预演说将停用 3 人，实际停了 30 人」，整个方向的信任就没了。
   - 缓解：分级如实呈现；`plan` 进连接器评审；预演期间记录所有外发请求；批量预演抽样交叉核对；闸门作为最后一道防线。
2. **「已到位」受读回能力和对方配额约束。**
   - 来源：每个应有结果都要能按键读、能列全量。北森列全量的接口未查到，滚动游标 10 秒就过期；飞书批量读的上限没取到原文；北森配额按企业共享（每分钟 3,000 次），平台没有按对方租户限流；令牌每步重取会让调用量翻倍；写后读的一致性未知。
   - 后果：台账要么不敢说「已到位」，要么把客户的接口配额耗光，连带客户别的应用一起被限流。
   - 缓解：先修令牌缓存；一律按批读；并发上限按配额倒推，并把占用显示出来；读不回的结果如实标「依据：发送记录」。
3. **台账和闸门的一致性，建在异步链路和单一入口上，而现状两样都不满足。**
   - 来源：生产运行行经 Redis 暂存后才落库，结束钩子看不到每步结果；Redis 不持久时，排队中的运行会丢，延迟恢复任务要等应用下次启动才补回。写目标系统的入口也不止一条：同步 Webhook、手动、重跑都绕过去重和并发；「从失败节点重放」用旧版本；MCP 的 action run 直接调连接器。
   - 后果：任何一条旁路都可能绕过闸门，或者让台账失真。
   - 缓解：闸门放在引擎执行写操作之前，而不是入口；补到位、排程、放行、唤醒统一走 `startRuns`；清扫任务用 `SKIP LOCKED` 并且可以重入；对账作为最终兜底，发现漂移就进问题。

**对设计的含义**：这三条都要在界面上留出口。预演要分级、写明「不保证成功」；台账每一行写依据，读不回的不叫「已到位」；运行列表和台账要能看出一次写入是从哪个入口来的（事件、补到位、放行、排程、人工）。

## 10. 需要实测或访谈才能确定的事

| 事项 | 怎么确定 | 影响 |
