Keep approvals and forms in the source system. Use the integration platform after submission or approval to update a ledger, notify an applicant or send a document to another system.

## Kingdee K3 Cloud manifest

The [example definition](/build-connectors/examples/kingdee-k3cloud.json) contains login, query by bill number, save, submit and audit operations. Its session header follows the [vendor's session documentation](https://vip.kingdee.com/article/182645). For the generic credential form, put the Kingdee username in Client ID, its password in Client Secret, and the data-center ID in accountId. Replace the example base URL with the test account's URL. Compare every endpoint and field with the WebAPI test page generated by that exact Kingdee tenant and version.

The save request is a starting purchase-order shape. Add its required bill header and line fields before using it. Keep `FBillNo` equal to the lookup `billNo`. The example restricts bill numbers to letters, digits, underscores and hyphens so they cannot change the query filter. Configure a unique bill number in the target, and serialize workflow runs by that number. Never test writes against a production account first.

Declare each manifest operation's `classification` and `reliability`. An authenticated operation declares its request bucket. `LOOKUP_BEFORE_WRITE` also requires `lookupKeys` and `lookupBeforeWrite: { operationKey, matchPath }`. The referenced operation must be `READ` or `SEARCH` and accept those keys. The runtime queries first, returns an existing result without writing, and rejects multiple matches. A failed lookup stops the write. This does not make two concurrent callers atomic: target uniqueness and workflow ordering remain necessary.

`readBack` points to a read action. Submit and audit in the sample are `UNSAFE`; uncertain failures stop for review. Change that declaration only when the target version documents a repeat-safe operation. Rate limits are conservative example values and need a tenant-specific quota check.

## e-cology and other OA systems

1. Add a Webhook trigger to the receiving workflow. Enable HMAC-SHA256, choose a signature header and store the shared secret in the trigger configuration.
2. In the OA workflow's post-approval integration action, send the completed document's stable ID, current status and required fields to that URL. The source remains responsible for approval decisions.
3. Sign the exact UTF-8 request bytes using HMAC-SHA256 and send the hexadecimal digest in the configured header. Do not sign a JSON string and then reformat or reserialize it. Configure the trigger's encoding and prefix to match the sender.
4. Keep the document ID as the business key and use `documentId:status` as the event deduplication key. Read the current source document before writing downstream state.
5. Test a valid request, one changed body byte and a missing signature. Invalid signatures receive HTTP 401 and start no run. Duplicate valid requests must converge to one ledger entry.

OA menu paths and integration actions differ by version. If that version cannot generate the configured signature, use an administrator-controlled signing adapter; do not disable signature checking to make the test pass. Customer-hosted endpoints also need the instance's outbound network allowlist configured when they use private addresses.
