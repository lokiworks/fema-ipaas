---
title: AI 与 MCP 作为连接器的消费层进入产品，不进入 Connector Domain
icon: 🤖
status: accepted
---

## Decision

在 ADR 0009 划定的依赖方向上加入 AI 与 MCP 能力：

- 大模型是一个普通连接器（`@fema-ipaas/connector-ai`），模型凭据就是这个连接器的连接，
  和 SAP、MySQL 的连接同级管理、同级授权。平台不设独立的「AI 服务商管理」。
- 外部 MCP 服务器也是一个普通连接器（`@fema-ipaas/connector-mcp`），一个连接就是一台 MCP 服务器，
  它的工具作为工作流里的操作调用。
- 「AI 智能体」是 AI 连接器里的一个操作，只能调用显式列出的 MCP 工具，步数有上限。
- 平台把已发布的工作流开放成 MCP 工具（项目级的 MCP 服务），调用走和 Webhook 同步调用相同的路径。
- 生成工作流、编辑器助手只产出草稿和文字建议，由人确认后才落到工作流上。
- 所有模型调用按项目、功能、模型和工作流记入 AI 用量。

## Context

ADR 0009 删除了上游深度耦合的 Agent、AI Provider 与 MCP Server，并留下
「Tool Adapter → MCP Tool → Agent」的接口位。产品原型要求 AI 生成工作流、编辑器助手、
智能体节点和 MCP 双向打通。

## Why

模型和 MCP 服务器建模成连接器，意味着 Connector 的输入输出契约不变，AI 只是它的又一个调用方，
这正是 ADR 0009 要守住的边界。否决的方案是恢复上游的平台级 AI Provider 配置：它要求运维在部署时
配置模型密钥（违反零配置自托管），并让 AI 能力绕开项目级的连接授权。

## Consequences

- 没有模型连接时，AI 功能显示为未启用并引导新建连接，不报错。
- MCP 服务只开放已发布、触发器可同步调用的工作流；单个连接器操作要先包成工作流再开放。
- 智能体节点的工具调用发生在沙箱里，受出站网络策略约束，与其他连接器一致。
- ADR 0009 的依赖方向仍然成立，本决策取代它「不做 AI 与 MCP 产品能力」的部分。
