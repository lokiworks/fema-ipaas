This section explains **why** FEMA Integration Platform works the way it does: the components, the execution model, and the trade-offs behind them. If you want to *do* something (size a deployment, set up SSL, scale workers), start with [Configure & Operate](../configure-operate/production-setup). Come here when you want the reasoning under those choices.

This page describes the main components, with a focus on how workflows run.

## Components

<img src="/resources/diagrams/fema-architecture.png" alt="FEMA Integration Platform production architecture: client, app, Redis job queue, Postgres, S3, and one-workflow-per-worker execution tier" />

**FEMA Integration Platform:**

- **App**: The main application that organizes everything from APIs to scheduled jobs.
- **Worker**: Polls for new jobs, allocates a sandbox from the pool, executes the workflows with the engine inside the sandbox, and sends results back to the app.
- **Sandbox**: An isolated execution environment that manages process lifecycle, resource limits, and communication with the engine via WebSocket.
- **Engine**: TypeScript code that parses workflow JSON and executes it. It is compiled into a single JS file and runs inside the sandbox.
- **UI**: Frontend written in React.

**Third Party**:
- **Postgres**: The main database for FEMA Integration Platform.
- **Redis**: Powers the queue using [BullMQ](https://docs.bullmq.io/).

## Reliability & Scalability

<Tip>
Postgres and Redis availability is outside the scope of this documentation, as many cloud providers already implement best practices to ensure their availability.
</Tip>

Everything is queue-backed: webhooks and recurring jobs land on Redis, and workers poll them off it. A spike does not drop work. It queues and drains as slots free. For exactly what survives a crash, what runs at-least-once, and where each promise stops, see [Guarantees](../guarantees/crash-recovery).

To scale FEMA Integration Platform, add replicas of the workers, the app, or the Postgres database. A small Redis instance is enough: it handles thousands of jobs per second and rarely becomes a bottleneck. For the concrete sizing model, see [Production Setup](../configure-operate/production-setup).

## Repository Structure


The repository is a monorepo built with Turbo, with TypeScript as the primary language. It is divided into several packages:

```
.
├── packages
│   ├── web
│   ├── server
│   │   ├── api
│   │   ├── worker
│   │   ├── engine
│   │   ├── sandbox
│   │   └── common
│   ├── ee
│   ├── connectors
│   └── shared
```

- `web`: This package contains the user interface, implemented using the React framework.
- `api`: This package contains the main application written in TypeScript with the Fastify framework.
- `worker`: This package contains the logic of accepting workflow jobs and executing them using the engine.
- `server-sandbox`: This package contains the sandbox execution environment, including process isolation, pool management, and WebSocket communication between the worker and engine.
- `common`: This package contains the shared logic between worker and app.
- `engine`: This package contains the logic for workflow execution within the sandbox. Located under `server/engine`.
- `connectors`: This package contains the implementation of triggers and actions for third-party apps.
- `shared`: This package contains shared data models and helper functions used by the other packages.
