---
title: MCP 服务按成员发 Key，连接器操作可以直接当工具
icon: 🔑
status: accepted
---

## Decision

MCP 服务的调用凭证从「一个服务一把 Token」改为「每个成员一把个人 Key」（`mcp_service_member`，`mcp_sk_` + 14 位）。
工具来源除已发布的工作流外，还可以直接是一个连接器操作，经单操作执行（EXECUTE_ACTION）运行；
这取代了 ADR 0019「单个连接器操作要先包成工作流再开放」那条后果。

## Context

设计文档 §4.16 要求：入参可取「客户端上下文」（调用者邮箱、姓名），连接可以「由服务使用者配置」
或「由用户首次调用时授权」，可用范围按人限制。这三条都要求服务端知道**是谁在调用**。

## Why

服务级 Token 只能证明「持有者拿到了 Token」，谁都可能是调用者，按人的规则无从落地。
个人 Key 让每次调用都落到一个平台用户上，可用范围、上下文、按人连接都能在服务端强制，
重置也只影响本人。否决的方案是给服务级 Token 加一个「调用者邮箱」请求头：助手客户端不会可靠地带，
而且可以随便伪造。连接器操作直接当工具是因为「包一层工作流」只为满足同步 Webhook 这条调用路径，
单操作执行已经是同步的请求/响应，没必要再造一个工作流。

## Consequences

- 老服务（没有 `key`、没有发布记录）继续用服务级 Token 走 `/v1/mcp/:id`，不强制迁移。
- 所有者创建服务时自动得到一把 Key；其他人要先「获取」服务。Key 加密保存，供本人再次复制。
- 连接器操作工具不产生运行记录，失败只体现在工具返回里；需要运行历史的场景仍应开放工作流。
- 「使用者配置 / 首次调用授权」要求连接在服务所在项目可用，非项目成员实际上用不了这两种模式。
