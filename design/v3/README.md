# 第三版原型：首发主线的核心闭环

> 已放弃的探索（2026-10-01）。产品以飞书 AnyCross 为蓝本，主原型是第二版 `design/index.html`。

第二版把 AnyCross 的页面铺全了；这一版只做首发主线（北森 → 飞书人员同步），把「上线之后」的体验做深。出发点是一句话：集成的成本大头在上线之后，平台卖的是「没人盯着也不出错，出了错能很快补平」。

产品上的取舍写在 [../research/product-brief.md](../research/product-brief.md) 的「可靠性原则」，以及决定 000040（对账不算 ETL）、000041（人员同步不做身份产品）、000042（按期望状态同步，待确认）。

## 怎么打开

双击 `design/v3/index.html`。不需要构建和联网，和第二版共用 `vendor/`、`fonts/`、`styles/tokens.css`、`styles/app.css`、`scripts/core.js`、`scripts/ui.js`。

- 演示数据存在浏览器的 localStorage（键 `fema-v3-state-v1`），和第二版互不影响。头像菜单 →「重置演示数据」回到初始状态。
- 深色模式在头像菜单里。`⌘K`（Windows 上是 `Ctrl+K`）按工号、姓名、手机号后四位查人。
- 左侧栏「导览」列出这版要证明的五件事，和一条约 5 分钟的值班演示路线。

## 这版要证明的五件事

1. 值班的人 10 秒内知道有没有人没同步好：首页按对业务的影响排序，每个集成显示「还没同步好的人数」，而不是运行成功率。
2. HR 问到某个人，30 秒内答上来：查人页把北森的变动、平台的运行、问题、对账和人工操作按时间排在一起。
3. 一条告警，修好原因，安全重放：重放前逐人检查，还会失败的先不重放；按幂等声明决定执行还是跳过。
4. 「不漏」是能证明的：对账抓到事件触发发现不了的差异。
5. 新集成一小时内上线，第一天就看清历史欠账：方案向导加首次对账。

## 新概念

- **业务键**：工号这类能认出同一个人的字段，在触发器上定义一次，同时用于去重、查人、对账匹配和重放分组。
- **按期望状态同步**：触发后按业务键重新读取源系统最新状态，确保目标与之一致；重放、补处理、对账补齐、手动同步都是「对这个人再跑一次」。
- **幂等声明**：每个写操作标明幂等、不幂等或只读。超时后幂等的自动重试；不幂等的进入「结果未知」，等人确认。
- **对账**：按业务键比对两边名单，产出差异（离职仍可登录、漏开通、部门不一致、目标系统多出的账号）。对账只读，补齐走工作流；例外可以设到期时间。
- **起点**：启用或停用后再启用时，选择从停用时刻、从现在或从指定时间开始处理。
- **连接速率上限**：同一连接的请求共用，超出的排队等待，不算失败。
- **深度清单**：第一方连接器都要过的 7 项：连接向导与缺权限提示、分页取全、声明速率上限、写操作声明幂等、错误码映射、输出结构、能列出全量名单。

## 和第二版的关系

编辑器的完整交互、环境推广与审批、AI 生成工作流、MCP、自托管运维仍以第二版（`design/index.html`）为准。第三版的工作流页是只读的结构视图加检查、试运行和启停，不重复造编辑器。

## 改原型时注意

- 和第二版共用 `scripts/core.js`、`scripts/ui.js`。第三版在加载它们之前设置 `window.PROTOTYPE_STORE_KEY`，所以存储键不同；改共用文件要两版都打开看一遍。
- 所有脚本共享一个全局作用域，第三版自己的文件之间也不能有同名的顶层函数或常量。页面组件按名字挂在 `window` 上，由 `app.js` 的 `ROUTES` 查找。
- 改了演示数据的结构，把 `index.html` 里的 `fema-v3-state-v1` 版本号加一。
- 演示时间都锚定在「最近一次凌晨 2 点的对账」上，打开原型的时间不同，相对时间仍然自洽。
- 验证至少做三件事：按 `index.html` 的顺序把脚本拼成一个文件跑 ESLint（`no-undef`、`no-redeclare`）；用 Playwright 把上面表格里的流程点一遍；亮色、深色各截图看一遍。

## 已知限制

- 没有后端，所有数据都是演示数据。AI 诊断、部门的 AI 匹配建议按规则模拟；「重新检查连接」「验证凭证」总会通过。
- 对账只把与故事有关的人做成了具体数据，其余一致的人只计入总数。
- 原型没有做响应式，建议在 1280px 以上的宽度查看。
