调研时间 2026-10-01。目的：核实 `design-inputs.md` 推荐方向（结果台账）所依赖的飞书能力，补第一轮缺的证据。只用官方文档：飞书部分全部取自 open.feishu.cn 开发文档（经开放平台文档门户 `document_portal/v1/document/get_detail` 读取正文，和网页同源），暂停账号的用户侧行为取自飞书帮助中心（官方，但不是开发文档，单独标出）；企业微信取自 developer.work.weixin.qq.com；钉钉取自 open.dingtalk.com 和钉钉官方维护的开发者百科（open-dingtalk.github.io）。

## 一页结论

1. **查人：能按手机号、邮箱、user_id 查，通讯录 v3 不能按工号查，权限范围外的人一律「查不到」。** `batch_get_id` 一次最多 50 个手机号加 50 个邮箱，应用无权查看的人不返回 ID，和「不存在」在返回上分不开（需实测返回形态）。按工号只能走另一套「组织架构 v1」的 `employees/filter`（`work_info.job_number` 支持 eq、in），或者列全量后在本地建索引。自定义字段在两套接口里都不能做查询条件。
2. **列人：只能按部门列直属成员（每页最多 50），部门树可以一次递归拿。** 1 千人约 90 次调用，1 万人约 820 到 1,020 次，受「每接口每分钟 1000 次」约束，1 万人全量读一遍约 1 分钟。通讯录接口不计入基础免费版的月调用量。
3. **权限范围能用接口读出来，也有变更事件；但读出来的是「配置的节点」，不是「覆盖的全部部门」。** 文档写明「只要有一个部门的通讯录范围权限，那么就拥有这个部门下所有子部门的权限」，所以父部门在范围内时，子部门（包括新建的）按规则也在范围内（生效时延需实测）。`contacts_range_configuration` 能读出范围类型（全部、部分、与可用范围一致），`contact.scope.updated_v3` 事件带新增和移除的对象。「平台读权限范围、就绪后自动补到位」的前提成立。
4. **写入有两条硬约束是第一轮没发现的：** 改部门（`department_ids`）和暂停（`is_frozen`）「限制调用频率为 1 QPS」，并发冻结会因事务冲突概率性失败；创建用户会立即发出邀请短信或邮件，接口没有关闭邀请的参数，账号在本人接受邀请前是「未激活」。
5. **「删除会直接删掉文档」与当前官方文档不符。** 现行文档写的是：不指定接收人时，文档、妙记、邮件、应用默认转给直属上级，没有上级就「保留在该用户名下」；被直接删除的是日程和飞书问卷；外部群在组织内只剩此人时会被解散。删除后 30 天内可以「恢复已删除用户」，但只限商业专业版、商业旗舰版和企业版各档（基础免费版不行），且部门归属、管理员角色、已转移的资源恢复不了。「首发只暂停、不删除」的结论仍成立，理由要换。
6. **暂停（`is_frozen`）是安全的停用方式，但占席位。** 帮助中心原文：暂停后「无法登录飞书」，数据保留，别人仍能给他发消息，企业邮箱退信；「被暂停账号的成员依然占用席位」，离职后才释放。已登录的会话是否立刻失效，文档没写，需实测。
7. **飞书的限流计数单位是「每个接口 × 每个应用 × 每个租户」，不是租户。** 同一租户里两个不同的自建应用不共享频控；但「组织架构 v1」接口另有企业级累计限制，基础免费版另有全租户共享的月调用量（消息接口计入，通讯录接口不计入）。超限返回 HTTP 429、错误码 99991400 和 `x-ogw-ratelimit-reset` 响应头，没有 `Retry-After`；月调用量耗尽也是 HTTP 429，错误码却是 99991403，不能按「等几秒再试」处理。
8. **事件可以不要公网入口：长连接模式只需出网。** 限企业自建应用；每个应用最多 50 个连接；多实例时「只有其中随机一个客户端会收到消息」；3 秒内处理完，否则按 15 秒、5 分钟、1 小时、6 小时重推，最多 4 次。一个应用的事件订阅方式只能二选一（长连接或一个公网地址）。新版卡片按钮回传（`card.action.trigger`）也能走长连接，回调里带点击者的 user_id 和 open_id。
9. **「推送会丢，要拉取比对兜底」现在有官方原话支撑。** 飞书重推 4 次后不再推；企业微信回调文档写明「目前无法保证100%回调成功……建议开发者不要强依赖回调，需要额外机制对齐相关业务数据」。
10. **企业微信只有「通讯录同步」能写，钉钉自建应用可以直接写。** 企业微信自建应用「仅能读取通讯录，不能编辑」，写入要用通讯录同步 secret，2022 年 6 月 20 日起必须配本企业服务器的可信 IP；2022 年 6 月 20 日后新建的自建应用读不到手机号和邮箱，按手机号兜底匹配在企业微信上走不通。钉钉企业内部应用申请「维护通讯录的接口访问权限」即可写，Stream 模式收事件和卡片回调都不需要公网 IP。

## 1. 查人

### 1.1 按手机号或邮箱批量查（`POST /contact/v3/users/batch_get_id`）

- **原文**（[通过手机号或邮箱获取用户 ID](https://open.feishu.cn/document/server-docs/contact-v3/user/batch_get_id)，2026-04-07）
  - 「要查询的用户邮箱，最多可传入 50 条」「要查询的用户手机号，最多可传入 50 条」「本接口返回的用户 ID 数量为 emails 数量与 mobiles 数量之和」。
  - 「请求后不返回用户 ID 的可能原因：……输入的手机号或者邮箱不存在……应用无权限查看用户信息。你需要在应用详情页为应用配置数据权限……使用企业邮箱查询将无法返回用户 ID，必须使用用户的邮箱地址……所查询的用户已离职，如果请求参数 include_resigned 取值为 false，则不会返回离职用户 ID。」
  - 返回带 `status`：`is_frozen`、`is_resigned`、`is_activated`、`is_exited`、`is_unjoin`。频控 1000 次/分钟、50 次/秒。
- **结论**：上限 50 + 50。**权限范围外的人查不到**，返回里没有 ID，和「手机号不存在」无法区分；返回的条目是「有 mobile 无 user_id」还是整条缺失，**需实测**。企业邮箱不能用来查。
- **对设计的影响**：匹配阶段的「没找到」只能写成「在通讯录权限范围内没找到」。存量对齐里「北森有飞书无」这一栏，可能混着「飞书里有、但在范围外」的人，对这些人直接创建会撞 41001。

### 1.2 按工号查

- **通讯录 v3：没有按工号查的接口。** 工号是用户对象上的 `employee_no` 字段，创建接口原文「同一租户下，用户工号不能重复」，重复时报 44051「员工工号重复」；但 v3 的查询接口只接受 user_id、open_id、union_id、手机号、邮箱。返回体里要拿到工号，需要开通对应的字段权限（如「查看成员工号」）。
- **组织架构 v1：`POST /directory/v1/employees/filter` 可以按工号筛。**
  - **原文**（[查询条件用法](https://open.feishu.cn/document/directory-v1/filter-usage)）：支持的筛选左值为 `base_info.mobile`（eq、in）、`base_info.email`（eq、in）、`work_info.job_number`（eq、in，「按照工号筛选」）、`work_info.staff_status`（「需配合部门ID组合查询」，「暂不支持离职状态(2)」）、`base_info.departments.department_id`（「需配合人事状态组合查询」）；`conditions`「多个表达式之间的关系为且」，长度 0 到 10。
  - **原文**（[批量获取员工列表](https://open.feishu.cn/document/directory-v1/employee/filter)）：分页「最大100条」；「使用tenant_access_token时，数据权限遵循应用的通讯录权限范围」；频控 1000 次/分钟、50 次/秒。组织架构 v1 的工号字段原文是「企业内在职员工的工号不可重复」（只约束在职员工，和 v3 的说法不同）。
  - **矛盾**：[配置应用数据权限](https://open.feishu.cn/document/home/introduction-to-scope-and-authorization/configure-app-data-permissions)说组织架构有自己的数据权限，「默认情况下，组织架构数据权限范围未配置……仅支持指定员工范围，不支持指定部门范围」。到底按哪个范围过滤，**需实测**；`in` 一次能放多少个工号，**未查到**。
- **对设计的影响**：「工号优先、手机号兜底」做得到，但要么接第二套接口（多一组权限、多一套数据权限配置），要么全量列出后在本地按 `employee_no` 建索引（见第 2 节，1 万人约 1 分钟）。手工建的存量账号常常没有工号，兜底不能省。

### 1.3 按自定义字段查

- 用户对象有 `custom_attrs`，但 v3 和组织架构 v1 的查询条件里都没有自定义字段（v1 的可筛字段见 1.2 原文）。**结论：不支持，未查到任何按自定义字段查询的接口。**
- **对设计的影响**：方向 B 设想的「下拉只列连接器声明能按值查询的字段」，飞书连接器能声明的只有手机号、邮箱、工号（v1）、user_id、open_id、union_id。

### 1.4 按 user_id（或 open_id、union_id）查

- **原文**（[获取单个用户信息](https://open.feishu.cn/document/server-docs/contact-v3/user/get)，2026-04-03；[批量获取用户信息](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/reference/contact-v3/user/batch)，2025-07-15）
  - `GET /contact/v3/users/:user_id`，用 `user_id_type` 指定 `open_id`、`union_id` 或 `user_id`；批量接口「单次最大请求可设置的用户 ID 数量上限为 50」。两者都是 1000 次/分钟、50 次/秒。
  - 不在范围内时报 41050「无用户权限……应用无法访问不在通讯录权限范围内的数据」。
  - 三种 ID 的含义（[用户资源介绍](https://open.feishu.cn/document/server-docs/contact-v3/user/field-overview)）：「user_id 是用户在某一租户内的身份标识」「open_id 是用户在某一应用内的身份标识」；user_id「可以自定义设置，也可以由系统随机生成」，最长 64 字符。
  - 可以改：`PATCH /contact/v3/users/:user_id/update_user_id`（[更新用户 ID](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/reference/contact-v3/user/update_user_id)，20 次/秒），有次数上限（41013「超过用户 ID 更新次数限制」，具体次数未查到）。组织架构 v1 的更新接口提醒：「员工ID（employee_id）是员工在企业内的唯一ID，可能会被应用引用来实现各种内部逻辑，唯一ID修改之后可能会导致引用失败」。
- **对设计的影响**：
  - 第一次匹配成功后，把 open_id 和 user_id 记进对应关系，之后一律按 ID 批量读（每次 50 人），这是最便宜、最确定的核对方式。
  - 新建账号时可以约定 `user_id = 工号`，以后按工号直接 GET。改存量账号的 user_id 会影响租户里其他应用，只能作为管理员明确同意的一次性动作，不能默认做。

### 1.5 用户状态（读回时看什么）

- **原文**（[用户资源介绍](https://open.feishu.cn/document/server-docs/contact-v3/user/field-overview)，2026-04-07）：用户状态「包括是否激活、是否暂停、是否离职、是否主动退出、是否未加入」。文档里的状态图：创建用户后进入「Inactive 用户未激活」或「Unjoined 未加入」；激活后为「Active」；Active 和 Inactive 都可以和「Frozen 冻结/暂停」互转；Active 退出租户为「Quit」，可重新加入。离职（删除）不在这张图里，由 `is_resigned` 表示。
- **对设计的影响**：「账号到位」要分两层：已建（待激活）和已激活。「离职仍可登录」应判为 `is_resigned = false` 且 `is_frozen = false`；其中 `is_activated = false` 的人此刻登不了，但还能接受邀请进来，同样是风险。

**对设计的含义（第 1 节）**

- 对应关系必须存飞书 ID（open_id、user_id），日常核对按 ID 批量读；工号和手机号只在第一次匹配时用。
- 台账要有一个独立状态「无权查看（不在通讯录权限范围）」，不能把看不见的人算成「未到位」或「不存在」。
- 连接器的「按键查」要声明自己能按哪些字段查、每批多少个，平台据此算预演耗时和配额。

## 2. 列人

### 2.1 按部门列直属成员（`GET /contact/v3/users/find_by_department`）

- **原文**（[获取部门直属用户列表](https://open.feishu.cn/document/server-docs/contact-v3/user/find_by_department)，2024-10-23）
  - 「调用该接口获取指定部门直属的用户信息列表」；`page_size`「默认值：10」「最大值：50」。
  - 「使用应用身份（tenant_access_token）调用该接口时，接口将根据应用的通讯录权限范围进行过滤。如果请求的部门 ID 为 0（即根部门），则接口会校验应用是否具有全员的通讯录权限；如果请求的是非 0 的部门 ID，则会校验应用是否具有该部门的通讯录权限。无权限时，接口会返回无权限的报错信息」（40004 或 41050）。
  - 频控 1000 次/分钟、50 次/秒。
- **结论**：只有直属，不递归；要逐个部门调用；对每个部门都校验权限范围。旧的「获取用户列表」（`GET /contact/v3/users`）已是历史版本，同样只返回直属成员（[获取用户列表](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/reference/contact-v3/user/list)）。

### 2.2 递归拿部门树（`GET /contact/v3/departments/:department_id/children`）

- **原文**（[获取子部门列表](https://open.feishu.cn/document/server-docs/contact-v3/department/children)，2024-09-20）：`fetch_child`「取值为 true 时，接口会递归查询当前部门下所有层级的子部门信息」；`page_size` 最大 50；「如果需要查询根部门（部门 ID 为 0）下的子部门列表，则应用的通讯录权限范围需设置为 **全部成员**」。频控 1000 次/分钟、50 次/秒。
- 组织架构 v1 的部门对象带 `recursive_members_count`、`direct_members_count`（[员工资源介绍](https://open.feishu.cn/document/directory-v1/employee/resources-introduction)），可以先估人数再决定怎么扫。

### 2.3 组织架构 v1 的批量员工列表（备选）

- `employees/filter` 每页最多 100，`page_token`「支持深分页，在需要遍历全部数据的场景只能使用该方式」。但部门条件必须和人事状态组合、不支持离职状态，条件为空能否列全量、部门条件是否含子部门，**需实测**。

### 2.4 全量调用次数估算

前提：范围是「全部成员」；部门数按平均每部门 12 人左右估；每个部门至少调 1 次 `find_by_department`，超过 50 人的部门按 50 人一页加页；`children` 和 `find_by_department` 是两个接口，频控各算各的。

| 规模 | 部门树（children，递归） | 成员（find_by_department） | 合计 | 按频控估的耗时 |
| --- | --- | --- | --- | --- |
| 1 千人，约 80 个部门 | ⌈80/50⌉ = 2 次 | 80 + 大部门加页约 5 = 约 85 次 | **约 90 次** | 50 次/秒下约 2 秒 |
| 1 万人，约 800 个部门 | ⌈800/50⌉ = 16 次 | 下限 800，上限 800 + 10,000/50 = 1,000 | **约 820 到 1,020 次** | 受 1000 次/分钟约束，约 1 分钟 |
| 已知对应关系，按 ID 核对 | 不需要 | 1 千人 20 次，1 万人 200 次（每批 50） | 20 / 200 次 | 秒级 |
| 组织架构 v1 filter（若可列全量） | 不需要 | 1 千人约 10 次，1 万人约 100 次（每页 100） | 需实测 | 需实测 |

- 一人属于多个部门时会被重复列出，本地去重。
- 范围不是「全部成员」时，从 `GET /contact/v3/scopes` 返回的每个部门分别递归，再加上范围里单独授权的用户（按 ID 批量读）。
- 这些都是通讯录接口，不计入基础免费版的月调用量（见 6.4）。

**对设计的含义（第 2 节）**

- 「看现状」和定期全量对账在 1 万人规模下是分钟级，可以放心做成产品能力；日常核对优先按对应关系里的 ID 批量读。
- 平台读不到范围外的人，所以「飞书有北森无」只覆盖范围内。看现状的结果页要写明「核对范围：飞书应用的通讯录权限范围（N 个部门）」。
- 连接器的「列出全部」要实现为「拿范围 → 递归部门 → 逐部门分页 → 去重」，并把每一步的调用数报给平台，用于预演里的「约 1 分钟」。

## 3. 权限范围

### 3.1 应用可用范围和通讯录权限范围是两件事

- **原文**（[权限范围资源介绍](https://open.feishu.cn/document/server-docs/contact-v3/scope/scope_authority)，2025-05-12）：「通讯录权限范围定义了应用在调用通讯录 API 时可获取的部门、用户的数据范围。应用无法访问不在通讯录权限范围内的数据。」「默认情况下，通讯录权限范围与应用的可用范围一致。」「商店应用无法修改用户所在企业的通讯录信息。」
- **原文**（[配置应用可用范围](https://open.feishu.cn/document/home/introduction-to-scope-and-authorization/availability)）：「应用可用范围定义了哪些用户群体（组织、用户组、个人）可以使用该应用」。典型案例：人力应用「应用可见范围：设置为仅 HR 部门内的成员」「应用的通讯录权限范围：设置为全部成员」。
- 通讯录权限范围的三种取值（[配置应用数据权限](https://open.feishu.cn/document/home/introduction-to-scope-and-authorization/configure-app-data-permissions)）：「与应用的可用范围一致」「部分成员」「全部成员」。
- 可用范围还决定能给谁发私聊：「给用户发送消息时，用户需要在机器人的可用范围内」（[发送消息](https://open.feishu.cn/document/server-docs/im-v1/message/create)）。

### 3.2 父部门在范围内时，子部门（包括新建的）是否自动进入范围

- **原文**（[权限范围资源介绍](https://open.feishu.cn/document/server-docs/contact-v3/scope/scope_authority)，「权限生效规则」）：「调用 API 的应用或者用户身份，只要有一个部门的通讯录范围权限，那么就拥有该部门下所有用户的权限。」「只要有一个部门的通讯录范围权限，那么就拥有这个部门下所有子部门的权限。」创建部门需要「父部门通讯录范围权限」。
- **结论**：按规则，权限沿部门树向下继承，父部门在范围内时其下新建的子部门也在范围内；平台在范围内的父部门下建子部门是允许的。文档没有明说新建子部门的生效时延，**需实测**。

### 3.3 谁能改、改了多久生效

- 开发者改：「修改通讯录权限范围后，需要创建应用版本，由管理员审核通过后才可生效。」（权限范围资源介绍）
- 企业管理员改：「企业管理员可以在管理后台 > 工作台 > 应用管理 页面，进入指定应用管理页，然后管理应用的 通讯录设置。」对可用范围，文档明确「由于企业管理员本身就是具备权限变更审核权限的，所以无需发布新版本，可直接修改应用的可用范围」；对通讯录权限范围走管理后台是否同样立即生效，**需实测**。
- 错误码给出的修复路径（[创建用户](https://open.feishu.cn/document/server-docs/contact-v3/user/create) 40004）：「在应用详情页的 开发配置 > 权限管理 > 数据权限 功能页查看 通讯录权限范围……并发布应用使配置生效」；若范围设成「与应用的可用范围一致」，要在「应用发布 > 版本管理与发布 > 创建版本」的版本详情里改可用范围再发布。

### 3.4 能否用接口读取当前范围：能，有三个入口

| 入口 | 原文要点 | 频控 |
| --- | --- | --- |
| `GET /contact/v3/scopes`（[获取通讯录授权范围](https://open.feishu.cn/document/server-docs/contact-v3/scope/list)） | 「当应用通讯录权限范围为全部成员时，该接口将返回根部门下的一级部门列表和直属用户列表，以及租户下所有用户组列表。」「当应用通讯录权限范围不为全部成员时，则只返回在通讯录权限范围内的部门列表（不包含部门内的子部门以及用户）、用户列表或用户组列表。」 | 1000 次/分钟、50 次/秒 |
| `GET /application/v6/applications/:app_id/contacts_range_configuration`（[获取应用通讯录权限范围配置](https://open.feishu.cn/document/server-docs/application-v6/admin/contacts_range_configuration)） | 「获取当前企业内某个自建应用线上实际生效的通讯录权限范围配置」；`contacts_scope_type` 取值 `equal_to_availability`、`some`、`all`；`some` 时给出 `visible_list`（用户、部门、用户组）。需要「获取应用信息」权限 | 100 次/分钟 |
| 事件 `contact.scope.updated_v3`（[通讯录权限范围变更](https://open.feishu.cn/document/server-docs/contact-v3/scope/events/updated)） | 「如果应用的通讯录权限范围发生变更，则会触发该事件」；事件体有 `added`（「新增的对象信息」）和 `removed`（「移除的对象信息」） | 不适用 |

另有 `GET /application/v2/app/visibility`（[获取应用在企业内的可用范围](https://open.feishu.cn/document/server-docs/application-v6/admin/obtain-the-app-availability-in-an-organization)），用于范围类型是「与可用范围一致」时查具体名单。

### 3.5 范围外会怎样

| 操作 | 范围外的表现（原文或错误码） |
| --- | --- |
| 按手机号或邮箱查 | 不返回 ID（1.1） |
| 按 ID 读、改、删 | 41050「无用户权限」 |
| 按部门列、读部门 | 40004「无部门权限」；查根部门要求全员权限 |
| 创建用户 | 「所操作的所有部门均需要在当前应用的通讯录权限范围内……如果需要在根部门下创建用户，则应用必须有全员权限」 |
| 删除用户 | 「待删除用户归属部门 A、部门 B，则应用的通讯录权限范围必须包括部门 A 和部门 B」 |
| 改用户的部门 | 40004「无部门权限。当前操作的部门需在应用的通讯录权限范围内」；组织架构 v1：「当变更员工的部门信息时，应用需要有变更前后的部门权限，才能变更成功」 |
| 移动部门 | 「所涉及的所有部门需要在应用的通讯录权限范围内」（[修改部门部分信息](https://open.feishu.cn/document/server-docs/contact-v3/department/patch)） |
| 变更事件 | 「用户必须在应用的通讯录权限范围内，应用才可以发送该用户的信息变更事件」（[员工信息被修改](https://open.feishu.cn/document/server-docs/contact-v3/user/events/updated)） |

**对设计的含义（第 3 节）**

- 「发布前检查权限范围」做得到，但要自己算覆盖集：拿 `scopes`（或 `contacts_range_configuration`）给出的部门，逐个 `children(fetch_child=true)` 展开，再拿映射表里的目标部门去比。目标部门不在覆盖集里时，平台分不清它是「在范围外」还是「已被删除」，问题文案要写「平台看不到这个部门」。
- 「等待对方」的自动关闭：订阅 `contact.scope.updated_v3`，收到 `added` 就重新检查受影响的人；定时读接口只做兜底。
- 对方待办单的步骤要按 `contacts_scope_type` 分支：`some` 时让管理员加部门；`equal_to_availability` 时要改的是可用范围；两种都要写「创建版本并审核」，同时给出管理后台路径。
- 可用范围要覆盖「要收私聊通知的人」。如果欢迎消息发给新员工本人，可用范围不能只设成 HR 部门，这是安装清单里的一项检查。

## 4. 写操作

### 4.1 创建用户（`POST /contact/v3/users`）

- **原文**（[创建用户](https://open.feishu.cn/document/server-docs/contact-v3/user/create)，2026-04-07）
  - 「调用该接口向通讯录创建一个用户（该动作可以理解为员工入职）。成功创建用户后，系统会以短信或邮件的形式向用户发送邀请，用户在同意邀请后方可访问企业或团队。」请求体里没有关闭邀请的参数（逐个字段核对过）。
  - `client_token`：「用于幂等判断是否为同一请求，避免重复创建」「默认值：空，表示不进行幂等判断」。40021：「两次请求如果传入了相同的 client_token，则当传入的其他参数取值不相同时，会报该错误。」
  - 41001：「手机号已存在。你需要修改传入的手机号，确保租户内唯一。如何通过手机号查询用户信息，可参见通过手机号或邮箱获取用户 ID。」41002 同理（邮箱）。41003：「用户的联系方式属于两个不同的飞书账号，导致添加失败」。44051：「员工工号重复，请修改后重试。」41053（HTTP 409）：「用户已存在。」
  - 部分成功：44054「创建用户成功，创建工作城市字段失败」，44055「创建用户成功，创建职务字段失败」，44056 两者都失败。
  - 其他与主线相关的：40004 部门不在范围；41007、41008、44023 人数或席位上限；44046 到 44048 多许可证租户必须指定席位；44004「用户加入团队过于频繁，请 24 小时后重试」；44009「一个手机号码或者一个邮箱，一天只能加入三个租户」；44021「直接主管或者虚线上级已离职，无法使用」；44022 主管无效；41016 部门人数过多；「未认证企业的人数上限为 100」。
  - 错误码表现有 **93 个**（第一轮记的是 79 个）。频控 1000 次/分钟、50 次/秒。
- **需实测**
  - `client_token` 的有效期，以及同一 token 重放时是返回第一次创建的用户，还是报错。文档都没写。
  - 41001、41002 的错误响应里有没有已存在用户的 ID。文档只让你再去调 `batch_get_id`。
- **对设计的影响**
  - 「入职日前 N 天开通」就是「入职日前 N 天发出加入企业的邀请」。这个提前量是 HR 和 IT 要知情的业务设置，不只是技术参数。
  - 41001、41002、44051 不应该是失败，而是转入「查找并链接」：先按手机号、邮箱、工号查；查不到（多半在范围外）时进对应关系的待确认池，交给飞书管理员。41003 要交给员工本人或 HR 处理联系方式。
  - 现有连接器用 `hash(appId:手机号)` 作为 client_token（`packages/connectors/community/feishu/src/lib/common/contacts.ts`），同一手机号的人离职再入职时会复用同一个 token；在有效期确认之前，token 应该由「业务键 + 这次要达成的状态（如入职生效日）」生成。
  - 44054 到 44056（以及更新时的 44057 到 44059）是「账号已建、某个字段没写进去」，台账要能表达「部分到位」，补救只补缺的字段。

### 4.2 更新用户：改部门、改直属上级（`PATCH /contact/v3/users/:user_id`）

- **原文**（[修改用户部分信息](https://open.feishu.cn/document/server-docs/contact-v3/user/patch)，2026-04-07）
  - 「发送请求时，未传递的参数不会更新。」
  - 「并发操作冻结用户时，因事务冲突会遇到概率性的接口调用失败。因此，请尝试降低请求速率或改为串行执行。」
  - 「更新 `department_ids`、`is_frozen` 时，限制调用频率为 1 QPS。」（接口整体频控仍标 1000 次/分钟、50 次/秒。）
  - 相关错误码：40004（部门不在范围）、41050（用户不在范围）、42006「用户已经离职，无法更新信息」、44010「不允许更新未加入状态的用户信息」、44011「禁止更新主动退出状态的用户信息」、44025「并发更新User受限，请等待一段时间重试」、44036「不允许将租户创建者的状态跟改为冻结」、44053「无法编辑来自外部数据源的数据」、41030 不能把直属上级设为自己、41016「用户所属部门中的用户数量不能超过 500」。
  - **PATCH 的错误码表里没有 44021。** 44021 只出现在创建用户的错误码表。把直属上级改成已离职的人会返回什么，**需实测**。
  - 部门创建接口另有 42006：「已离职的用户不能设置为部门主管、部门负责人以及 HRBP」。
- **矛盾**：PATCH 说单部门用户「不能超过 500」，[创建部门](https://open.feishu.cn/document/server-docs/contact-v3/department/create)说「单个部门的直属成员数量上限为 10,000」。**需实测**。
- **对设计的影响**
  - 改部门和暂停是 **1 QPS 的串行队列**，与创建（50 次/秒）分开排。一次组织调整要移动 300 人，至少 5 分钟；预演卡上的「约 N 秒」必须按动作类型分别算。
  - 44053（以及部门侧的 43031）意味着：如果客户的飞书通讯录由某个外部数据源维护，接口写不进去。这是安装前要检查、并要访谈确认的前提。
  - 「上级已离职」要在收敛顺序里处理（先处理上级，或暂不设上级），不能只依赖 44021 这个码。

### 4.3 暂停（`is_frozen`）

- **开发文档原文**：PATCH 的 `is_frozen`「是否是暂停状态的用户」，`true` 暂停、`false` 恢复；改它限 1 QPS（4.2）；不能冻结租户创建者（44036）。组织架构 v1 的更新员工接口同样能「冻结/恢复员工」，频控 10 次/秒（[更新员工信息](https://open.feishu.cn/document/directory-v1/employee/patch)）。
- **帮助中心原文**（[管理员暂停成员账号](https://www.feishu.cn/hc/zh-CN/articles/360041605594)，飞书帮助中心，非开发文档）
  - 「暂停期间，该成员将无法登录飞书，但组织内其他成员依然可以向该成员发送消息、邀约日程、共享文件等。」
  - 「成员的账号被暂停后，该成员将无法登录飞书，登录时会提示“该账号已冻结，联系管理员处理”。」
  - 「系统会保留该成员的所有数据」；「暂停期间成员的企业邮箱将无法收信，发送给该成员的邮件将会被退回。」
  - 「被暂停账号的成员依然占用席位，因此企业剩余席位数量不会增加。管理员操作成员离职后，系统才会释放席位。」
  - 恢复：「被暂停的账号依然可以恢复使用。恢复后，该成员可以看到暂停期间的所有记录。」
  - 「管理员无法对状态为“未激活”和“未加入”的账号进行暂停操作。」（这是管理后台的限制；开发文档的状态图里 Inactive 可以转 Frozen，接口能不能暂停未激活账号，**需实测**。）
- **需实测**：已登录在手机和电脑上的会话是否立刻被踢下线、多久生效（文档未写）；未激活账号是否占席位。
- **对设计的影响**
  - 「离职默认暂停」成立：可逆、不动数据、能读回（`status.is_frozen`）。代价是席位，台账和月报要显示「已暂停占用席位 N 个」，后续需要「暂停 N 天后删除」的策略。
  - 暂停后企业邮箱退信。如果客户依赖离职人员邮箱做交接，要先转移再暂停，或者在设置页上说明这一点。
  - 入职前取消入职的人（账号未激活）可能暂停不了；未激活账号没有数据，直接删除是安全的替代动作，前提是实测确认。

### 4.4 删除用户（`DELETE /contact/v3/users/:user_id`）

- **原文**（[删除用户](https://open.feishu.cn/document/server-docs/contact-v3/user/delete)，2026-04-07）
  - 「从通讯录内删除一个指定用户（该动作可以理解为员工离职），删除时可通过请求参数将用户所有的群组、文档、日程和应用等数据转让至他人。」
  - 「删除用户后，你可以调用获取单个用户信息接口……确保用户已成功删除（对应已离职状态）。」
  - 接收人参数和不传时的默认去向：

| 参数 | 不指定时（原文） |
| --- | --- |
| `department_chat_acceptor_user_id` 部门群 | 「群主会默认转让给群内第一个入群的人」 |
| `external_chat_acceptor_user_id` 外部群 | 转给「群内与被删除用户在同一组织的第一个入群的人。如果组织内只有被删除用户在群里，则解散外部群」 |
| `docs_acceptor_user_id` 文档 | 「默认转让给被删除用户的直属上级。如果被删除用户无直属上级，则将文档资源保留在该用户名下」 |
| `calendar_acceptor_user_id` 日程 | 默认给直属上级，「如果被删除用户无直属上级，则直接删除日程资源」 |
| `application_acceptor_user_id` 应用 | 默认给直属上级，无上级则保留，「但该用户无法登录开发者后台进行应用管理」 |
| `minutes_acceptor_user_id` 妙记 | 默认给直属上级，无上级「将妙记保留在该用户名下」 |
| `survey_acceptor_user_id` 飞书问卷 | 默认给直属上级，无上级「直接删除飞书问卷资源」 |
| `email_acceptor` 邮件 | 默认给直属上级，无上级则保留；`processing_type` 可选「转移资源」「保留资源」「删除资源」 |
| `anycross_acceptor_user_id` 集成平台资源 | 默认给直属上级，无上级则保留 |

  - 错误码：40004、41050（范围）、41052 接收人无效、44037「无法删除租户管理员」、44042「当前用户在恢复流程中」、44062「根据租户管理员规则配置，该用户仅能通过生命周期引擎删除」。
- **恢复**（[恢复已删除用户](https://open.feishu.cn/document/server-docs/contact-v3/user/resurrect)，2025-04-30）：「仅适用于飞书商业专业版、商业旗舰版、企业标准版、企业专业版、企业旗舰版」「仅适用于企业自建应用」「仅支持恢复离职 30 天内的成员」；「不可恢复的数据：已转移的资源、成员所属部门、管理员角色等数据」；频控 10 次/分钟；44034「用户离职流程仍在进行中，请等待至多 48 小时后重试」。
- **对设计的影响**
  - 第一轮「没有接收人、员工又没有上级，文档会被直接删掉」与现行文档不符：文档会保留，直接删除的是日程和问卷，外部群可能被解散。
  - 更该防的反而是默认去向：不传接收人时，文档、邮件、妙记默认转给直属上级。删除动作必须显式配接收人规则，预演里列出每类资源转给谁。
  - 删除释放席位、只能在付费版 30 天内部分恢复，所以「首发只暂停、不删除」仍是对的。删除要等「接收人规则 + 缓冲期 + 审批」齐了再开放。
  - 44062 说明有的租户只允许用飞书自己的「成员生命周期」删除，连接器要把它归为「需要飞书管理员」。

### 4.5 其他写入路径：组织架构 v1

组织架构 v1（[组织架构概述](https://open.feishu.cn/document/directory-v1/overview)）也能创建（5 次/秒）、更新（10 次/秒）、离职（10 次/秒）员工，另有「更新在职员工为待离职」（10 次/分钟，「「待离职」员工不会自动离职，需要使用「离职员工」API操作离职和资源转交」）。它的创建接口没有 `client_token`，组织架构 v1 自身「当前尚未提供事件」。首发不建议走这条路，只把 `employees/filter` 当作按工号查的备选。

**对设计的含义（第 4 节）**

- 处理工作流的写步骤分三类排队：创建（50 次/秒、带 client_token）、改部门和暂停（1 次/秒、串行）、删除（暂不开放）。
- 「到位」要读回核对：创建后读 `status.is_activated`，暂停后读 `status.is_frozen`，删除后读 `status.is_resigned`。
- 错误码到「谁能修」的分派表可以直接从文档建：范围类（40004、41050）给飞书管理员；席位类（41007、41008、44023、44046 到 44048）给飞书管理员或采购；数据类（41004、41005、41010、41003、44051）给 HRIS 或员工本人；外部数据源和生命周期引擎（44053、43031、44062）给飞书管理员并标「需要访谈确认」；锁冲突（44025、43024、43030）由平台自己退避重试。

## 5. 部门

### 5.1 部门 ID 的类型

- **原文**（[部门资源介绍](https://open.feishu.cn/document/server-docs/contact-v3/department/field-overview)，2026-04-07）
  - 根部门：「通讯录默认包含一个根部门（根部门的部门 ID 为 0）」。
  - `department_id`：「在创建部门时支持自定义配置，若不自定义配置，系统会默认生成一个 ID 值。因此，如果你的企业内部系统已有维护中的部门 ID，你可以将这些部门 ID 写入到飞书通讯录的部门 ID 属性中，由此实现飞书部门 ID 和企业内部系统部门 ID 的一致性，节省跨系统调用的映射成本。」不能以 `od-` 开头；「可以复用已删除部门的 department_id。因此，department_id 在未删除的部门范围内具有唯一性」；最长 64，正则 `^[a-zA-Z0-9][a-zA-Z0-9_\-@.]{0,63}$`。
  - `open_department_id`：「由系统自动生成，ID 前缀固定为 `od-`，无法自定义编辑。open_department_id 在租户内全局唯一。」
  - 改自定义 ID：`PATCH /contact/v3/departments/:department_id/update_department_id`（[更新部门 ID](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/reference/contact-v3/department/update_department_id)），要求部门在范围内。
- 各接口用 `department_id_type` 在两种 ID 之间切换，默认 `open_department_id`。

### 5.2 创建（`POST /contact/v3/departments`）

- **原文**（[创建部门](https://open.feishu.cn/document/server-docs/contact-v3/department/create)，2026-04-07）：「只可在应用的通讯录权限范围内的部门下创建部门。如果需要在根部门下创建子部门，则应用的通讯录权限范围需要设置为 全部成员。」支持 `client_token`「用于幂等判断是否为同一请求，避免重复请求」。上限：「单租户内部门总数上限为 30,000」「单个部门的直属成员数量上限为 10,000」「单个部门的直属子部门数量上限为 1,000」「部门层级上限为 25 层」；「该接口不支持设置自定义部门字段」。
- 错误码：43000「部门已存在」、43007「自定义的部门 ID 重复」、43022「部门名重复」（重名的判定范围是不是同级，需实测）、40014 没有父部门权限、43024「部门结构变动获取租户锁失败。由并发请求产生的冲突，请稍后重试」、43019 超过 25 层、43013 子部门过多、43029 名称不能含斜杠。

### 5.3 移动（改父部门，`PATCH /contact/v3/departments/:department_id`）

- **原文**（[修改部门部分信息](https://open.feishu.cn/document/server-docs/contact-v3/department/patch)）：「所涉及的所有部门需要在应用的通讯录权限范围内」；「leaders、department_hrbps 如果传入空数组，则会把原有值清空」；把父部门改成根部门需要全员权限（权限范围资源介绍的「全员权限说明表」）。错误码另有 43030「并发受限，请等待几秒后重试」、43031「无法编辑来自外部数据源的数据」。

### 5.4 删除（`DELETE /contact/v3/departments/:department_id`）

- **原文**（[删除部门](https://open.feishu.cn/document/server-docs/contact-v3/department/delete)）：「应用需要同时拥有待删除部门及其父部门的通讯录权限范围」；「待删除的部门下边不能包含用户或子部门」（43011、43012）。

**对设计的含义（第 5 节）**

- 部门映射表不是唯一解。飞书官方建议把内部系统的部门 ID 写进 `department_id`：平台新建的部门可以直接用北森组织编码做 `department_id`，映射表只管存量部门；改存量部门的 ID 会影响别的系统，只能作为管理员确认的一次性对齐动作。
- 「部门先于人员」的依赖要落到收敛顺序里：先建（或确认）部门，再建人；删部门前先移走人和子部门。
- 部门结构变更有租户级锁（43024、43030），部门类写操作也要串行。
- 平台建的部门自动落在范围内的父部门之下，不会新增 40004；建在根部门下则要求全员权限，这一点要在安装清单里提前说明。

## 6. 限流与配额

### 6.1 计数单位

- **原文**（[频控策略](https://open.feishu.cn/document/server-docs/api-call-guide/frequency-control)，2024-10-10）：「通常情况下，频控策略等级都是应用于 **每个 API**、 **每个应用**、**每个租户** 的基础上。」「写入接口的频控等级会略低于读取接口」；「对于不同时间周期内的限频策略（如 1000次/分&50次/秒），请求速率达到任意上限（QPS 或 QPM）都会触发限流」；「自建应用根据所属企业的套餐不同，对应的频控等级有所不同」（等级 10 基础版 50 次/秒、商业版 100 次/秒）；「飞书开放平台暂不支持自行调整 API 接口频控」，短期提频要找企业的 CSM，「消息、群组、多维表格暂时不支持提频」。

### 6.2 主线用到的接口限额

| 接口 | 限额（原文） |
| --- | --- |
| 创建用户、获取单个、批量获取、按部门列、按手机号邮箱查、删除用户 | 1000 次/分钟、50 次/秒 |
| 修改用户部分信息 | 1000 次/分钟、50 次/秒；但「更新 department_ids、is_frozen 时，限制调用频率为 1 QPS」 |
| 恢复已删除用户 | 10 次/分钟 |
| 更新用户 ID | 20 次/秒 |
| 创建、修改、删除部门，获取子部门，更新部门 ID | 1000 次/分钟、50 次/秒 |
| 获取通讯录授权范围 | 1000 次/分钟、50 次/秒 |
| 获取应用通讯录权限范围配置 | 100 次/分钟 |
| 获取企业席位信息 | 100 次/分钟 |
| 发送消息 | 1000 次/分钟、50 次/秒；另「向同一用户发送消息的限频为 5 QPS、向同一群组发送消息的限频为群内机器人共享 5 QPS」 |
| 组织架构 v1 | 创建 5 次/秒，更新、离职 10 次/秒，读 1000 次/分钟、50 次/秒，待离职 10 次/分钟 |

### 6.3 超限时的返回

- **原文**（频控策略）：「超过限制阈值时，飞书会返回 HTTP 状态码 429……并在失败请求的响应头中返回建议的等待时间」，示例响应头 `x-ogw-ratelimit-limit`、`x-ogw-ratelimit-reset`，响应体 `{"code": 99991400, "msg": "request trigger frequency limit"}`；「对于部分旧版 OpenAPI，你收到的 HTTP 响应可能略有不同（HTTP 状态码为 400）」；「使用该响应头延迟请求是解除限频的最好方法」。
- **结论**：没有 `Retry-After`，等待时间在 `x-ogw-ratelimit-reset`（秒）；判断限流要看业务码 99991400，不能只看 HTTP 状态。

### 6.4 另外两种「额度」

- **组织架构 v1 的企业级累计**（[组织架构概述](https://open.feishu.cn/document/directory-v1/overview)）：「组织架构接口采用应用级+企业级双重限制」「同一企业下多个应用调用同一接口时，累计触发企业级限制」。
- **基础免费版的月调用量**（[自建应用 API 调用量上限调整说明](https://open.feishu.cn/document/platform-notices/platform-updates-/custom-app-api-call-limit)，2026-06）：「飞书基础免费版内，单租户下所有企业自建应用的 API 调用总量上限」，2024 年 11 月 13 日起为「10,000 次/月」，文档写「2026 年 6 月份限时 100 万次」；超量后返回「HTTP 状态码：429、错误码：99991403」。**不计入**调用量的业务包括「认证及授权」「事件订阅」「通讯录」「飞书人事」等；**消息接口计入**；「调用 API 失败，返回 4xx/5xx 错误码，是否占用企业的 API 调用量？不占用。」2026 年 10 月当前的上限值，**需在管理后台「费用中心 > 权益数据」实测查看**。

**对设计的含义（第 6 节）**

- 产品备忘里「限流属于连接」和调研里的「限流属于对方租户」，对飞书都不准确。限流要挂在「对方系统定义的计数单位」上：飞书是「租户 × 应用 × 接口」，再加按动作的特例（改部门、暂停 1 次/秒）、组织架构 v1 的企业级累计和免费版的租户月额度。连接器声明计数单位，平台按声明排队。
- 同一个飞书应用被多条集成共用时，它们共享频控；客户为平台单独建一个自建应用，就不会和别的系统抢频控（月额度除外）。
- 错误分类：99991400 按 `x-ogw-ratelimit-reset` 等待后重试；99991403 是「本月额度用尽」，生成「需要飞书管理员升级版本」的问题，不能自动重试。
- 免费版租户里，「通知 HR 群」这一步消耗月额度，通讯录读写不消耗。预演和连接详情要分开显示这两种消耗。

## 7. 事件、长连接、卡片回调

### 7.1 通讯录事件

| 事件 | 类型 | 原文要点 |
| --- | --- | --- |
| [员工入职](https://open.feishu.cn/document/server-docs/contact-v3/user/events/created) | `contact.user.created_v3` | 「通过管理后台添加成员、调用创建用户 API」都会触发 |
| [员工信息被修改](https://open.feishu.cn/document/server-docs/contact-v3/user/events/updated) | `contact.user.updated_v3` | 覆盖「ID、用户名……状态、所属部门、直属主管……工号……自定义字段」等；带 `old_object`；「用户手机号和邮箱的变更会发送一条独立的事件」；用户须在范围内 |
| [员工离职](https://open.feishu.cn/document/server-docs/contact-v3/user/events/deleted) | `contact.user.deleted_v3` | 「通过管理后台离职成员、调用删除用户 API」都会触发 |
| 部门新建、信息变化、被删除 | `contact.department.created_v3` 等 | 见[部门新建](https://open.feishu.cn/document/server-docs/contact-v3/department/events/created)等 |
| 通讯录权限范围变更 | `contact.scope.updated_v3` | 带 `added`、`removed` |

平台自己的写入是否也会推回给自己（回环），文档没写，**需实测**。

### 7.2 推送语义（两种订阅方式通用）

- **原文**（[事件概述](https://open.feishu.cn/document/server-docs/event-subscription-guide/overview)）
  - 「需要在 3 秒内（TCP 建联的超时时间为 2 秒，回调整体的超时时间为 3 秒）以 HTTP 200 状态码响应该请求（长连接场景下，需要 3 秒内处理请求，且在 SDK 的处理函数中不抛出异常，即视为处理成功）。否则飞书开放平台认为本次推送失败，并以 15秒、5分钟、1小时、6小时 的间隔重新推送事件，**最多重试 4 次**。」
  - 「系统整个链路中出现超时等异常时，均会触发内部消息重发逻辑，这会导致接收事件时即使成功接收，仍会收到重复消息的情况」；2.0 版事件用 `event_id` 去重。
  - 「对于部分事件，开放平台使用了**有序事件**的形式进行推送……当有序事件发生阻塞时，后续投递的事件会直接进入重试队列排队」；哪些事件有序「可查看对应事件页面」。通讯录事件页面没有标注是否有序，**需实测**。
  - 「完成事件订阅方式配置后，即可为应用添加所需订阅的事件，并发布应用使配置生效」。

### 7.3 Webhook 模式（将事件发送至开发者服务器）

- **原文**（[将事件发送至开发者服务器](https://open.feishu.cn/document/ukTMukTMukTM/uYDNxYjL2QTM24iN0EjN/event-subscription-configure-/choose-a-subscription-mode/send-notifications-to-developers-server)）：「每个应用只能配置一个请求地址，该应用订阅的所有事件都会发送到该请求地址。」「该请求地址必须是 IPv4 公网地址。」保存时要「在 1 秒内」原样返回 `challenge`。
- [事件订阅常见问题](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/event-subscription-guide/event-subscriptions/faq)：「设置的请求地址必须是 IPv4 协议的、公网可访问的请求地址」。

### 7.4 长连接模式

- **原文**（[使用长连接接收事件](https://open.feishu.cn/document/server-docs/event-subscription-guide/event-subscription-configure-/request-url-configuration-case)，2026-06-11）
  - 「与开放平台建立一条 WebSocket 全双工通道（你的服务器需要能够访问公网）」「只需保证运行环境具备访问公网的能力即可，无需提供公网 IP 或域名、无需使用内网穿透工具」；内置加密鉴权，「无需额外解密、验签逻辑，也无需部署防火墙和配置白名单」。
  - 「长连接模式仅支持企业自建应用。」
  - 「长连接模式下接收到消息后，需要在 3 秒内处理完成且不抛出异常，否则会触发超时重推机制。」
  - 「每个应用最多建立 50 个连接（在配置长连接时，每初始化一个 client 就是一个连接）。」
  - 「长连接模式的消息推送为 **集群模式**，不支持广播，即如果同一应用部署了多个客户端（client），那么只有 **其中随机一个** 客户端会收到消息。」
  - 设置时「编辑订阅方式，选择 使用长连接接收事件……必须确保本地客户端启动正常，有长连接在线的情况下，才能保存成功」。Node.js SDK「版本需大于等于`1.24.0`」。
- **结论**
  - 是否需要公网：只要出网，不要入网。
  - 多实例怎么投递：每条事件随机投给一个在线客户端，不广播；最多 50 个连接。
  - 处理时限：3 秒，超时按 7.2 的节奏重推。
  - 订阅方式是应用级的单选：同一个应用不能一边长连接、一边推给某个 URL。
  - 需实测：没有客户端在线时事件是排队、按重试节奏丢弃还是直接丢；WebSocket 要放行哪些出网域名（文档未列）。

### 7.5 卡片按钮回传能否走长连接：新版能，旧版不能

- **原文**（[使用长连接接收回调](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/event-subscription-guide/callback-subscription/configure-callback-request-address)，2026-06-11）：长连接用于「飞书卡片交互、链接预览」等回调；「长连接模式仅支持企业自建应用」；「消息卡片回传交互（旧）回调不支持 使用长连接接收回调 订阅方式」；同样「每个应用最多建立 50 个连接」「3 秒内处理完成」「集群模式……只有其中随机一个客户端会收到消息」。
- **原文**（[卡片回传交互回调](https://open.feishu.cn/document/uAjLw4CM/ukzMukzMukzM/feishu-cards/card-callback-communication)，2026-05-09）：回调类型 `card.action.trigger`；「需要在 3 秒内响应回调请求，声明通过弹出 Toast 提示、更新卡片、保持原内容不变等方式响应用户交互」；`operator` 带点击者的 `user_id`、`open_id`、`union_id`、`tenant_key`；更新卡片用的 token「有效期为 30 分钟，最多可更新 2 次」。

### 7.6 消息的去重与读回

- **原文**（[发送消息](https://open.feishu.cn/document/server-docs/im-v1/message/create)）：`uuid`「用于在发送消息时请求去重。持有相同 uuid 的请求，在 1 小时内至多成功发送一条消息」；前提是开启机器人能力，私聊对象在可用范围内，群聊要求机器人在群里并有发言权限。
- **原文**（[获取会话历史消息](https://open.feishu.cn/document/server-docs/im-v1/message/list)）：「获取指定会话（包括单聊、群组）内的历史消息」，「获取消息时，机器人必须在被查询的群组中」；另有[获取指定消息的内容](https://open.feishu.cn/document/server-docs/im-v1/message/get)。
- **结论**：群消息能读回。发出后丢了响应的那条消息，能否从历史消息里按内容或标记认出来，**需实测**。

**对设计的含义（第 7 节）**

- 飞书连接默认用长连接收事件和卡片回调：自托管实例不用暴露任何公网入口，`lightweight.md` 里「公开的事件入口和管理界面要能分开暴露」对飞书就不再是问题。Webhook 只留给商店应用或客户强制要求的场合。
- 每个飞书应用只保持一到两个在线客户端（用 `distributedLock` 选主），收到事件只做验证和入 BullMQ 队列，3 秒内返回；用 `event_id` 去重。
- 订阅方式和事件地址都是应用级单选，平台必须独占一个飞书自建应用。安装清单里写「为本平台新建一个企业自建应用，不要复用 AnyCross 或其他系统在用的应用」。
- 官方重推 4 次后就不再推（最后一次约在首次失败 7 小时后），对账是必需能力，不是可选项。
- 「对方待办卡片」可以直接发到飞书，按钮走 `card.action.trigger`，以飞书身份（`operator.user_id`）认人，不需要「不登录就能点的 POST 链接」；回调必须 3 秒内应答，真正的重新检查放进队列，再用 token 在 30 分钟内更新卡片结果（最多 2 次）。
- 「每次变化一条」的通知：`uuid` 只防 1 小时内的重复，超过 1 小时的重试要靠平台自己的发送记录；需要证据时读回群消息。

## 8. 企业微信、钉钉速查

### 8.1 企业微信

- **写入**
  - 原文（[通讯录管理概述](https://developer.work.weixin.qq.com/document/path/90193)，2026-08-31）：「企业如果需要从自有的系统同步通讯录到企业微信，需要使用 通讯录同步secret」；「注意，自建应用、代开发应用、第三方应用仅能读取通讯录，不能编辑，且仅能读取可见范围内的通讯录。」
  - 原文（同页）：「配置企业可信IP，仅所配IP可调用通讯录API。（2022年6月20日起，新开启的通讯录同步必须配置企业可信IP。为保证企业数据安全，请配置本企业服务器的IP地址，不允许配置第三方服务商的IP）」；「只有管理员才可以看到“管理工具” - “通讯录同步”这个工具，其他分级管理员无操作权限。」
  - 原文（[创建成员](https://developer.work.weixin.qq.com/document/path/90195)）：「权限说明：仅通讯录同步助手或第三方通讯录应用可调用。」
- **读回核对**
  - 原文（[通讯录同步接口调整](https://developer.work.weixin.qq.com/document/path/96079)，2022-08-20）：通过通讯录同步调用接口或接收变更事件时，「将不再返回除ID（userid和部门ID）之外的其他信息，包括但不限于姓名、手机号、部门名等。通讯录的新增、修改、删除等写入接口不受影响」；影响范围是「新的IP（过去90天通讯录同步助手未使用过的IP）」和「新配置或修改的接收事件服务器」。
  - 原文（[获取成员ID列表](https://developer.work.weixin.qq.com/document/path/96067)）：「仅支持通过“通讯录同步secret”调用」，每页 `limit`「取值范围 1 ~ 10000」，返回 userid 与部门的对应。
  - 原文（[读取成员](https://developer.work.weixin.qq.com/document/path/90196)）：「应用只能获取可见范围内的成员信息」；「从2022年6月20号20点开始……新创建的自建应用与代开发应用，调用该接口时，不再返回以下字段：头像、性别、手机、邮箱、企业邮箱、员工个人二维码、地址，应用需要通过oauth2手工授权的方式获取」。
  - 原文（[获取部门成员](https://developer.work.weixin.qq.com/document/path/90200)）：「如需获取该部门及其子部门的所有成员，需先获取该部门下的子部门，然后再获取子部门下的部门成员，逐层递归获取。」
  - 结论：写用同步 secret，核对用「同步 secret 拿 ID 全量 + 自建应用读姓名和部门（可见范围内）」。手机号读不回来，匹配只能靠 userid。
- **事件与回调**
  - 原文（[回调配置](https://developer.work.weixin.qq.com/document/path/90930)）：「开发者提供的URL是公开可访问的」；验证请求要「在1秒内响应」；「企业微信服务器在五秒内收不到响应会断掉连接，并且重新发起请求，总共重试三次……目前无法保证100%回调成功，若开发者服务失败过多或者超时过多，企业微信可能会根据回调情况丢弃一些回调事件。建议开发者不要强依赖回调，需要额外机制对齐相关业务数据」。
  - 原文（[成员变更通知](https://developer.work.weixin.qq.com/document/path/90970)）：「由通讯录同步助手通过api发起的新增成员触发的事件不回调给通讯录同步助手应用」（更新、删除同理），即自己的写入不回环。
  - 长连接只给「智能机器人」：[智能机器人长连接](https://developer.work.weixin.qq.com/document/path/101463)（2026-05-25）支持消息回调和 `template_card_event`（「用户点击模板卡片按钮」），「每个智能机器人同一时间只能保持一个有效的长连接……新连接会踢掉旧连接」。通讯录事件没有长连接，**未查到**。

### 8.2 钉钉

- **写入**：原文（[创建用户](https://open.dingtalk.com/document/orgapp/user-information-creation)，2025-04-23）：企业内部应用「是」支持调用，权限「维护通讯录的接口访问权限」，第三方企业应用不支持；`userid`「员工唯一标识ID（不可修改），企业内必须唯一……如果不传，将自动生成」；`mobile`「企业内必须唯一，不可重复」。[删除用户](https://open.dingtalk.com/document/orgapp/delete-a-user)同一权限，删除时「该员工所在的考勤组会同步删除该员工」「智能人事花名册会同步删除该员工」。
- **读回核对**：原文（[查询用户详情](https://open.dingtalk.com/document/orgapp/query-user-details)，2026-09-10）：权限「成员信息读权限」；`mobile`「企业内部应用，只有应用开通通讯录企业员工手机号信息权限，才会返回该字段」。[获取部门用户详情](https://open.dingtalk.com/document/orgapp/queries-the-complete-information-of-a-department-user)：「本接口只支持获取指定部门下的员工详情信息，子部门员工信息获取不到」。
- **事件与回调**
  - HTTP 模式（[事件订阅](https://open.dingtalk.com/document/org/push-events)）：要配「HTTP请求接收地址」，「测试阶段可选择使用frp内网穿透工具生成公网服务」；「如果企业的回调地址没有在1500毫秒内返回正确的加密信息给钉钉服务器，钉钉服务器会判断为推送失败」。
  - Stream 模式（钉钉官方开发者百科 [概述](https://open-dingtalk.github.io/developerpedia/docs/learn/stream/overview/)、[协议](https://open-dingtalk.github.io/developerpedia/docs/learn/stream/protocol/)、[常见问题](https://open-dingtalk.github.io/developerpedia/docs/learn/stream/faq/)）：「零公网IP：不需要依赖公网IP或域名」，只需出网到 `api.dingtalk.com` 和 `wss-open-connection.dingtalk.com` 的 443 端口；支持「机器人收消息」「事件订阅：各类事件变更通知，例如员工入职离职」「互动卡片回调」；多连接时「钉钉服务端每次推送消息时候，通过随机策略选取一个Stream通道推送」；事件订阅「如果不回复 ACK，会触发服务端的超时重新推送」，正确 ACK 后「依然可能出现重复推送」。
- **限流**（[如何处理钉钉服务端API限流](https://open.dingtalk.com/document/orgapp/how-to-process-api-throttling-on-the-dingtalk-server)）：标准版「每个应用，调用每个接口」每秒不超过 20 次；每个 IP「超过20秒10000次」会被禁 5 分钟；标准版有每月调用量限制，通讯录接口不纳入。通讯录事件不纳入每月 Webhook 与 Stream 使用量限制（[不纳入使用量限制的事件清单](https://open.dingtalk.com/document/orgapp/appendix-a-list-of-events-not-included-in-webhook)）。

### 8.3 三家对照

| | 飞书 | 企业微信 | 钉钉 |
| --- | --- | --- | --- |
| 自建应用能否写通讯录 | 能（企业自建应用；商店应用不能） | 不能；要用「通讯录同步 secret」+ 本企业可信 IP | 能（「维护通讯录的接口访问权限」） |
| 读回核对 | 能，限通讯录权限范围 | 同步 secret 只给 ID；自建应用读可见范围内姓名、部门，2022-06-20 后新建的应用读不到手机和邮箱 | 能；手机号要单独权限 |
| 自定义账号 ID | user_id 可自定义、可改（有次数限制） | userid 可自定义 | userid 可自定义、不可改 |
| 列全量 | 按部门直属，递归要自己走 | 同步 secret 的 ID 列表每页最多 1 万；详情按部门逐层 | 按部门直属，游标分页 |
| 不要公网收事件 | 长连接（自建应用） | 通讯录事件不行；智能机器人可以 | Stream 模式 |
| 卡片按钮回调不要公网 | 新版卡片可走长连接 | 智能机器人长连接的模板卡片事件 | Stream 模式 |
| 官方对回调可靠性的说法 | 重推最多 4 次 | 「建议开发者不要强依赖回调」 | 事件订阅有 ACK 和超时重推，仍可能重复 |

**对设计的含义（第 8 节）**

- 「连接」要能声明自己的写入凭证和读取凭证可以不同：企业微信天然是两套（同步 secret 写、自建应用读），台账的「读回核对」要能用另一套凭证。
- 企业微信的可信 IP 只能填企业自有服务器，自托管反而合规；平台的「出网体检」要显示当前出口 IP，并提示填进「通讯录同步 > 企业可信IP」。
- 企业微信上「手机号兜底」做不到，匹配规则要允许只按 userid（或工号）匹配，并在搭建时就说明。
- 「不要公网」在飞书和钉钉都成立，在企业微信只对机器人成立；企业微信的通讯录事件要么开公网入口，要么只靠定时全量比对（`list_id` 每页 1 万，成本很低）。

## 10. 实测清单

### 10.1 准备

1. **注册一个真实的飞书免费租户**（不是开发者后台的「测试企业」）。只有真实租户才会走「创建版本 → 管理员审核」，第 3 节的生效时延只能在这里测。注意：未认证企业「人数上限为 100」、只能加 +86 手机号；「一个手机号码或者一个邮箱，一天只能加入三个租户」（44009），测试号码不要在多个租户间反复用。
2. （可选）在开发者后台建一个「测试企业」用于快速调试。原文：测试版应用「权限、事件和应用信息等发生变更，将自动生效，无需再重新创建版本和走审核流程」，「应用默认具有全员范围的通讯录权限」，测试企业「固定为未认证的基础版」，每个测试企业最多 100 名测试人员（[测试企业与人员](https://open.feishu.cn/document/develop-process/test-and-release-app/testing-enterprise-and-personnel-functions)）。所以范围类、审核类测试不能在这里做。
3. 建一个**企业自建应用**，开权限：「更新通讯录」「以应用身份读取通讯录」「获取用户 user ID」「通过手机号或邮箱获取用户 ID」「获取用户手机号」「获取用户邮箱信息」「查看成员工号」「获取应用信息」「调用 API 获取员工列表」（组织架构 v1），开启机器人能力和「以应用的身份发消息」「获取单聊、群组消息」，订阅通讯录事件和 `contact.scope.updated_v3`。
4. 准备组织：根部门下建 `P`（父部门）、`P/C1`（子部门）、`X`（与 P 平级、不放进范围）；成员 6 到 8 人，至少 1 人只在 `X` 里，1 人有直属上级，1 人没有上级，1 人是管理员。通讯录权限范围先设为「部分成员：P」，发布版本。
5. 每个测试都记录：请求、完整响应体（含 `code`、`msg`、`data`）、HTTP 状态、响应头（尤其 `x-ogw-ratelimit-*`、`X-Request-Id`）、时间点。

### 10.3 只能访谈或付费租户才能确认的

- 客户是否愿意为平台单独建一个飞书自建应用、把通讯录权限范围给到哪一层（第 7、3 节）。
- 客户能否接受 `user_id = 工号`、`department_id = 北森组织编码` 的约定（1.4、5.1）。
- 客户的飞书通讯录是否由外部数据源或「成员生命周期」维护（44053、43031、44062）。
- HR 是否接受「入职前 N 天就收到飞书邀请」（4.1）。
- `resurrect` 只能在付费版测（4.4）。

## 未查到与需实测（汇总）

- **需实测**：`client_token` 有效期与重放返回；41001、41002 响应是否带已存在用户 ID；PATCH 改直属上级为离职者的错误码；暂停后已登录会话是否立刻失效；接口能否暂停未激活账号、未激活账号是否占席位；范围外的人在 `batch_get_id` 里的返回形态；新建子部门进入范围的时延；管理后台改通讯录权限范围是否免发版、多久生效；组织架构 v1 按哪个数据范围过滤、`in` 上限、能否列全量、部门条件是否递归；长连接离线期间事件的去向、出网域名；自己写入是否回环；通讯录事件是否有序；单部门 500 人还是 1 万人；重复删除的错误码；消息 `uuid` 重复发送的返回；当前免费版月调用量上限。
- **未查到**：按自定义字段查人的接口；创建用户时关闭邀请的参数；`update_user_id` 的次数上限；企业微信通讯录事件的长连接方式；钉钉按部门列成员的每页上限。
