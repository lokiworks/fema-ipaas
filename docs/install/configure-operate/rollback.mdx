## Overview

FEMA Integration Platform ships a rollback command that reverses database migrations when you need to downgrade to a previous version. Most releases are fully rollback-safe — the release notes will let you know if one isn't.

## Backups

For most upgrades you won't need a backup, but if you want to be extra safe:

### PostgreSQL

```bash
pg_dump -Fc $DATABASE_URL > backup-pre-upgrade.dump
```

### PGLite

Copy the `pglite` folder inside your configured `FEMA_CONFIG_PATH`:

```bash
cp -r /path/to/config/pglite /path/to/config/pglite-backup
```

## Release Notes

Releases that include non-reversible database changes will have a note at the bottom of the release notes mentioning which migrations are affected. If you don't see a note, the release is rollback-safe.

## Rolling Back

The rollback command runs against the **current (newer) image** since it has the migration reversal logic. After rolling back the database, you swap to the older image.

### Step 1: Stop FEMA Integration Platform

```bash
docker compose down
```

### Step 2: Run the rollback command

Replace `0.78.0` with your current version and `0.77.0` with the version you want to go back to:

```bash
docker run --rm --env-file .env --entrypoint npm \
  lokiworks/fema-ipaas:0.78.0 \
  run rollback -- --to 0.77.0
```

If the release has breaking migrations, the command will ask you to confirm with `--force`:

```bash
docker run --rm --env-file .env --entrypoint npm \
  lokiworks/fema-ipaas:0.78.0 \
  run rollback -- --to 0.77.0 --force
```

### Step 3: Switch to the older image

Update your `docker-compose.yml`:

```yaml
services:
  fema:
    image: lokiworks/fema-ipaas:0.77.0
```

### Step 4: Start FEMA Integration Platform

```bash
docker compose up -d
```

## Rolling back to the previous image (migration manifest)

`--to <version>` undoes every migration whose `release` is newer than the version you give. Use it only when the target version is a real release boundary. Migrations added since the fork baseline are all tagged `0.89.0`, so `--to 0.88.3` lists all of them (22 at the time of writing), stops at the two that are marked breaking and changes nothing unless you add `--force`.

To go back exactly one image, give the command the list of migrations the older image knows. Every image ships it in `packages/server/api/dist/src/migration-manifest.json`:

```bash
MANIFEST=$(docker run --rm --entrypoint cat \
  lokiworks/fema-ipaas:0.77.0 packages/server/api/dist/src/migration-manifest.json)

docker run --rm --env-file .env --entrypoint npm \
  lokiworks/fema-ipaas:0.78.0 \
  run rollback -- --manifest "$MANIFEST"
```

The command undoes, newest first, the migrations that are in the database but not in the manifest, and then you switch the image as in Step 3. Before it undoes anything it checks that those migrations are exactly the latest ones recorded in the database, and stops with `Migration order mismatch` if they are not.

<Note>
Checked on a PostgreSQL 16 database that held a sample project: upgrading from the build before the backup, release change, reliability and service settings migrations to the current build added 8 migrations, kept every row, and the manifest rollback removed the 8 migrations and their tables and columns again, with the workflows, runs and connections still readable by the older build. The Docker commands above were not run in a container; the `npm run rollback` step was run with `node` directly.
</Note>

## Restoring From Backup

If you took a backup and prefer to restore from it:

```bash
dropdb fema
createdb fema
pg_restore -d fema backup-pre-upgrade.dump
```

Then switch your `docker-compose.yml` to the previous image version and start FEMA Integration Platform.

## For Contributors

Every new database migration must:

1. **Implement `Migration`** instead of `MigrationInterface`
2. **Set `breaking`** to `true` (destructive changes) or `false` (additive only)
3. **Set `release`** to the target release version (e.g., `'0.78.0'`)
4. **Implement `down()`** with working rollback queries

Example:

```typescript
import { Migration } from '../../migration'
import { QueryRunner } from 'typeorm'

export class AddNewColumn1710000000000 implements Migration {
    name = 'AddNewColumn1710000000000'
    breaking = false
    release = '0.78.0'

    public async up(queryRunner: QueryRunner): Promise<void> {
        await queryRunner.query(`ALTER TABLE "project" ADD COLUMN "description" text`)
    }

    public async down(queryRunner: QueryRunner): Promise<void> {
        await queryRunner.query(`ALTER TABLE "project" DROP COLUMN "description"`)
    }
}
```

These requirements are enforced by CI — PRs with migrations that don't meet them will fail checks.
