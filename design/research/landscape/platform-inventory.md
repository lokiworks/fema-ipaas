# 平台能力盘点：重新设计的地基

盘点对象是 `main` 分支（`fa504f817f`，2026-10-01）。依据：直接读源码和 codegraph 核对、`brain/knowledge/` 各区域页、`brain/knowledge/decisions/`（重点 000037 到 000042）、`docs/adr/`、`design/research/product-brief.md`、两版原型的说明。brain 和代码说法不一致时以代码为准，不一致的地方集中列在第 2 节。

**状态的含义**

| 状态 | 含义 |
| --- | --- |
| 已上线 | 代码在 `main`，有接口和界面，一台新实例里能用起来。不代表在真实客户环境验证过 |
| 部分实现 | 代码里有一部分，但缺关键环节，或者只在某一条路径上生效 |
| 只在原型里 | 只出现在 `design/`（第二版）或 `design/v3/`（第三版）的演示里 |
| 没有 | 代码和原型都没有 |

**验证程度**（对所有「已上线」都适用）：问题中心、发布审批、映射表、告警、运行日志只有纯函数单测和首发主线脚本（`tools/e2e/main-line/`，北森、飞书都是模拟服务，8 项全过），`packages/server/api/test/integration/` 里没有这些模块的集成测试；SSO、即时通讯告警渠道、OAuth、SSE 这类外部链路没有端到端记录；首发主线还没接过真实的飞书企业。

## 一页结论

1. **地基比两版原型显示的厚。** 版本化的工作流引擎、触发器的去重和并发保序和定时策略、问题聚合与重放预检、单实例内的测试与生产双环境（连接替换、审批、回滚、编辑锁）、写入前打码、MCP 双向、AI 生成工作流与编辑器助手，都已经在代码里。首发主线（北森变动 → 查映射表 → 飞书开通 → 通知 HR 群 → 出错进问题 → 修好后重放）在模拟服务上跑通了。
2. **备忘里 10 月 1 日定的「可靠性原则」，平台层几乎都没有。** 幂等只是一个给 AI 看的可选字段，没有任何代码读它；没有业务键、对账、按连接限流、启用时选起点、「结果未知」状态；轮询失败对用户完全不可见。第三版原型要证明的五件事，代码里一件都还没有。
3. **产品是按「资源类型」组织的，不是按「集成」或「同步」组织的。** 项目侧栏 12 个入口，新建工作流从「选触发器类型」开始，运行按运行 ID 列，问题按「工作流:步骤:错误码」聚合。「张三的账号开好了没有」这个问题，库里没有能直接回答它的数据。
4. **连接器很薄。** 新实例里只有 24 个连接器（20 个通用 + 北森、飞书、MySQL、PostgreSQL）。北森、飞书只够跑「入职开通」：飞书没有改部门、停用账号、列出全部账号，北森没有列出全部在职员工，两个都没有声明输出结构。
5. **改造成本的分界线很清楚。** 在 API 和前端加一层「同步」投影（业务键列、按键状态表、对账任务、新的问题类型），引擎基本不用动，属于中低成本；把「同步」做成平台自己执行的新原语（自己读两边、算差异、写目标、按记录记结果），等于再写一个引擎，而且贴着「不做 ETL」的边界。可靠性原则里真正贵的是按连接限流和「结果未知」两项，因为都要动引擎和连接器的调用路径，而引擎和连接器子进程碰不到 Redis。
6. **有几处「看起来做了、其实没做」，新设计要纠正。** 问题详情里的「根因分析 · 置信度 96%」是规则表加写死的数字；「从失败节点重放」用的是出错时的旧版本，修了工作流再这样重放，修复不会生效；映射表改动立即对生产生效，不分环境、不进审计，值班角色还改不了；AI 生成的草稿用的引用写法很可能和引擎对不上，跑起来入参是空的。

## 2. 容易误判的地方：说法和代码不一致

1. **「AI 根因分析」不是 AI。** `issueUtils.insightOf` 按错误类型返回固定的原因、固定的置信度（0.96、0.72、0.83……）和固定的修复按钮，界面用闪光图标写「根因分析 · 置信度 96%」。新设计要么接上真实的模型诊断，要么把它如实叫做「常见原因」。
2. **幂等声明存在，但没有人读。** SDK 的 `aiMetadata.idempotent` 和 `classification` 填在大多数第一方动作上，名字里的 `ai` 已经说明了定位。重放、批量重跑、步骤重试、智能体确认都不看它。
3. **「从失败节点重放」用的是出错时的版本。** `executionService.retry` 的 FROM_FAILED_STEP 分支读 `oldExecution.workflowVersionId`。重放预检把「工作流在失败后改过」算作可重放，而重放对话框默认就是「从失败节点」，于是修了工作流再重放，跑的还是旧逻辑。映射表例外：它在运行时实时读取，改了立刻生效。
4. **「不重复开通」靠的是飞书连接器，不是平台。** 首发主线脚本里「同一员工再次变动 → 不重复开通」这一项，靠 `provision_user` 先按手机号查人；同一个脚本期望 HR 群收到两次通知，也就是说「只在状态真的变化时通知」（决定 000042）还没有落地。
5. **轮询失败和丢事件都看不见。** 轮询出错只在 Redis 里给「租户 × 连接器 × 天」加一，没有界面；检查点推进之后建运行失败，这批变动就丢了，也只写一行日志。问题中心只看得到「跑了但失败」的运行。
6. **映射表绕开了所有变更管控。** 不分环境、不进版本、不走审批、不写审计，改完下一次运行立即生效；而值班角色反倒没有权限改它。
7. **测试环境跑不了轮询触发器。** 测试环境只有 Webhook 入口；编辑器里测试写操作会真的写进目标系统，没有试运行模式。
8. **令牌缓存基本不生效。** 飞书、北森的访问令牌缓存在模块里，而连接器每次调用都是新子进程，缓存只在一次调用内有效。
9. **默认没有连接器隔离。** 第一方连接器只能在 `UNSANDBOXED` 或 `SANDBOX_CODE_ONLY` 下运行，默认就是 `UNSANDBOXED`。
10. **和决定 000039 冲突的存量还在。** 新建工作流弹窗有「表单触发」，节点选择器有「人工」分类（等待审批、审批链接），公开的表单页面（`/forms/:workflowId`）也还在。
11. **brain 里有一批描述上游的页面。** Tables、知识库、事件目的地、密钥管理器、全局连接的付费门槛、连接器集合，在 `getEntities()` 里都已经没有对应的表；项目说明里写的「400+ 连接器」是上游的数，本仓库是 24 个。重新设计时不要把这些当成现有能力。
12. **小处：** 问题汇总里的 `alertsLast7Days` 写死为 0；运行日志的「共尝试 N 次」「沿用原结果」没有做，引擎不记录这两件事。
13. **AI 生成和助手修改出来的引用很可能解析成空值（需要跑一次确认）。** 生成工作流和编辑器助手的提示词都让模型用 `{{trigger.<路径>}}`、`{{step_1.<路径>}}` 写引用，单测也断言保留这种写法；而引擎交给表达式的步骤视图是 `{ output, error }`（`getStepView`），brain 的首发主线页明确写着漏了 `['output']` 会解析成空字符串；能把老写法改成 `['output']` 形式的 `expressionRewriter` 现在没有任何调用方。也就是说，AI 生成的草稿看起来引用齐全，跑起来入参可能全是空的。

## 3. 架构约束：哪些改动便宜，哪些贵

### 3.1 决定成本的几条结构事实

1. **执行的单位是「某个工作流版本的一次运行」，引擎只认工作流。** 映射表、变量、数据存储这些项目资源，都是运行时经 API 读取的。所以「同步」「对账规则」这类新对象可以完全放在 API 层，引擎不需要知道它们存在。
2. **引擎和连接器子进程碰不到 Redis 和 Postgres。** 它们只能拿引擎令牌调 API；连接器每次调用起一个新子进程，进程内缓存不跨调用；沙箱只透传白名单里的环境变量。凡是要跨调用共享的东西（令牌缓存、速率配额、幂等记录），都得经 API 往返。
3. **运行记录 = `execution` 一行 + 压缩日志文件（原始状态一份，打码后的展示日志一份）。** 行上能查的只有状态、时间、失败节点（JSONB）、`issueId`、`rerunOfExecutionId`、`tags`；步骤入参出参在 zstd 压缩的文件里（库里或 S3），不能查询。`execution` 行永远不删，只按保留期清日志文件，所以这张表只会越来越大；列表类的索引都以 `projectId, environment` 开头。
4. **触发器的状态散在三处。** `TriggerSource`（Postgres，按工作流唯一）、轮询检查点（连接器 store，Postgres）、去重窗口和并发排队（Redis，按 workflowId）。任何「跨工作流」的触发概念，都要同时考虑这三处。
5. **一个触发载荷就是一次运行。** 轮询和异步 Webhook 返回的每条记录都建一条运行（北森「员工变动」天然是一人一次运行），这让「运行 ≈ 一条业务记录」在首发主线上成立；批量型的触发（一次运行处理一批）不成立。
6. **问题是「项目 + 签名」唯一的一行，签名是字符串。** 加新的问题类型是加枚举值和签名规则，表结构不用大动；告警分发、复发、静默都挂在「问题被记录」这个事件上，新问题类型可以直接复用。
7. **环境是运行的一个属性。** `RunEnvironment` 由引擎令牌带着，worker 取变量和连接时据此换值；变量有测试值、连接有替换，其他项目资源都没有环境维度。
8. **连接器版本：** 第一方连接器镜像里只有一个版本，SDK 加字段、加操作都是加法，老工作流锁定的版本会落到同主版本的新包上，所以「给连接器加声明、加操作」很便宜；删字段、改含义要升主版本。
9. **工程纪律带来的固定成本：** 新实体要进 `getEntities()` 并写迁移；`@fema-ipaas/shared` 改动要升版本；engine 和 web 的构建不做类型检查，要单独跑 tsc 并逐文件对比；问题中心、发布、映射表没有 API 集成测试。改这几个模块，验证要算进估算。

### 3.3 专题：引入「同步」作为一等对象

**两种做法**

| | 薄：同步是一层投影 | 厚：同步是新的执行原语 |
| --- | --- | --- |
| 是什么 | 项目里的一个配置聚合，加一张按业务键的状态表；真正干活的仍然是工作流 | 平台自己按规则读源、算差异、写目标，按记录记结果（Census、Hightouch、Entra 入站开通的做法） |
| 数据库 | 新增同步、按键状态、对账规则 / 运行 / 差异 / 例外几张表；`execution` 加业务键列；`issue` 加同步 ID、业务键列 | 以上全部，外加按记录的结果表，一次运行 N 行，量级比运行记录大一到两个数量级 |
| 引擎 | 不动。收敛逻辑写在工作流里：按键读源 → 确保目标一致 → 有变化才通知；平台在运行结束的钩子（`executionHooks.onFinish`）里更新按键状态 | 新的引擎操作或独立服务：分页读两边、比对、批量写、按记录重试；连接器要提供实体级的列出、读取、写入、停用契约 |
| 触发器 | 业务键在触发器设置上定义（和去重键、保序键同一套键路径工具）；起点选择沿 `isRepublish` 的管道加参数；对账补齐、「再同步这个人」都调同一个可调用工作流 | 触发器退化成「什么时候跑一轮同步」，事件只是加速信号 |
| 问题中心 | 加新问题类型（对账差异、触发器失败），签名带同步 ID 和差异类型；运行失败的问题显示影响了几个人；重放变成「对这些键再跑一次」；告警、复发、静默原样复用 | 问题从「运行失败」变成「记录失败」，签名、重放、告警都要重做 |
| 和已定边界 | 符合决定 000040（对账只产出差异，补齐走工作流）和 000041（方案建在工作流上） | 贴着「不做 ETL」走，需要重新论证 |
| 成本 | 中 | 高 |

**薄做法对每一层的具体影响**

- **数据库。** 全是新增：一张「同步」表（所属项目、名称、源连接、目标连接、业务键定义、收敛工作流、入口工作流、对账规则、起点）；一张按键状态表（同步、业务键、最近一次运行和结果、最近同步时间、最近一次对账结论、两边摘要）；对账的规则、运行、差异、例外。迁移是加法，不需要标 `breaking`；唯一要小心的是给 `execution` 加索引，它是最大、最热的一张表。
- **引擎。** 不用改。要补的是连接器：飞书「改部门」「停用账号」「列出全部账号」，北森「列出在职员工」；把「开通账号」这种「确保存在」的语义推广到「确保一致」，并让动作返回「是否有变化」，通知步骤据此决定发不发。
- **触发器。** 一个同步可以有多个入口（北森轮询、对账补齐、手动「再同步这个人」），都指向同一个收敛工作流；`TriggerSource` 按工作流唯一，不受影响。前提是「一次运行一个业务键」，北森触发器已经满足。保序键直接用业务键，同一个人的入职、调岗、离职按到达顺序处理。
- **问题中心。** 加两种问题类型：对账差异（签名如 `recon:<同步>:<差异类型>`，差异和已有问题关联，不重复告警，这是决定 000040 的要求）、触发器失败。运行失败的问题按 `execution.issueId` 关联到业务键，就能显示「影响 5 个人」，重放时同一个键只跑最近一次。
- **前端。** 「同步」成为项目里的一等入口，首页按同步汇总「还没同步好的人数」= 按键状态表里不一致或未知的数量。
- **权限。** 可以复用工作流权限；如果希望值班的人能补映射表、处理差异，要放开相应权限（现在映射表要 `WRITE_WORKFLOW`）。
- **「一致」的真相来源。** 运行成功只能说明「平台做了该做的」，只有对账能确认「两边确实一致」，所以按键状态要同时吃运行结果和对账结果两路输入，界面上也要区分「已处理」和「已核对」。

### 3.4 专题：按业务键检索运行记录需要什么

1. **定义。** 触发器设置加「业务键」（键路径 + 显示名），校验、推荐候选字段都复用去重那套工具；去重键可以默认等于业务键。成本低。
2. **落库。** `execution` 加业务键列和 `(projectId, businessKey, created)` 索引。轮询、异步 Webhook、定时走 `submitPayloads`，载荷已经是触发器的输出，在 `executionService.start` 里就能算出来；同步 Webhook 传的是原始请求（`executeTrigger: true`），要等引擎回传触发器输出时（运行进度回调）再补写。成本低到中。
3. **重跑。** 「从失败节点」是同一行，键自然保留；「整体重跑」新建一行，要复制过去。
4. **查询和展示。** 运行日志加「业务键」精确匹配条件（不要用现在内容搜索那种 `ILIKE`）；问题详情显示影响了哪些键；重放预检按键去重。
5. **隐私。** 键本身可能是工号、手机号，而打码只作用于日志内容，不作用于列。可以学 `deduped_event` 的做法：存哈希做精确匹配，再存一份打码预览用来展示；按人删除数据时同时清这两列。「按姓名查」需要另存显示名，和打码规则有冲突，要明确取舍。
6. **历史数据。** 老运行没有键，回填只能逐条解压日志读触发器输出，建议只对新运行生效。
7. **局限。** 一次运行处理多个人（循环、批量触发）时一个运行对应多个键，需要子表，或者约束同步类工作流「一次运行一个人」。
8. **跨工作流按人汇总。** 要在项目或同步层面统一定义「员工 · 工号」这种键的含义，不同工作流抽出来的键才能放在一起看，这正是「同步」对象要承担的事。

结论：单个工作流内按键查运行是低成本；跨工作流的「查人页」（两边状态对照 + 完整经过）依赖「同步」对象和对账，是中成本。

### 4.4 第三版原型里有、代码里没有的

业务键；查人页（两边状态对照、完整经过、立即同步这个人）；重放前逐人检查并按幂等声明决定执行或跳过；「结果未知」的确认流程；对账（差异分类、补齐、可到期的例外、立即对账）；映射表覆盖率和就地补值；启用时选起点；连接的速率上限与排队；按用到的操作列出权限、通讯录权限范围检查；凭证到期变成问题；连接器深度打分；方案向导与首次对账；首页「需要处理的事按影响排序」「每个集成还没同步好的人数」「平台替你处理的」；「一个项目就是一条集成」的组织方式；AI 诊断给出依据。

## 5. 对重新设计的提示

**可以直接当积木用的，不必重做：** 问题聚合、复发和告警链路；重放预检的框架（加一个「动作声明」维度即可）；触发器运行设置里的键路径工具和保序键；单实例内的双环境、审批、回滚、编辑锁；写入前打码和原文保存期；可调用工作流（天然适合做「按键再跑一次」的收敛单元）；单操作执行（对账时读两边）；编辑器的校验规则表（往里加覆盖率、权限规则）；AI 产物的「待确认」机制。

**设计时不要假设已经存在的：** 业务键、按人查、对账、按连接限流、启用时选起点、「结果未知」、按幂等声明重放、连接器的全量名单和改部门与停用操作、方案模板、跨实例项目包、真实的 AI 根因分析、企业 IM 单点登录。

**建议的地基顺序**（每一步都能单独交付，大体上后一步依赖前一步）：

1. 业务键进运行记录：触发器上定义，运行日志按键筛选，问题显示影响人数，重放按键去重。
2. 轮询失败进问题中心；启用时选起点；检查点改为建完运行再提交。
3. 幂等声明升为连接器契约，重放和批量重跑按声明分类；重放对话框说清版本差异。
4. 连接器补齐：飞书改部门、停用、列出账号；北森列出在职、按工号读；两个都补输出结构和结构化错误。
5. 对账：只读，差异进问题中心，补齐调用收敛工作流。
6. 「同步」对象把前五步串成一个用户看得见的单位：按键状态、还没同步好的人数、查人页。
7. 方案模板和项目包共用一个格式。

按连接限流和「结果未知」放在对账之后：这两项要动引擎和连接器的调用路径，成本最高。首发主线的量（一次几十到一两百人）先用工作流级并发上限顶住；第 3 步做完之后，可以先用「不幂等的写操作不自动重试，超时就进问题等人看」这条保守规则顶替完整的「结果未知」流程。
