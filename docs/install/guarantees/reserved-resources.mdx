---
title: "Reserved Resources"
description: "Every workflow gets its own guaranteed CPU and memory slice. No workflow can starve or crash another."
icon: "memory"
---

Every workflow runs alone in its own worker, with a guaranteed slice of CPU and memory that nothing else can take. There is no noisy neighbour: one workflow can't starve another by pegging the CPU, and one workflow's memory blow-up can't take down anyone else's run.

We chose this: **isolation over density**. You pay for one worker per concurrent workflow rather than packing many workflows into one box, and in return every workflow's resources are predictable and its blast radius is itself.

<Note>
This is one of the FEMA Integration Platform execution guarantees for the [recommended production setup](/install/configure-operate/production-setup). For the full scope and Cloud parity, see [Crash Recovery](./crash-recovery).
</Note>

Two promises follow from one mechanism:

## A workflow can't be starved

A workflow that pegs the CPU or hangs cannot degrade any other workflow's latency. Each workflow has its own reserved CPU and memory, enforced by the orchestrator, so contention between workflows simply doesn't exist.

## An OOM kills one job, not its neighbours

A workflow that exhausts memory takes down only its own run. The worker is OOM-killed with `MEMORY_LIMIT_EXCEEDED`, the run is requeued and retried elsewhere (see [Crash Recovery](./crash-recovery)), and no other in-flight work is touched.

## How it's enforced

At `FEMA_WORKER_CONCURRENCY=1`, each worker container runs exactly **one workflow at a time**, hard-capped at its own CPU and memory by the orchestrator (e.g. 0.5 vCPU / 1 GB). One workflow's CPU spin is bounded by *its* container's CPU limit; one workflow's memory growth is bounded by *its* container's memory cap, and the kernel OOM-killer's blast radius is that single job. Nothing reaches into another worker. See [Workers](/install/architecture/workers).

About 300 MB of a 1 GB budget is overhead for a warm process with connectors loaded; the rest is the workflow's. To handle larger work, split it into multiple workflows (one workflow calls another via webhook, or each processes a smaller batch).

## Where it stops

The guarantee holds at concurrency 1. Running `FEMA_WORKER_CONCURRENCY` higher packs multiple workflows into one container and **reintroduces** the shared fate it removes: they contend for the same CPU and memory cap, and a single OOM takes down *all* in-flight jobs in that container. The shipped default is `5`; concurrency 1 is what keeps this promise, and is becoming the default. The cost of concurrency 1 is density: one worker per concurrent workflow (size the fleet from peak concurrent workflows, see [Production Setup](/install/configure-operate/production-setup)).

## Governing configuration

| Variable | Recommended | Effect |
|---|---|---|
| `FEMA_WORKER_CONCURRENCY` | `1` | One workflow per container, the isolation boundary and OOM blast radius |
| Container CPU / memory cap | 0.5 vCPU / 1 GB | The per-workflow reserved slice, enforced by the orchestrator |
