title: 联邦租户的管理员从身份源的成员名录里选人加进来，选中即按 issuer + sub 预绑
icon: 📇
status: accepted

## Decision

`matchBy=SUBJECT` 且平台开通时登记了成员变动订阅（`oidc.memberSubscription`，带着这家的集成服务应用连接）的租户，「添加成员」默认是「从成员名录选择」。名录不落库，每次都用这家的集成服务应用（`client_credentials` 业务连接）调 fema 的 `POST /iam-identity/member/find-all` 实时读，按名片的显示名或用户名搜索、分页。管理员勾选后选角色和模块权限，ipaas 先按 id 回 fema 复核这些成员确实在这家名录里且状态是 `ACTIVE` 或 `PENDING`，再按 issuer + 成员 ID 预绑（`external_identity.prebindRole`、`prebindModules`），不发任何通知。成员第一次经身份源登录时，`sso-user-resolver` 走预绑建号并给上选定的角色和模块。已有绑定（待登录或已建号）的人跳过，重复加入什么都不变；登录前可以撤销预绑。

其他租户（按邮箱认人、没有企业登录、或没有集成服务应用）保持原样，只有邮箱或手机号邀请。

## Context

决定 000046 让 SUBJECT 租户只认绑定，邮箱只用于显示；fema 的 sub 是成员 ID，成员可能只有手机号。管理员原来只能按邮箱或手机号邀请，邀请建出的本地账号和 fema 成员身份对不上，只有手机号的成员经 rental 的「集成」入口登录仍被拒（`USER_NOT_PROVISIONED`），rental-saas 验收场景集成 5 过不去。决定 000047 已经给每家租户配了集成服务应用，它在 fema 有读成员与组织的许可。产品方向照飞书集成平台：成员从企业通讯录里选。

## Why

否决了「被拒的人提交申请、管理员审批」：用户没选；它要另起申请对象和审批流，被拒的人还得先知道去哪里申请，而管理员本来就知道该加谁。也否决了「继续用邮箱或手机号邀请，再想办法和 fema 成员对上」：fema 的名片按设计只披露显示名、用户名和账号状态，手机号和邮箱拿不到，没有可靠的对应关系，按联系方式猜就回到了 000046 否决的路子。名录不落库，是因为成员会改名、停用、移出，镜像一份就要处理同步和过期；成员事件和联邦复核已经管着状态，这里只在选人那一刻读当前值。

## Consequences

- 只能按名字或用户名搜，不能按手机号搜：fema 的成员名片不含手机号，这是数据主人的不变量，不是 ipaas 的限制。
- 名录读不到（fema 不可达、连接缺失、没有读权限）时界面直接报错，不显示空名单；预绑不经过名录就不会发生，浏览器提交的成员 ID 一律回 fema 复核。
- 预绑不占成员数上限，首次登录建号时才按 `usersLimit` 检查；管理员停用的已有账号在名录里显示「已停用」，在成员列表里启用，不经名录。
- 成员列表把待首次登录的预绑显示为「待激活」（`kind: BINDING`），可以撤销；平台接口加的预绑也一样显示。
- 以前按手机号邀请、建出了本地手机号账号的人，再从名录选一次，首次经身份源登录会得到另一个账号；两者没有可靠依据合并，需要管理员把旧账号移除或转移资源。
