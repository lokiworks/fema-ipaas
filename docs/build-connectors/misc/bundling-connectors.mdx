FEMA Integration Platform builds every connector into a **self-contained bundle**. Instead of shipping a connector that depends on `@fema/shared`, `@fema/connectors-framework`, `@fema/connectors-common`, and the `@fema/core-*` packages at install time, the build inlines all of that code into a single artifact.

This is what lets the engine provision a connector by downloading **one artifact** — no `bun install` / `npm install` of a dependency tree at runtime.

### What gets bundled

When a connector is built for publishing, the bundler:

- **Inlines all `@fema/*` workspace libraries** (`shared`, `connectors-framework`, `connectors-common`, `core-utils`, `core-connector-types`, …) directly into the bundle. These libraries are **never published to npm** — they only exist as part of each connector's bundle.
- **Inlines third-party dependencies** (e.g. an SDK the connector imports) into the same bundle.
- **Keeps a small allow-list of deps external** only when they genuinely cannot be inlined — native addons or packages that use dynamic `require`. These remain in the published `dependencies` so the runtime installer resolves them.

The result is typically **~2–3× smaller** than the raw inputs, and the published `package.json` lists only the few unavoidable external deps (e.g. `tslib`).

### The published manifest

After bundling, the connector's `dist/package.json` is rewritten:

```jsonc
{
  "name": "@fema/connector-json",
  "version": "0.1.7",
  "main": "./src/index.js",      // the self-contained bundle
  "dependencies": {
    "tslib": "2.6.2"             // only genuinely-external deps remain
  },
  "files": ["src/index.js", "package.json", "src/i18n"]
}
```

No `@fema/*` dependency appears — installing the connector never requires those packages to exist on the registry.

### Forcing a dependency to stay external

If a dependency must not be inlined (for example a native module), add it to a `bundleDeps` array in the connector's `package.json`. The bundler will keep it external and preserve it in the published `dependencies`.

```jsonc
{
  "name": "@fema/connector-example",
  "bundleDeps": ["some-native-addon"]
}
```

### Files loaded at runtime (forked processes)

A file your connector loads by path at runtime — for example `child_process.fork(path.join(__dirname, 'runner.js'))` — is invisible to the bundler's import graph, so by default it would not exist in the published package. Declare it in `bundleForkedEntries`:

```jsonc
{
  "name": "@fema/connector-oracle-database",
  "bundleForkedEntries": ["src/lib/common/oracle-runner.ts"]
}
```

Each declared entry is bundled on its own and emitted **next to the main bundle** at `src/<name>.js` — which is where `path.join(__dirname, '<name>.js')` resolves at runtime, since the bundled parent code lives at `src/index.js`. Dependencies that only the forked file imports (e.g. `oracledb`) are still captured into the published `dependencies`.

The bundler **fails the build** if connector code uses `__dirname` without declaring any `bundleForkedEntries`, because such code breaks silently after publishing.

### Building and publishing

Bundling happens automatically when you build or publish a connector:

- `npm run build-connector <name>` — builds and packs the bundle into a `.tgz` (see [Build Custom Connectors](./build-connector)).
- `npm run publish-connector-to-api` — bundles and uploads the connector to a platform (see [Publish Custom Connectors](./publish-connector)).

You don't need to configure anything for bundling — it is the default behavior.
